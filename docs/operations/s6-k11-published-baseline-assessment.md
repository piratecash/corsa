With the [old driver constraints][k11-old-driver], this statically supports the pure-Go modernc path despite CGO1. It is not independent whole-binary/source identity or runtime wiring proof. Existing cached v1.57.0 Linux amd64 source (`lib/sqlite_g_000000000001fea8.go:16918–17140`, helper `lib/sqlite.go:39705–39725`) syncs FULL commits before publishing the new reader-visible WAL header; sync/write errors prevent normal publication. Its recovery path (`lib/sqlite_g_0000000000001a80.go:11992–12038`) reconstructs headers from valid WAL commit records without proving successful original application Exec/sync. Recovered or IO-error-ambiguous rows remain UNKNOWN. These are cached-source observations, not portable runtime proof; see SQLite [isolation][k11-sqlite-isolation] and [WAL/FULL semantics][k11-sqlite-wal].

A conditional route exists: a calibrated reading **before the original send invocation** gives a causal lower bound, not proof async sending finished by the pending response. A fresh isolated SQLite read returning the exact final-recipient **application-message** tuple (ID/sender/recipient/original attempt, `topic=dm`) can give `FIRST ≤ positive-read completion + clock uncertainty`, after proving successful live FULL commit applicability. Read the live DB/WAL together with fresh snapshots; receipt/status/system rows are insufficient. Raw chatlog bodies are ciphertext: plaintext-token search and a sole-new-row delta do not alone prove the action/ID join. Errors, drops, ambiguous joins, competing/replacement sends, restart/recovery and clock gaps stay UNKNOWN. Actual writer-connection FULL, VFS/filesystem durability, API/schema, correlation and complete success/error coverage remain unverified; the reader's PRAGMA cannot prove writer settings. External fsync or restart survival cannot redefine the application's first successful durable commit.

The smallest future check is one isolated original application send on the unchanged Desktop pair with bounded reads and retained causal/error/clock evidence. Disclose emulation before launch; profile, resources and runtime permission remain separate. No threshold, G2, activation or release decision changes.
