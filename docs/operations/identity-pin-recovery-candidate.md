# Identity pin recovery candidate

## English

This is an inactive implementation candidate. Public identity pin confirmation always returns unavailable, including under a verified supervisor. The [dedicated desktop modal](identity-pin-desktop.md) is implemented and respects unavailable production confirmation. The owner approved the Linux stop/finalize workflow on 2026-10-18. This does not establish independent deployment provisioning or authorize public RPC activation.

Preview consequence version 2 binds the token to the candidate's additional consequence: stop the node, perform at most one removal per node before external operator finalize, and never treat a receipt alone as permission for network restart. Endpoint bindings and other v2 requirements survive. A later proof pins the identity normally.

The Linux candidate consists of a separate mTLS broker ledger, a root launcher and a separate-UID node child. The broker must reside in an independently provisioned failure domain. The launcher and its credentials remain outside the node volume. The launcher owns a canonical per-node lifetime lock; the child retains the inherited raw FD4 until kernel exit. Only the actual private FD3 handshake can construct a verified session; an interface, zero session or environment variable alone cannot do so.

The launcher requires `--candidate`; `--recover` selects the distinct offline role and network namespace. The child profile must explicitly supply `CORSA_STARTUP_FENCE_CANDIDATE=1`, `CORSA_STARTUP_FENCE_LAUNCHER` (absolute expected root-owned launcher path) and `CORSA_STARTUP_FENCE_STORE`. The launcher supplies `CORSA_STARTUP_FENCE_FD=3`. An incomplete profile is refused. This allowlisted profile supports a reviewed subset of node settings, not every environment option; it never inherits the launcher's complete environment or broker credentials.

`corsa-node` connects and branches on the verified recovery role before `App.Run`, pprof, RPC, bootstrap priming or peer listeners. Recovery needs the original complete pin store, even when both guard and marker disappeared. It restores protection durably, preserves sibling pins/endpoints, acknowledges the restored receipt, and exits. Missing/corrupt main or a damaged/foreign guard is a refusal. No network startup follows recovery in the same process.

An external fenced permit precedes every local removal write. The node records a receipt after confirmed local main and guard cleanup; that receipt does not un-fence the broker. A failure retains the runtime pin and attempts protective rollback. Unconfirmed rollback latches fatal recovery and propagates a nonzero process outcome even through cancellation and a successful final flush.

After every App/Service teardown and final write, the child performs the bounded private shutdown handshake carrying its exact last acknowledged receipt and acknowledgement challenge. It then exits immediately. The launcher seals only that receipt after actual exit zero; a crash, nonzero exit, missing acknowledgement, raw EOF or timeout remains fenced. Private requests are bounded by caller cancellation/deadline and a five-second maximum; an incomplete exchange poisons session framing and cannot be reused as a success acknowledgement. The final close has its separate two-second exit bound.

A private `committed` result confirms local removal only: the overall workflow remains awaiting finalization. Full workflow completion requires actual child exit zero, an exact sealed receipt and external operator finalize. The result distinguishes confirmed removal from confirmed protection restoration; restoration is never successful removal. The operator must see the node-shutdown warning before mutation. The operator CLI emits the broker status as JSON: `last_finalized_receipt.kind` distinguishes `clean_committed` from `protection_restored`; exit zero alone does not mean the pin was removed. A pending absent pin retains one restoration slot in the global capacity; its own reproof may consume that slot. Fresh recovery grants can replace an earlier restored snapshot after an interrupted attempt, but old grants and generic receipt writes cannot. Supervisor TERM allows bounded graceful direct-child teardown; only verified exit zero permits bounded broker completion after cancellation. Deployed control-group policy remains responsible for descendants. A separate authenticated external operator finalize selects the exact sealed receipt. A clean receipt preserves the removal after the next approved startup; a restored receipt preserves the pin. Core removal/recovery never invokes finalize. The workflow is approved; independent broker provisioning and admission of the environment and every startup path remain required; the candidate tests do not enable public removal or prove actual Windows support. Strict Windows local storage refuses mutation.

The 30-second storage context limits admission to subsequent stages; it cannot interrupt a kernel-blocked open, rename or fsync. Tests cover returning errors and uncertain acknowledgements, not permanently uninterruptible storage I/O.

## Русский

Это неактивный кандидат реализации. Публичный confirm снятия identity pin всегда возвращает unavailable, в том числе под проверенным supervisor. [Отдельный desktop modal](identity-pin-desktop.md) реализован и соблюдает недоступность production-подтверждения. Владелец утвердил Linux stop/finalize workflow 2026-10-18. Это не подтверждает независимое provisioning окружения и не разрешает включение публичного RPC.

Версия последствия preview 2 связывает token с дополнительным последствием кандидата: остановить узел, выполнить не больше одного снятия на узел до external operator finalize и никогда не считать receipt разрешением перезапуска сети. Endpoint-привязки и остальные требования v2 сохраняются. Последующее proof закрепляет identity обычным порядком.

Linux-кандидат состоит из отдельного mTLS broker ledger, root launcher и node child с отдельным UID. Broker требует независимо подготовленного failure domain. Launcher и его credentials остаются вне node volume. Launcher держит канонический lifetime lock на узел; child сохраняет унаследованный raw FD4 до kernel exit. Verified session создаёт только реальное private FD3 handshake; интерфейса, zero session или переменной окружения недостаточно.

Launcher требует `--candidate`; `--recover` выбирает отдельную offline-роль и network namespace. Child profile явно задаёт `CORSA_STARTUP_FENCE_CANDIDATE=1`, `CORSA_STARTUP_FENCE_LAUNCHER` (абсолютный ожидаемый root-owned путь launcher) и `CORSA_STARTUP_FENCE_STORE`. Launcher передаёт `CORSA_STARTUP_FENCE_FD=3`. Неполный profile отклоняется. Allowlist поддерживает проверенное подмножество настроек, а не все параметры окружения; полный environment launcher и broker credentials не наследуются.

`corsa-node` подключается и выбирает проверенную recovery-роль до `App.Run`, pprof, RPC, bootstrap priming и peer listeners. Recovery требует целиком загруженный исходный pin store, даже если исчезли и guard, и marker. Оно durable-восстанавливает защиту, сохраняет соседние pins/endpoints, подтверждает restored receipt и завершает процесс. Отсутствующий/повреждённый main или повреждённый/чужой guard означает отказ. После recovery сеть в том же процессе не запускается.

Внешний fenced permit предшествует любой локальной записи снятия. Узел записывает receipt после подтверждённых локальных main и cleanup guard; receipt не снимает broker fence. Ошибка сохраняет runtime pin и запускает protective rollback. Неподтверждённый rollback фиксирует fatal recovery и даёт ненулевой исход процесса даже после отмены и успешного final flush.

После всех App/Service teardown и последних записей child выполняет bounded private shutdown handshake с точным последним ACKed receipt и acknowledgement challenge, затем немедленно завершает процесс. Launcher запечатывает только этот receipt после реального exit zero; crash, ненулевой exit, отсутствующий ACK, raw EOF или timeout сохраняет fence. Private requests ограничены отменой/deadline вызывающего и максимумом в пять секунд; незавершённый обмен делает framing непригодным для повторного использования как ACK успеха. Final close имеет отдельную границу exit в две секунды.

Приватный результат `committed` подтверждает только локальное снятие: весь workflow ещё ожидает finalization. Полное завершение workflow требует реального child exit zero, точного sealed receipt и external operator finalize. Итог различает подтверждённое снятие и подтверждённое восстановление защиты; восстановление никогда не считается успешным снятием. До операции оператор видит предупреждение об остановке узла. Операторский CLI выводит broker status в JSON: `last_finalized_receipt.kind` различает `clean_committed` и `protection_restored`; один exit zero не означает снятия pin. Отдельный аутентифицированный внешний operator finalize выбирает точный sealed receipt. Clean receipt сохраняет снятие после следующего разрешённого старта; restored receipt сохраняет pin. Core removal/recovery никогда не вызывает finalize. Workflow утверждён; независимое размещение broker и проверка окружения и всех способов запуска остаются обязательными; тесты кандидата не включают публичное снятие и не доказывают actual Windows support. Strict Windows local storage отклоняет мутацию.

Storage context на 30 секунд ограничивает переход к следующим этапам, но не прерывает заблокированные в kernel open, rename или fsync. Тесты покрывают возвращаемые ошибки и неизвестные ACK, а не навсегда непрерываемый storage I/O.

Отсутствующий pending pin сохраняет одно место в глобальной ёмкости для восстановления; его собственное
reproof может занять это место. Fresh recovery grant позволяет заменить прежний restored snapshot после
прерванной попытки, но старый grant и generic receipt — нет. Supervisor TERM допускает ограниченный
graceful teardown прямого ребёнка; только проверенный exit zero разрешает bounded broker completion после
отмены. За descendants отвечает deployed control-group policy.
