# S6 · пилот внешнего UTC и подготовка baseline

На одной уже работающей Linux-ноде соберите **16 раундов с шагом 60
секунд**. Это примерно **15 минут в сети** после готовности RPC.
Для пилота используйте штатный трафик. Нужны chronyd с внешним
источником времени и доступ пользователя corsad к локальному
Unix-сокету `/run/chrony/chronyd.sock`. Команда использует
`/usr/bin/chronyc`. Сначала можно вызвать `getBaselineClock` из
локальной RPC-консоли и проверить `status`.

Из корня репозитория, с настроенными локальными учётными данными
`CORSA_RPC_USERNAME` и `CORSA_RPC_PASSWORD` в окружении:

```sh
python3 scripts/s6-baseline-rpc.py --output s6-clock-pilot.jsonl
```

Передайте полученный `s6-clock-pilot.jsonl` и полный SHA сборки.
Скрипт обращается к аутентифицированному RPC на IPv4 loopback.
При другом локальном порту используйте `--port`. В файл попадают
ответы RPC без заголовков авторизации и паролей. Если файл
показывает `status: unavailable`, пришлите его с полем `reason`.
Код возврата 2 сохраняет все раунды и означает неполный пилот.

`getBaselineClock` возвращает boot ID, time namespace, идентификатор
локального сокета chrony, SHA-256 `chronyc`, исходный tracking CSV
и скобки MONOTONIC/BOOTTIME/REALTIME по обе стороны запроса.
Команда принимает пустые аргументы. Через HTTP она доступна
только по loopback с включённой аутентификацией. На других ОС
команда сообщает о недоступности.

Для квалификации проверяем источник и свежесть tracking, leap status,
System time, root delay и root dispersion, границы скобок и согласие
часов. Состояние `sample` подтверждает сбор данных. Для доказанного
UTC-интервала также нужны независимая граница ошибки источника,
непрерывность домена часов и предел дрейфа. Поле `current_time`
штатного RPC берётся с системных часов узла. Пропуск данных,
неподтверждённая непрерывность или смена домена оставляют интервал
UNKNOWN.

## Запуск семисуточного baseline

1. Принять пилот и закрепить роли реальных источников по плану,
   версии и SHA-256 бинарников и сборщиков, параметры опроса и UTC.
   Для R0 с неизменённым опубликованным бинарником внешние скобки
   должен снимать сборщик в том же часовом домене. Новый RPC
   на кандидате не добавляет этот источник к R0.
2. Закрепить манифест и окно после проверки всех источников.
   Проверить на каждом источнике закрытие интервалов, обнаружение
   пропусков и сохранение RAW. Для критериев непрерывности срезы
   RPC дополняют события и сведения о потерях.
3. Собирать семь **общих непрерывных суток**. Отсчёт начинается с
   первого общего квалифицированного интервала. Разрыв требует нового
   общего окна. Пилот одной ноды даёт первичные данные для
   квалификации и отдельный результат по её RPC.

### Нода в Docker

В штатном образе есть `corsa-cli` и `jq`. Проверьте источник
clock RPC внутри контейнера:

```sh
docker exec corsa-node corsa-cli -host 127.0.0.1 getBaselineClock
```

Если ответ содержит `status: sample`, из корня репозитория на
Docker-хосте запустите:

```sh
sh scripts/s6-baseline-docker.sh corsa-node s6-clock-pilot.jsonl
```

Укажите фактическое имя контейнера при необходимости. Понадобятся
те же 15 минут в сети. Файл пишется на хосте. Скрипт использует
настроенную аутентификацию ноды и loopback внутри контейнера.
Python и публикация RPC-порта для этого варианта не нужны.

Штатный Dockerfile не устанавливает `chronyc`. При
`status: unavailable` пришлите первый JSON с `reason`, прежде чем
собирать весь пилот. `clock_domain_or_chrony_socket_unavailable`
означает, что команда не смогла прочитать часовой домен или увидеть
Unix-сокет. `chronyc_binary_unavailable` означает, что проверка
`/usr/bin/chronyc` не прошла. `chrony_tracking_unavailable` означает,
что локальный вызов `tracking` не завершился штатно.

Если chronyd работает на хосте, для квалификации нужно сверить
его с контейнером по часовой области и источнику UTC. Установка
`chronyc` сама по себе не даёт этой привязки.
