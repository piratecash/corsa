# Service Locking — Domain Mutex Split

## English

### Motivation

`node.Service` historically guarded every piece of in-memory state with a single `sync.RWMutex` (`s.mu`). That mutex covered at least seven distinct concerns — peer connections, message delivery queues, cryptographic knowledge, gossip topics, IP-level policy, file transfer, and aggregate status. Go's `sync.RWMutex` is writer-preferring: one queued writer blocks every new reader until every in-flight reader drains. Any write to any domain therefore serialised reads across every other domain.

Under reconnect storms this produced a reader-starvation failure class where `fetch_network_stats`, `fetch_peer_health`, `get_peers` and similar read-mostly RPCs stalled for 10–15 s while a burst of peer-management writers drained.

Phase 1 addressed the hot read paths by materialising atomic snapshots outside `s.mu`. Phase 2 attacks the root cause: the single mutex itself. The fields of `Service` decompose naturally into seven independent domains — a write to one domain must not block a reader in another.

### Domain mutex map

Every previously-`s.mu`-protected field moves to exactly one of the following mutexes. Each mutex is a `sync.RWMutex`; reader-dominated domains benefit from the RWMutex split, and we keep the shape uniform.

| Mutex | Fields |
|---|---|
| `peerMu` | `sessions`, `health`, `peerIDs`, `peerTypes`, `peerVersions`, `peerBuilds`, `inboundHealthRefs`, `identitySessions`, `identityRelaySessions`, `sessionTransitionSeq`, `peers`, `conns`, `connIDByNetConn`, `connIDCounter`, `dialOrigin`, `persistedMeta`, `peerStateDirty`, `pendingWithdrawals`, `withdrawalsShutDown`, `setupFailures`, `peerQuarantine`, `peerDisconnectHistory`, `peerAnnounceHistory`, `lastResyncAccepted` |
| `deliveryMu` | `pending`, `pendingKeys`, `outbound`, `relayRetry`, `awaitingDelivered`, `recipientPassState`, `cancelledDeliveries`, `frozenDeliveries`, `markedNeverEmitted`, `awaitingSeenAck`, `sentDMIDs`, `seenReceipts`, `receipts`, `upstream` |
| `knowledgeMu` | `known`, `boxKeys`, `pubKeys`, `boxSigs`, `selfRecord`, `selfRecordBody` |
| `gossipMu` | `topics`, `seen`, `subs`, `notices`, `events`, `lastExpiredCleanup` |
| `ipStateMu` | `bans`, `inboundByIP`, `observedAddrs`, `observedIPHistoryByPeer`, `bannedIPSet`, `remoteBannedIPs`, `remoteIPBanOffenders` |
| `fileMu` | `fileStore`, `fileTransfer`, `fileRouter` |
| `statusMu` | `aggregateStatus`, `lastPublishedAggregateStatus`, `lastAggregateStatusPublishAt`, `versionPolicy`, `lastVersionPolicyPublishAt` |

**Penalty records are keyed by `penaltySubject`, never by a named identity.** `peerQuarantine`, `peerDisconnectHistory`, `peerAnnounceHistory` and `lastResyncAccepted` (all `peerMu`), the `announceLimiter` buckets and the `nonDMKeySync` hop records are keyed by `penaltySubject` (`penalty_subject.go`): the identity only when a v2 session proved it over the connection, otherwise the address this node dialled, the TCP source IP, or the connection for loopback. Resolving a subject adds no lock edge. For a dialled session it is `peerSession.penaltySubject()`, computed from fields written in the struct literal (`address`, `proven`) and never rewritten, so it needs no lock. For an accepted connection it is `penaltySubjectOfCore`, which reads only the NetCore's own synchronised state (`Auth()`, `RemoteAddr()`); `trackInboundDisconnectWithPresenceEvidence` therefore resolves it from the core it already holds, without re-entering `peerMu`. `connPenaltySubject` takes `peerMu.RLock` through `netCoreForID` and is called only by the receive dispatch, outside every domain mutex. The close path receives the closing session's subject as a parameter (`onPeerSessionClosedWithAttribution`), so `maybeArmRouteQuarantineOnCloseLocked` charges it inside the same `peerMu` section as before. Transit gating (`isPeerTransitQuarantinedLocked`) reads only the proven-identity entry, under the same lock as before. See `docs/protocol/network_security.md` §13.

**Legacy claims of an identity that requires v2** (`v2_identity_claims.go`). `identityRequiresV2` reads the pin store under its leaf `mu` and then, separately, takes `peerMu.RLock` to look for a live v2 connection (`identityHasProvenConnection`); the two are never held together and the caller holds no domain mutex — it is called from the receive handlers, `refuseLegacyIdentity` (hello, welcome, the `auth_session` re-check, and the outbound re-check right after a legacy session is registered), `ReactionsSupportOf` (before it takes `peerMu.RLock` itself) and the hop-ack paths. `onIdentityProvenV2` runs in `openInboundTransport` / `provenTransport` after the pin is written and BEFORE the v2 connection is registered, holding no domain mutex: `closeLegacyClaimsOf` snapshots the legacy connections naming the identity under `peerMu.RLock`, releases it and only then closes them (a close tears down through the connection's own reader, which takes `peerMu`); `unprovenRouting.waitDrained` then waits — holding no mutex at all — until every legacy routing handler of the identity that was admitted before the pin has finished its write; only then does `forgetUnprovenRoutingResidue` call `routing.Table.ForgetUplink` (`t.mu` only) and the announce registry, with no domain mutex held. A handler is admitted by `admitRoutingInput`, which counts it in (`enter`) BEFORE it re-reads `identityRequiresV2`: either the handler sees the pin and refuses, or the proof sees the handler counted and waits for it — there is no window in which a check passed and a write lands after the purge. The handler holds no domain mutex while counted in and its write takes only the routing table's own lock, so the wait cannot close a cycle. If the caller's context ends first (a dial timeout, not only shutdown), the purge is not dropped: `owePurge` hands it to the last in-flight handler, whose `release` (`releaseRoutingInput`) runs `forgetUnprovenRoutingResidue` while still counted in flight — so a proof waiting meanwhile wakes after it — and the cancelled proof fails, so its connection is not registered. `release` is therefore called with no domain mutex held: every handler releases after its write and outside its own locks, and the hop-ack timer callback runs after `rs.mu` is released. `unprovenRouting` (`unprovenRoutingWriters`) owns a leaf mutex outside the domain split — see below.

Fields that remain outside this scheme:

- `listener` — written exactly once inside `Run` before `Accept`. Keeps its existing single writer discipline; readers observe it via `loadListener` if needed.
- `done`, `connWg`, `backgroundWg`, `peerActivityNanos`, `trafficMu` / `lastTrafficSnap`, `*Snap` atomic pointers — already have their own synchronisation (chan, WaitGroup, `sync.Mutex`, `atomic.Pointer`). Not covered by the domain split.
- `backgroundMu` (`sync.Mutex`) / `backgroundClosed` (`service.go`) — the ADMISSION GATE in front of `backgroundWg`. Outside the seven-domain split with their own synchronisation: `backgroundMu` is a leaf that guards only `backgroundClosed` and orders the `backgroundWg.Add` that `goBackground` performs under it; no other lock is ever taken under it and it is never held across I/O or a callback, so it adds no edge to the canonical order. `goBackground` checks the flag and calls `Add(1)` in one critical section and reports whether the job was admitted; `Run` sets the flag in its FIRST registered defer, so it runs LAST — after the inbound drain, after `stopRunLifecycle` has joined every lifecycle loop and outbound session goroutine, after the subsystem teardowns and `close(s.done)`. Work scheduled by the teardown itself is therefore still admitted and joined by `WaitBackground`; work asked for once `Run` has returned is refused and never started. That is what keeps `WaitBackground` — which callers run after `Run`, right before closing the stores and deleting the data directory — from racing an `Add` that raises the counter from zero (a `WaitGroup` misuse the race detector reports), and keeps receipts, key-sync dials and trust-store writes off a stopped node. `WaitBackground` does NOT close the gate: unit tests use it as a barrier on a Service that was never run and keep scheduling work afterwards. A refusal is logged at debug with the call site; the three callers that hold something for the job act on it: `runSenderKeySyncPass` returns the in-flight slot itself (`release`), `triggerRouteQueryAsync` releases the target's in-flight slot (`releaseInFlight`), `tryEnqueueGossipJob` reports `gossipPoolShutdownDrop`. Every other caller is fire-and-forget on a node that has stopped for good — the refusal is the same outcome as the process exiting. **The refusal makes no exception for a continuation:** a job admitted before `Run` returned that asks for a follow-up afterwards — `pushBacklogToSubscriber` → `goBackground(confirmEnvelopesDurably)`, `writePushFrame` → `confirmEnvelopeOnWire` → the durable confirmation on `goBackground` — is refused like any other. Its effect is what a crash at that instant would leave (the envelope stays unconfirmed on disk), and it is recovered the way a crash is: by the sender-owned delivery retries and the durable journals on the next start. Refusal log: `background_job_refused_after_run_returned` at debug, carrying `node`, `op` (`goBackgroundOp` names the operation; `goBackground` logs `unnamed`) and `caller`. Pinned by `TestBackgroundJobIsRefusedOnceRunHasReturned`, `TestBackgroundJobIsAdmittedWhenRunWasNeverCalled`, `TestARefusedSenderKeySyncPassReturnsItsSlotExactlyOnce`, `TestTheGossipFallbackDropsAJobOnceRunHasReturned`, `TestARefusedRouteQueryReleasesItsInFlightSlot` and `TestRunServiceForTestDrainReportsUnfinishedBackgroundAsError`. `WaitBackground` has a precondition: `Run` is not executing — after `Run` has returned no job can be admitted, and on a Service that was never run the caller owns every goroutine that schedules work.
- **`Run` assigns no field that a caller of the Service can read.** The application starts the RPC server and the metrics collector BEFORE it calls `Run` (`internal/app/node/app.go`), and the desktop and SDK runtimes hand the Service to the UI while `Run` starts on a goroutine of its own, so every local-frame handler and every RPC provider method may run concurrently with `Run`'s start-up. A plain field assigned there is published to those readers with no happens-before edge — a data race, not a startup ordering detail — and waiting for `connManager.Ready()` only hides it from callers that know to wait. A value such readers need is built in `NewService`; a value that only `Run` can build is published through an atomic store that its readers load first. The fields this rule covers:
  - `runCtx` / `runCancel` — the Service lifecycle context and its cancel, minted by `NewService` (`context.WithCancel(context.Background())`) and immutable afterwards; a `context.Context` is safe for concurrent use, so reads take no lock. `Run` never replaces it: it makes it FOLLOW the caller's context (`context.AfterFunc(ctx, runCancel)`) and cancels it on every exit, the backstop `defer` being registered before the first return. Two consequences are deliberate: work that captured `runCtx` BEFORE `Run` (the sender-key recovery goroutine, for one) is still ended by `Run`'s teardown, where the old per-`Run` assignment left it on a context nothing would cancel; and the caller's deadline and values do not carry over, only its cancellation. `Run` is single-shot (it closes `done`), so a cancelled `runCtx` after `Run` returns is final. Pinned by `TestTheLifecycleContextTakenBeforeRunEndsWithRun` and `TestReadingTheLifecycleContextDuringRunStartupIsNotADataRace`.
  - `captureManager` — built by `NewService` (`newCaptureManager`, bound to `runCtx`), immutable afterwards, synchronised by the `capture.Manager`'s own mutex, so readers (the capture RPCs, `peerHealthFrames` behind `fetch_peer_health`, the connection taps) take no domain mutex. `Run` owns only its shutdown (`defer s.captureManager.Close()`). It exists before `Run`, so a capture RPC served before `Run` reaches the same manager instead of being refused; `nil` survives only in struct-literal test Services, which is why the nil checks stay. Pinned by `TestTheCaptureManagerExistsBeforeRun` and `TestCaptureRPCDuringRunStartupIsNotADataRace`.
  - `gossipJobs` / `gossipNoticeJobs` — the one exception that stays assigned in `Run` (`startGossipDispatch`), because the struct-literal Services of the pool tests start it directly. They are PUBLISHED by the `gossipPoolUp.Store(true)` that follows the assignment, and a dispatcher reads a lane only after `gossipPoolUp.Load()` returned true: `tryEnqueueGossipJob` takes the ADDRESS of the lane field and dereferences it behind the load. Reading the field at the call site — the shape before — raced `Run` even for callers that wait for `connManager.Ready()`, since the pool starts after it. Pinned by `TestGossipDispatchDuringRunStartupIsNotADataRace`.
  - Assignments in `Run` that stay safe and why: `listener` (under `peerMu`), `relayStates.onHopAckTimeout` (written before `relayStates.start()`, whose `go` statement is the edge to its only reader, the TTL ticker), the file-transfer handles (under `fileMu`). A new assignment in `Run` must name its edge here in the same commit.
- `unattributedNonDMDrops` — `atomic.Uint64` counter of non-DM pushes refused because the author's key is unknown (`refuseUnattributedNonDM`). Own synchronisation, observability only.
- `nonDMKeySyncPasses`, `nonDMKeySyncSkipped` — `atomic.Uint64` counters of the non-DM key-sync budget (`nondm_key_sync.go`). Own synchronisation, observability only.
- `trustedKeysAtLoad` — what `NewService` did with the trust store's keys (`classifyContactKeys`: refused contacts, dropped box pairs). Written once in `NewService`, immutable afterwards; no lock is required.
- `inboundClosed` — peer domain (`peerMu`): set by `closeAllInboundConns` at shutdown and never cleared; `registerInboundConn` refuses once it is set, so a connection between its first byte and its registration when the drain ran cannot register unseen and hold `connWg`. `inboundBeforeRegister` — a test hook between the session handshake and registration; set only before `Run`, immutable afterwards.
- **The three one-way shutdown flags, in the order `Run`'s teardown raises them** (all are single-shot, as `Run` is): `inboundClosed` (`peerMu`) first, by `closeAllInboundConns` in the inbound drain — no connection registers after it, so `connWg.Wait` waits for a closed set; then `withdrawalsShutDown` (`peerMu`), by `cancelAllPendingWithdrawalsForShutdown` after the drain and before the lifecycle join — no route-withdrawal timer is armed and no withdrawal body runs after it; and `backgroundClosed` (`backgroundMu`) last, by the first-registered defer after the join and every subsystem teardown — no fire-and-forget job is admitted after it, so `WaitBackground` waits for a closed set. Each refuses a different producer; none of them is taken under another, and the two under `peerMu` are written in separate critical sections.
- `secureSessions` — the v2 session state (`session_secure.go`): set once in `NewService` and never replaced. Its mode, `sessionv2.Local` and certificate source are immutable or synchronise themselves; its address marks (`sessionAddressMarks`) own a leaf mutex under which nothing is called and no domain mutex is taken. Its downgrade-protection store (`secureSessionStore`, `secure_session_store.go`) has a leaf `mu` for the maps (and the `pin_store_full` refusal counter; `SecureSessionStoreStats`, read by the lock-free `fetchRouteSummary`, takes only this leaf) and a separate `writeMu` that serialises disk writes and is held WITHOUT `mu`: the snapshot is taken under `mu`, the file is written after it is released, and no domain mutex is ever held across either. The v2 handshake runs in `handleConn` and in every dial path (`openPeerSessionForCM`, `syncPeer`, `sendNoticeToPeer`) BEFORE the connection is registered, so it holds no domain mutex and touches no domain state.
- `unprovenRouting` — the marks of identities a legacy connection wrote routing input for, and the count of legacy routing handlers in flight per identity (`v2_identity_claims.go`); a mark is consumed when the identity proves itself over v2, and the proof waits for the in-flight count to reach zero. Its own leaf mutex: it is touched once per legacy routing frame on the receive path, where `peerMu` is the hottest lock; nothing is called and no other mutex is taken under it, and waiters block on a channel AFTER releasing it. Bounded (4096) WITHOUT eviction: a mark is never dropped before its TTL, because a dropped mark would mean "no legacy residue" when there is some; a full store instead switches every proof to purging for one TTL. Swept against the TTL by the maintenance tick. The close of a session that did not prove its identity also leaves a mark: the close writes flap history and the withdrawal in that identity's name.
- `nonDMKeySync` — the non-DM key-sync admission state. Guarded by `senderKeySyncMu`, the same leaf mutex as the DM recovery maps (`senderKeySyncInFlight`, `senderKeySyncHopInFlight`, `senderKeySyncLastRun`); nothing is called and no other domain mutex is taken under it.
- `presenceClock` — assigned once by `NewService` and immutable afterwards; it timestamps both direct EOF observations before withdrawal grace and transit loss observations during snapshot rebuild. Tests replace it before starting lifecycle work. No lock is required.
- `presenceProjection` — a leaf mutex plus the previous reachability/`hasTransit` map used only for last-online ownership. Snapshot capture takes `presenceProjection.mu → routing.Table.t.mu` and holds the leaf lock across the entire exclusive `SnapshotIncremental` build, the one combined reachability/source-classification pass and the atomic cache store. Direct teardown takes `peerMu → presenceProjection.mu → routing.Table.t.mu`; therefore a teardown queued behind snapshot capture holds `peerMu` for that wait and temporarily stalls the whole peer domain. This dependency already existed for the table build itself, but the presence layer must not lengthen it with duplicate route/health passes. Event publication, persistence and filesystem I/O happen after release.
- `presenceProjector` / `presenceSnap` / `lastPresenceSnapAtNanos` — the per-contact liveness projection (`presence_projector.go`, `presence_service.go`). The projector's mutex is a **leaf**: it is taken inside `project` and inside each `note*` event, and nothing external is called under it. That is enforced by construction rather than by discipline — `project` gathers every external answer (routing state per contact, aggregate status, probeability) into a local slice BEFORE taking the lock, so the callbacks that reach into `routing.Table`, `statusMu` and the datagram scheduler cannot run underneath it and cannot invert the canonical order. The published snapshot is an `atomic.Pointer` of the `*Snap` class above, for the reason that class exists: the contact list repaints on every frame, and a hot reader must not queue behind a routing writer. `refreshPresenceSnapshot` is called from `rebuildRoutingSnapshot` **after** `presenceProjection.mu` and `peerMu` are released, never from inside that section.

  Note that this is a second, unrelated thing named "presence". `presenceProjection` (above) is the routing-side bookkeeping for last-online attribution; `presenceProjector` answers the human question "is this contact there". They share a word and nothing else — different state, different mutex, different consumers.

- `presencePublishMu` — the mutex serialising one presence pass with its publication. Three writers reach `refreshPresenceSnapshot`: the presence loop, the routing refresher (before it publishes `TopicRouteTableChanged`, so a subscriber never reads a presence generation older than the routing change that woke it) and each liveness event. The previous-generation comparison that decides whether to emit `TopicContactPresenceUpdated` — and which contacts count as arrivals for the delivery wake — is only meaningful under one lock.

  **It is an OUTERMOST mutex, not a leaf, and an earlier revision of this document said the opposite.** The pass gathers its inputs while holding it, and those inputs reach across most of the node: `presenceLocalConnectivity` → `AggregateStatus` (`statusMu`), `presenceContacts` → the trust store's own mutex, `presenceRouteStateFor` → `routing.Table`, `presenceContactIsProbeable` → the trust store, the datagram scheduler's `Reachable` and, on a miss, `startPresenceIdentityResolution`. The wake-ups at the end add `deliveryMu` twice (`kickDeliveryRetriesForReachable`, `wakeOverdueForPresenceReturn`). So the contract has two halves and only the first was ever written down:

  1. **Enter holding no domain mutex.** Every current call site does, which is why there is no deadlock to find today — but the guarantee came from the call sites, not from the lock, and a fourth caller reaching `refreshPresenceSnapshot` from under `peerMu` or `deliveryMu` would inherit an inversion the document told it was impossible.
  2. **Under it, domain mutexes are taken ONE AT A TIME and in canonical order**, each released before the next is acquired. Nothing here holds two at once, so the pass adds no new edge between domains; what it adds is an edge from `presencePublishMu` to all of them, which is why nothing may take it while holding one.

  The projector's own mutex stays a leaf underneath all of this, for the reason its bullet gives: `project` gathers the external answers before locking.

  `sessionTransitionSeq` is listed under `peerMu` above and is the counter that orders a session close against a reconnect (`nextSessionTransitionLocked`). It is minted inside the same `peerMu` section that decides the 0 → 1 / 1 → 0 transition, and that placement is the whole point: a clock reading has to be taken BEFORE the lock, so two overlapping sessions can take their readings and then reach the lock in the other order. Presence compares transition numbers and never the readings.

- `presenceProber` — immutable after `NewService`; its schedule and open attempts live behind its own leaf mutex (`presence_prober.go`), which is never held across `SendLocal`. It is a separate engine from `identityResolver` even though both send `get_identity`: a resolution ENDS when it succeeds and a liveness question never does. The two are told apart at ingest by whose label an answer carries.

- `identityResolver` — immutable after `NewService`; every mutable field of the identity lookup engine lives behind the resolver's own mutex (`identity_resolver.go`), and its disk I/O (the durable intent table) runs outside any domain mutex.
- `connBudget` (`internal/core/connbudget`) — the shared connection ceiling, and a **leaf** by
  construction rather than by discipline: nothing inside that package calls out, so no other lock
  can be taken while its mutex is held. That is what makes it usable from BOTH sides of a boundary
  the canonical order forbids crossing — `ConnectionManager` takes it under `cm.mu` when it reserves
  capacity for a dial, and `registerInboundConn` takes it under `peerMu` when it admits a socket.
  Neither one reaches the other, so the forbidden `cm.mu → peerMu` edge does not appear. Both take
  it LAST; nothing takes anything under it.

  This leaf is the only lock taken under `cm.mu`. Everything else runs with `cm.mu` released, on
  the event loop: every slot-state publication on the ebus (a synchronous subscriber may read the
  slot table), closing an evicted session (`tearDownSession` — the close is I/O and the session's
  `onClose` takes `peerMu`), scoring an `add_peer` eviction victim (`slotScoresForEviction` —
  `PeerProvider.Score` reads peer health under `peerMu`), reading the slot limit (`MaxSlotsFn`), the
  setup-failure ban lookup, the pin lookup, and every other `ConnectionManagerConfig` callback.

  The reservation handle it returns is deliberately a value that can be MOVED rather than a counter
  someone has to remember to decrement: an outbound unit travels with the dial attempt and, when
  its slot disappears mid-dial, is parked in `ConnectionManager.orphanReservations` keyed by the
  attempt's generation, because removing a slot does not cancel a dial and the socket it may still
  open must stay accounted for. Release is idempotent, so the several ends an attempt can have —
  failure, shutdown, a late success closing a stale socket — cannot free the same unit twice and
  inflate the ceiling.

- `identityFileMu` — a leaf mutex serialising the `identity_backup` / `identity_restore` local RPC pair: both funnel secrets through one predictable `<path>.tmp` (`identity.Save`, `writeSecretFile`), so two concurrent calls could interleave write-then-rename — or remove each other's temp — and acknowledge content another call wrote. The name→path resolution (`resolveIdentityBackupPath`) runs INSIDE the same section, not before it: its symlink check is a check on what is there right now, and a check performed outside the lock that guards the write is a TOCTOU window, not a check. Held only inside the two frame handlers around the file I/O; it takes no domain mutex, no domain mutex takes it, and it adds no edge to the canonical order.
- The two snapshot-persisted stores (`trustStore`, `identityIntentStore`) share one write discipline: a mutator takes the store's own state mutex, advances a **snapshot generation counter**, copies the state and releases the mutex BEFORE any disk I/O. The write itself runs under the store's dedicated `saveMu` (they share one `.tmp` path), and a snapshot whose generation is ≤ the last persisted one is dropped — two mutators racing to the disk can land in either order, and the generation, not scheduling luck, decides what the file holds. `saveMu` is never taken with the state mutex held and no domain mutex is anywhere near either lock. The trust store's session-record cache (`sessionRecordCache`, trust_session_records.go) is a leaf under the same state mutex: a non-contact record merges under `trustStore.mu` and never reaches `saveMu` at all — no snapshot, no disk write — which is what keeps a push from every new session peer off the I/O path; the TTL sweep runs from the bootstrap loop under the state mutex alone. The cache's live set — the addresses whose seq floor must survive the TTL and the budget — lives in `recordProtection` (record_protection.go), NOT in the trust store and not in a set handed to it periodically. A hold is taken inside the critical section that makes its fact true: the `peerMu` section of `onPeerSessionEstablished` that increments `identitySessions`, and the `r.mu` section of `StartResolution` / `reseedFromIntents` that inserts into `resolutions`; the releases sit in the matching sections of `onPeerSessionClosedWithAttribution` and `finishLocked`. `recordProtection.mu` is a LEAF taken under those domain mutexes — the same shape as `seenReceipts` under `deliveryMu` — and it takes nothing further, does no I/O and calls nobody back. The cache does not read the set and then delete: `sessionRecordCache.dropLocked` calls `recordProtection.dropIfUnprotected`, which checks the holds and runs the removal callback inside ONE `recordProtection.mu` section, so a pin is ordered strictly before the check or strictly after the removal. A lock-free read followed by a delete — the shape this replaced — leaves the interleaving where the pin lands between them and the entry is removed under a session that is already live; re-reading the answer narrows the window without closing it. The nesting is therefore `trustStore.mu → recordProtection.mu`, with the callback touching only cache state the caller already owns under `trustStore.mu`. The lock-free `recordProtection.contains` survives for exactly one caller, the `identity_record_cache_protected` gauge, where a one-instant-stale answer costs nothing. Neither shape creates `trust.mu → peerMu`, which would sit beneath the existing `presencePublishMu → trust.mu` and `trustMutationMu → trust.mu` edges and would put the resolver's intent-store disk I/O under the state mutex the snapshot-generation design exists to keep I/O out of. `bootstrapLoop` calls `reconcileRecordProtection` before the sweep: it reads a generation, recomputes the holds from `identitySessions` (`peerMu.RLock`) and the open resolutions (the resolver's own mutex) — each taken and released on its own while the loop holds nothing — and commits only if the generation has not moved, so a session that opened during the gather cannot be erased by counts that predate it. Three attempts, then the pass gives up: what it would install is what the events have already installed. It is the self-heal for a missed hold or a doubled release, not the mechanism.
- `messageStore`, `seenAckJournal`, `deliveryFailureJournal`, `emissionJournal` — registered once before `Run` (RegisterMessageStore / RegisterDeliveryOutbox) and immutable afterwards, so reads need no mutex; their SQLite I/O never runs under a domain mutex. The failure-journal write is synchronous after lock release (it is the durable boundary of retry abandonment — shutdown does not wait for backgroundWg before the chatlog closes); MarkSeenConfirmed may run on the background pool, losing it only costs one redundant idempotent seen re-send. `emissionJournal` is the one reached through a lane of its own — `emissionLane`, described in the delivery-retry section below — because its two writers compete for the same single SQLite writer and one of them is on the critical path of an outgoing message.
- `conversationControl` — the door for accepted `dm_control` commands (reactions today). Registered once before `Run` (RegisterConversationControlStore) and immutable afterwards, exactly like `messageStore`, so reads need no mutex. Its SQLite I/O runs on the datagram ingress goroutine and under NO domain mutex: the handler in `dm_control.go` takes none, and the type's registration is the only thing it shares with the rest of the node. On the desktop side it lands in `ReactionControlAdapter`, which takes the same `removalGate` lease `MessageStoreAdapter` does — a fact written during a conversation wipe would otherwise survive it as a row no deletion path can reach. The adapter's own mutable state is one map, `reoffer` (per conversation: the next page, the current backoff interval and when the periodic pass may take it), behind its own `reofferMu`: it is written from the datagram ingress goroutine when a session opens a round and from the router's reaper loop on every pass, and it belongs to neither. That mutex is a leaf — nothing external is called under it — and it is never taken from under a domain mutex.
- `dmControl` — the outgoing conversation-control sender (`dm_control_send.go` for the pass, `dm_control_outbox.go` for what is queued, `dm_control_policy.go` for what is believed about the peer's build — three files, ONE mutex, because a pass reads both halves and they must not disagree mid-pass). Set once in `NewService` and immutable afterwards; all of its mutable state lives behind its OWN `sync.Mutex`, so it sits outside the seven-domain scheme in the same way `identityResolver` does. Two rules keep it there.

  1. No domain mutex is ever held when a path enters it. There are EIGHT entry points, and the list is what a new caller is checked against: `QueueReactionFacts`, `ReactionsSupportOf`, `QueuedReactionsFor`, `ForgetPeerReactions` and `HoldReactionSends` from the service layer, `answerCommandUnsupported` and `noteCommandRefused` from the datagram handler, and `forgetDMControlRefusal` from the node's own session paths (`peer_sessions.go`, and the inbound `auth_ok` branch in `service.go`). That last one is the only one inside the node, so it is the one most easily added to under a lock. `ForgetPeerReactions` and `HoldReactionSends` are the entries that BLOCK — both wait for the frames of that peer already being sealed, see below — so on top of the shared rule neither may be entered from the send path they wait on, and a caller that holds anything of its own while calling them holds it for the length of one hand-over to the plane. `HoldReactionSends` is the bracket a per-message delete puts around itself: the queue names reactions rather than messages, so it cannot see that delete coming, and a frame built from the record a moment earlier would otherwise go out about a message that has just been erased. What it stops is requeued, not dropped.
  2. Its own mutex is never held across anything external — `takeDue` releases before `send`, so the box-key lookups, the seal and the hand-over to the plane all run unlocked. A future caller that reaches it from under a domain mutex breaks the first rule and must not be added. Its MUTABLE state is exactly `pending`, `refusedAt`, `typeRefusalShown`, `forgot`, `inflight`, `framesOut`, `paused` and `draining`, all eight behind that one mutex, with `quiet` (a `sync.Cond` on it) for the one wait described below. `pending` holds KEYS, not facts: what a queued reaction says is read from the chatlog when the frame is built, so nothing here is a copy of state another path can delete. `ForgetPeerReactions` clears the first three for one peer in a single section when the contact or the conversation is removed — immediately rather than waiting for the next flush to find the keys stale — and then handles the two things the maps cannot reach. A batch `takeDue` has already handed to `send` is no longer in `pending`: it is marked through `inflight` on the batch ITSELF (`dmControlOutbox.abandoned`, pointer identity rather than a counter, which would be an ABA the moment a sweep reset it), and `send` refuses to start another of its frames while `requeue` refuses to put the rest back. And a frame already past that mark is still being sealed and built OUTSIDE the mutex, so the removal WAITS on `quiet` until `framesOut[peer]` is zero — the same shape as `removalGate.begin` one layer up, and for the same reason: a check is not a write. It follows that `ForgetPeerReactions` must never be called from the send path itself, which it waits on. `forgot` is the third piece and is about what the PEER says back: an answer to a frame sent before the removal arrives after it, and is refused for `dmControlForgetGrace` — a window derived from the longest such chain (our frame's remaining validity on the plane, the peer's own outbox retrying its answer, that answer's trip back), which a new fact for the peer deliberately does not cut short; entries are swept in the same pass as the refusals; everything else on the type (`svc`, `clock`, `jitter`, `dispatch`) is set before the send loop starts and never written again, and the frame builder is `sync.Once`-guarded. `draining` is raised by `dmControlSendLoop` while it runs and read by `canSendLocked`; an atomic beside the mutex was tried and rejected, because `stop()` has to lower the flag and clear the outbox as ONE step — with the flag outside, an enqueue taken between the two lands in a map nothing will ever look at again.
- `lastPeerSave`, `lastPeerEvict`, `lastSync` — peer-lifetime timestamps; move with `peerMu`.
- `peerStateDirty` — moves with `peerMu`. Set by `markPeerStateDirty` on every path that mutates persisted peer state outside the periodic catch-all — add_peer, remote-ban record (`handlePeerBannedNotice`) and remote-ban clear (`clearRemoteBansOnAuth`) — instead of a synchronous `flushPeerState` per event; `maybeSavePeerState` (the 2s `bootstrapLoop` tick) coalesces the marked changes into one debounced flush after `peerStateDebounceSeconds`, and `flushPeerState` clears the flag under `peerMu.Lock` at snapshot time (a mutation landing during the disk write re-marks it). See the `flushPeerState` section below.
- `reachableGroups` — populated exactly once by `computeReachableGroups` during `New` and treated as immutable for the runtime lifetime of the `Service`. Concurrent reads of the unmutated map are safe without a lock, so no mutex is assigned. If a future change makes it runtime-mutable, it must gain a mutex (either by moving into `ipStateMu` with every reader taking the lock, or its own dedicated synchronisation) in the same commit that adds the writer.
- The TEST-SEAM family — `sendAdmissionBarrier`, `peerTeardownBarrier`, `cmSessionRegisterBarrier`, `faultDuringRunStartup`, `heartbeatIntervalOverride` — is outside the scheme as a class. Every one of them is `nil` (or zero) in production, is installed by the test that owns the fixture BEFORE the first goroutine that could read it and is never changed afterwards, so it is written by one goroutine with no reader and read afterwards by many with no writer — the same discipline as `listener`. They guard no `Service` state and their call sites are a load and a branch, so they take part in no cross-domain transaction. Three of them additionally carry a POSITION requirement, stated at the field and repeated where it matters: `sendAdmissionBarrier` and `peerTeardownBarrier` must be fired with no domain mutex and no leaf mutex held, because the two goroutines they interleave each take `peerMu` immediately afterwards; `cmSessionRegisterBarrier` (the CM session goroutine, after setup succeeded and before `registerCMSession`) likewise, because the eviction it lets in takes `peerMu` in `onCMSessionTeardown`. A seam that ever becomes runtime-installable must move under a mutex or an `atomic.Pointer` in the same commit. The `ConnectionManager` has one seam of the same family, `ConnectionManagerConfig.RetainOnlyEnqueued` (`nil` in production; `RetainOnly` calls it on the caller's goroutine once its request is in the slot-event queue). It lives in the configuration, so it is fixed when the manager is built and never changes, and tests that hold the event loop wire their observer into the configuration rather than installing it later.
- `startedAt` — wall-clock timestamp captured exactly once by `NewService` and read by the PIP-0001 `getNodeStatus` RPC handler. Immutable after construction, so it is read without any lock. If a future change ever resets the field at runtime (e.g. soft-restart semantics), it must move under one of the existing domain mutexes — likely `statusMu` — in the same commit.
- `connectOnly` (`atomic.Pointer[domain.PeerAddress]`, the single-peer egress pin set by the `connectOnly` command / `CORSA_CONNECT_ONLY`, `connect_only.go`) — deliberately outside the seven-domain split: it is a single pointer with its own atomic synchronisation. Read lock-free on the `PeerProvider.Candidates()` dial hot path through `connectOnlyTarget` (wired as `ConnectOnlyFn`), matching the "hot read = atomic snapshot, never an RLock" rule the routing/peer-health snapshots follow. Writers (`enableConnectOnly`, `disableConnectOnly`, the fail-closed startup sentinel) replace the whole pointer in one `Store`, so readers always observe a consistent value and the field introduces no edge in the canonical lock order. `enableConnectOnly` validates the target first (`validateAddPeerTarget`, no lock, no state written) and stores the pin only for a target that will be admitted, so a failing command never makes its target live and has nothing to restore; only AFTER the store does it call `admitAddPeerTarget` (takes `peerMu`) and `ConnectionManager.RetainOnly`, never while holding a domain mutex. `RetainOnly(ctx, …)` does not touch the slot table itself: it enqueues a `retainOnlyRequest` and waits until the CM event loop — the only writer of the slot table — has applied the pin rule (evicted the other slots, published their removal, closed their sessions and run their `OnSessionTeardown` callbacks), or until `ctx` or the loop's context ends; `false` means "not confirmed", including when the loop is not running. The rule is level-triggered and is applied against the LIVE pin, which the loop reads through `ConnectionManagerConfig.ConnectOnlyFn` (the same lock-free `connectOnlyTarget`): while a pin is live, the slot table holds only the live pin. Every write of a non-nil pin requests it — `enableConnectOnly` and the fail-closed startup sentinel — every `fill` re-applies it before it shrinks to the slot limit (so a limit drop cannot evict the pin's still-dialling slot), a retention that leaves the live pin without a slot fills at once, and `handleManualPeer` does not dial anyone but the live pin (the `add_peer` reply says so, `CodeAddPeerNotDialledConnectOnly`). Because it waits on the loop, a caller of `RetainOnly` must hold NO domain mutex, NOT `PeerProvider.mu` and NOT `cm.mu`, and must never call it from the event loop (a CM callback): the loop takes all of those while handling the events queued ahead of the request, so waiting under any of them is a deadlock. Both callers qualify — `connectOnlyFrame` on the RPC / console goroutine (with the request's context) and `applyStartupConnectOnly` on the `Run` goroutine (with `Run`'s context), neither holding a lock across `enableConnectOnly`.
- `connectOnlyResolver` (`*net.Resolver`, `connect_only.go`) — the resolver for a connect_only hostname target. Set to `net.DefaultResolver` in `NewService`; a test may replace it after `NewService` and before the Service is first used (the `networkOverride` discipline), and nothing writes it afterwards, so it is immutable once the Service runs and takes part in no domain; `resolveConnectOnlyHost` reads it with no lock and resolves outside every domain mutex.
- `transportTotals` (`netcore.TransportTotals`, the node-wide transport byte counters behind `fetch_traffic_totals.transport`, `transport_traffic.go`) — deliberately outside the seven-domain split. It is held BY VALUE and never replaced; the two counters inside are `atomic.Uint64`, advanced only by `netcore.MeteredConn.Read` / `Write` on the I/O goroutines of every peer socket and loaded by `TransportTrafficStats` without any lock. Putting a domain mutex on that path would serialise all socket I/O of the node for a statistic, and the counters take part in no cross-domain transaction: no decision reads them together with domain state. The zero value is live, so struct-literal `Service` fixtures count correctly without a constructor step. Its period starts at `startedAt` and it is never persisted. If it ever becomes resettable at runtime, it must move behind an `atomic.Pointer` (a new period = a new value with a new start) in the same commit — resetting the atomics in place would let a reader pair the old start with the new counts.
- `datagramMetrics` (the datagram-plane counter set, `internal/core/datagram.Metrics`, wired by `NewService` and read by the ingress in `datagram_integration.go`) — deliberately outside the seven-domain split. The pointer is assigned once by the constructor and never replaced, and the counters behind it are `atomic.Uint64`, so the type carries its own synchronisation. Taking a domain mutex to bump a receive-path counter would put the whole datagram plane behind `peerMu` for no benefit, and the metric takes part in no cross-domain transaction. Every method is nil-safe, so struct-literal `Service` fixtures in tests observe a no-op counter instead of panicking. If the field ever becomes runtime-replaceable (a metrics-reset RPC, say), it must move to `atomic.Pointer` or under `statusMu` in the same commit.
- `datagramPlane` (`atomic.Pointer[datagramLayer]` — the assembled datagram transport plane: the strict conveyor of the spec §4.1, the route scheduler of §4.4, the §5 budgets and queues; `datagram_layer.go`, read through the `datagramLayer()` accessor) — deliberately outside the seven-domain split, on the same terms as `datagramMetrics`. `nil` is the feature flag (`CORSA_ENABLE_DATAGRAM_V1` off), so every reader is one nil check away from the pre-datagram behaviour. It is an ATOMIC POINTER rather than a plain field because the receive path reads it concurrently with the single store `NewService` performs; **the pointer is written exactly once and the handle it publishes is immutable** — no field of a published `datagramLayer` is ever written, and a reader takes the pointer once and works off that snapshot for the whole of its decision. There is no rebuild path any more: the plane that could be REPLACED at runtime existed to re-read a durable boot generation behind a recovery barrier, and the durable half of the layer — the profile stores, the attempt machine, recovery and the boot generation — is gone. The components behind the handle carry their own synchronisation (the base replay cache's mutex, the reverse table's mutex, the weighted queue's mutex, the copy-on-write `atomic.Pointer` generation of the type registry, the `atomic.Uint64` counters of the admission budget), so no domain mutex is taken to reach it and it adds no edge to the canonical lock order. NONE of them is held ACROSS a call back into `Service`, and the layer no longer calls back into the node at all outside the emitter: the observer seams the fail-closed transitions used (`ProfileWithdrawn` / `ProfileRestored`) went with the profiles. Reads happen on the receive path (`handleDatagramFrame`), on the outbound emitter (`datagramFrameEmitter.EmitTo`), from the four background loops and from the RPC diagnostics; the layer's own send entry point (`Pipeline.SendLocal`) is an **extension point**, not a production path in `node` — until a protocol migrates onto the layer (§8 of the datagram spec) it is reached only from tests, and the field comment must be revisited together with the first adapter that calls it.
  The layer's own adapters DO take `peerMu`, and always as the outermost and only domain mutex they touch: `datagramSendTargetsLocked` is called under `peerMu.RLock` by `datagramPeerMetadata.SendableConnection` and `datagramDirectSession.LookupDirectSession`, by `datagramFrameHeadTargetLocked`, and by `datagramFrameEmitter.EmitTo` through `datagramFrameSendTargetsLocked` — the same ordered list with the frame's own gates applied per connection. Those gates are now exactly two, the ROLE gate (`mesh_datagram_v1`, plus `mesh_datagram_transit_v1` unless the peer is the destination) and the LAST-HOP `dtype` gate; the third one, over the envelope's `req_caps`, went with the field, so nothing a SENDER wrote into the frame decides which of our sockets may carry it. Every one of these helpers RELEASES the lock before doing anything else. That is not a style preference — the emitter then calls `sendTrackedFrameToSession` / `sendTrackedFrameToConn`, which take `peerMu` themselves (the stalled-peer gate through `peerState`, the registry read through `netCoreForID`), so holding the lock across the hand-off would self-deadlock; the hand-off also ends in a queued socket write, which the "no network I/O under a domain mutex" rule forbids under a lock. Those two helpers address the CONNECTION the selection chose — the `peerSession` object on the outbound tier, the `domain.ConnID` on the accepted one — and never the peer's address: `peerMu` is released between the selection and the hand-off, so the peer may reconnect in that window and `s.sessions[address]` (or the tracked inbound connection under a given `remoteAddr`) then names a DIFFERENT socket, with a different handshake and a different `ConnID`. A session or connection that died in that window refuses through its own fence, which is the answer the candidate walk wants. The route resolver takes no domain mutex at all: `FreshRoutes` goes to `routing.Table.Lookup` (the table's own `RWMutex`) and `CachedRoutes` to the `atomic.Pointer` snapshot, which is the hot-read pattern this document already prescribes.
  **There is no recovery barrier and no startup disk I/O left on this path.** `startDatagramLayer` starts the schedules and nothing else: the layer's whole memory is an in-memory anti-replay cache that starts empty and is correct from the first frame, so there is no durable pass to run before the listener opens, no `datagram_boot.json` to read or write, no fail-closed withdrawal to publish and no capability this node can lose at runtime. `localDatagramAdvertise` — read by every hello/welcome builder — answers from the feature flag and the node type through `datagramPlaneReady`, which is a nil check on the handle and takes no mutex at all. `localAdvertisedCapabilities`, the construction-time snapshot handed to the pipeline's transit gate, reads `datagramPlaneCapability` for the same reason it always did: it is taken before the handle is stored, and a readiness-gated snapshot would be frozen shut for the life of the process.
  The four background loops started by `startDatagramSchedules` (the outbound class-queue pump, the queue expiry sweep, the reverse-state sweep and the maintenance loop that sweeps the base replay cache) stop on the `Run` context and hold no domain mutex: the only one that reaches the node at all is the pump, and it does so through the emitter, which follows the discipline above. `forgetDatagramPeer` — the §5 admission-bucket release on the last session of a peer — is called from `onPeerSessionClosedWithCause` AFTER `peerMu` has been released, alongside the other close-path side effects.

- `runLoopsWg` (`sync.WaitGroup`, `service.go`) — THE lifecycle group: every long-lived goroutine `Run` starts is on it, and it is the only such group. The CM event loop, `bootstrapLoop`, `hotReadsRefreshLoop`, the announce loop, the routing TTL ticker, the probe sender, the listener closer, the gossip dispatch pool (thirty-six workers plus its shutdown supervisor), the datagram plane's four schedules (`startDatagramSchedules`) AND the three goroutines of every outbound CM session — the handshake guard and the session reader started by `openPeerSessionForCM`, and the serve goroutine started by `onCMSessionEstablished` — all of them through the single `goRunLoop` wrapper. The session goroutines are the shorter-lived members: they end on the same lifecycle context (`servePeerSession`, the handshake guard) or on the socket the CM closes in its own shutdown (the reader, which watches no context and stops only when its read fails), and their `Add` never raises the counter from zero under `stopRunLifecycle`'s `Wait`, for two different reasons: the serve goroutine is started ON the CM event loop, itself a member; the guard and the reader are started on a CM dial worker, which is NOT a member — they rely on the CM event loop waiting for `cm.dialWg` before it returns, so a member is alive for as long as any dial worker is. The reader is on the group because it does work of its own off the serve loop — `file_command` frames go straight to the file router, datagrams to the datagram plane — and must not be left inside one when `Run` stops the file-transfer subsystem. The join depends on every outbound session socket being closed by then: the CM closes the sessions of its slots and of the dial results it discards (`tearDownSession`, `drainChannels`), the dial worker closes a result the loop no longer accepts, and `openPeerSessionForCM` closes its own on every error path. The serve goroutine and the reader used to be bare `go` statements: `Run` returned while they were still serving frames, and those frames scheduled receipts and key-sync passes on `goBackground` after the node was reported stopped (pinned by `TestRunWaitsForAnOutboundSessionGoroutineInsideAFrame`; the reader and the handshake guard by `TestNoLongLivedGoroutineEscapesTheLifecycleGroup`, which no longer exempts `openPeerSessionForCM`). Outside the seven-domain split because a `WaitGroup` synchronises itself and guards no `Service` state. It exists because cancellation only ASKS: a loop that is merely cancelled can still be inside a network send, a TTL drain, a `peers.json` write or a call into the datagram layer when `Run` returns, and `Run` returning is what the runtime treats as permission to close those underneath it. `Run` cannot get that guarantee by waiting on `backgroundWg`: that group tracks fire-and-forget jobs across the whole Service, some of them started during the very teardown `Run` is performing, so joining it from inside `Run` would trade this bug for a shutdown deadlock. `WaitBackground` waits on BOTH, so callers and tests still know exactly one join point. The wait is deliberately NOT bounded by a timeout: every loop in the group is bounded on cancellation by its own contract (see the audits on `startDatagramSchedules` and on the gossip pool), so a wait that does not end is a component ignoring the context it was handed — and a timeout would convert that into the use-after-teardown the join exists to prevent. A wait group rather than done-channels for one reason: it is correct for a loop that was NEVER STARTED, so the teardown can be armed before any of them exists, while a channel nobody will ever close would make it wait for ever.

  **There is ONE group and ONE wait, and there used to be two.** The datagram plane kept `datagramWg` with a context and teardown of its own (`armDatagramPlaneShutdown`, `goDatagramWorker`), because the plane owned DURABLE STORES and `Run` had to join those workers before the store owner was stopped. The stores are gone — the four schedules are two in-memory sweeps, a queue pump and a replay-cache expiry pass — and every guarantee that second group carried is a property of `stopRunLifecycle` instead: (i) *joined before `Run` returns* — the teardown runs on every exit, including a panic unwind, because it is a `defer`; (ii) *joined before every subsystem defer* — `stopFileTransfer`, `relayStates.stop`, `captureManager.Close`, `close(s.done)` — which is the POSITION of the single `defer s.stopRunLifecycle(runCancel)`: it is registered after those defers and before the first `go`, so LIFO puts the join ahead of them; (iii) *cancel before join* — the first statement of `stopRunLifecycle`; joining without asking first deadlocks the moment any pass is in flight. The one thing the second group added on top — joining the plane's workers BEFORE the node's loops — carried nothing: both sets are asked to stop by the SAME cancel and no teardown step runs between the two waits, so `wait(A); wait(B)` releases the caller at exactly the same instant as `wait(A ∪ B)`. What it did cost is a second place the ordering had to be right.

  **The inbound-connection drain is NOT in that list, and it runs BEFORE the join.** `closeAllInboundConns` + `connWg.Wait` sit in a defer registered BELOW `defer s.stopRunLifecycle(runCancel)`, so LIFO runs them first, with every lifecycle loop still live. That is the correct order rather than an accident, and the reasons are three: (a) the drain STOPS NO SUBSYSTEM a loop calls into — the hazard the join exists for. It closes sockets and clears per-connection rows (the conn registry, the subscribers, the conn auth, the inbound health refs); a loop reaches a connection only through the netcore registry, which answers "unknown conn" for a closed `ConnID` instead of handing out a freed handle, and an absent per-connection row is the ordinary state every peer disconnect already produces. (b) The dependency that IS load-bearing runs the other way: the connection handlers are PRODUCERS into what the loops consume — the CM event loop (`EmitSlot`), the gossip lanes, the announce plane — and their teardown path produces its last work as it exits (`trackInboundDisconnect` → `markPeerDisconnected`, `removeSubscriberConnID`, the session-closed routing bookkeeping), so joining the handlers while those consumers are still alive is the order in which that work can still be absorbed. (c) The drain must in any case precede `cancelAllPendingWithdrawalsForShutdown`, whose defer sits between the two — so the cancel runs AFTER the drain and BEFORE the join. After the drain, because the inbound handlers report session closes until they exit and every withdrawal they arm is still pending when the cancel runs. Before the join, because the join lasts as long as the outbound session sockets take to close, and a timer still pending then would fire inside it and tear a direct route out while the loops consuming the withdrawal are being stopped. The closes reported during or after the join — by the outbound session goroutines unwinding in it, or by a caller that outlives `Run` — come after the cancel, and the flag it sets, `withdrawalsShutDown` (under `peerMu`), refuses them on both paths instead of arming a timer nobody would cancel: `maybeScheduleDeferredWithdrawal` checks it under the `peerMu` it arms under, and `executeDeferredWithdrawal` checks it in its first `peerMu` section, next to the relay-session re-check and under the same lock as the route mutation — which covers the inline path (grace disabled) and a timer that claimed its entry before the cancel, with no window between check and mutation. Pinned by `TestAWithdrawalArmedBeforeShutdownDoesNotFireInsideTheJoin`, `TestAWithdrawalAskedForAfterRunReturnedIsNotArmed` and `TestASynchronousWithdrawalOnAStoppedNodeIsDropped`. The order is pinned by `TestTheInboundDrainRunsBeforeTheLifecycleJoin`, which observes the inbound socket being closed while a lifecycle loop is still parked; swapping the two defers turns it red.

  Ordering inside `Run` is load-bearing and produced four defects in four rounds, so it is not a property of where a `defer` happens to sit: `Run` has ONE ordered teardown, `stopRunLifecycle` (cancel → join), armed at ONE point. A bare `runCancel` remains at the top of `Run` as the backstop for a panic raised before that point. A cancel registered ONLY at the top ran after the waits and made an error exit — a listen that fails because the address is already bound — block forever in its own teardown; and joining the loops only on the two graceful returns let an error exit return while `bootstrapLoop` was still writing `peers.json` on its way out, i.e. while the caller was already entitled to delete the data directory.

  The gossip pool is what shows why the group has to be defined by the PROPERTY and not by the call site: it is started by a helper (`startGossipDispatch`) rather than by `Run` directly, so a guard that looked for `go` statements inside `Run` could not see it, and it sat on `backgroundWg` — which `Run` deliberately does not wait on — while its jobs dial, handshake and write to sockets. Joining it is bounded because a worker refuses to START a job once the context is done, so the wait covers only the jobs already running: each is bounded by the dial timeout (2 s), the handshake timeout (2 s / 1.5 s for sync) and netcore's per-write deadline. The rule is ENFORCED rather than documented: `TestNoLongLivedGoroutineEscapesTheLifecycleGroup` parses every non-test file of the package and fails on any goroutine that RECEIVES from a context's `Done` channel — the observable property of being long-lived — while being started with a bare `go` or on `backgroundWg`. Its blind spots are stated in the test: a long-lived goroutine that consults no context at all, goroutines in other packages, dynamic dispatch, and the fact that it proves MEMBERSHIP rather than that the group is waited on (the blocking lifecycle tests of `datagram_lifecycle_test.go` prove that half). The guard's coverage is stated in the test rather than claimed complete — twice a list that read exhaustive omitted the shape that broke next — but it now classifies EVERY `go` statement in the package and fails on any form it cannot resolve, so nothing is skipped without being named.

  Goroutines that belong to a SHORTER lifetime are joined THERE, one goroutine one owner: the per-connection handler by `connWg`; the inbound heartbeat by its own connection's handler, which waits on a per-connection `WaitGroup` before returning (closing its stop channel only ASKS — the loop can be inside a ping send, bounded by netcore's write deadline, and it touches the Network and `peerMu` afterwards); the ConnectionManager's dials by `cm.dialWg`; the five hot-read snapshot tickers by the local `WaitGroup` `hotReadsRefreshLoop` waits on, that loop itself being on `runLoopsWg`. The outbound session goroutines are NOT among them: the CM only closes a session's socket in its shutdown and never waits for the goroutines serving it, so those are on `runLoopsWg` themselves. **Known exception:** the LEGACY session path — `ensurePeerSessions` → `runPeerSession` → `openPeerSession`, inert while the ConnectionManager is wired — starts its per-dial goroutine, its context watcher and its session reader with bare `go` statements that `Run` does NOT join. Its callers are not on `runLoopsWg`, so moving them there could raise the counter from zero under `stopRunLifecycle`'s `Wait`; the path is listed as an exception in `TestNoLongLivedGoroutineEscapesTheLifecycleGroup` rather than treated as joined. Their `goBackground` jobs are refused once `Run` has returned. **Residual, not joined either:** a withdrawal timer callback already past the shutdown check inside `executeDeferredWithdrawal` when the cancel runs finishes it outside the join; `probeRegistry` timers (`routing_probe_loop.go`) still fire after `Run` and call `routingTable.MarkProbeFailure` — in-memory state only.

- `peerSession.declarations` (the raw handshake self-description mirrored onto an outbound session — the validated raw capability names of the datagram spec §2.2 and the declared `dtypes` set of §6.1) is not a `Service` field, but it follows `peerSession.capabilities` and `peerSession.peerIdentity` exactly: written once by `applyWelcomeMetadata` and read under `peerMu` (through `sessionDeclarations`, `sessionHasCapability`, `sessionPeerIdentity`). **The write is under `peerMu` too, and that is not belt-and-braces.** The session is NOT private to the dialling goroutine at that point: `readPeerSession` was started before the handshake began — it is the goroutine that delivered the `welcome` — and it reads these same fields on the capability gates of its own receive path (`datagram`, `file_command`). A peer that pipelines a frame behind its own `welcome` therefore puts a reader on the field at the instant the handshake goroutine assigns it, which the race detector confirms. `applyWelcomeMetadata` is consequently called with `peerMu` held at both outbound call sites (`openPeerSession`, `openPeerSessionForCM`); the datagram advertise is resolved BEFORE the lock, because it consults the datagram layer. A session that has not reached the write answers the empty capability set and the zero identity — but that is NOT what makes the window safe, and treating it as such was a defect: the set is published on the `welcome`, while the handshake ends a full round trip later, on `auth_ok`. The authoritative copy lives on `netcore.NetCore`, which has its own internal `RWMutex`; the mirror exists only because the outbound dispatcher is addressed by `PeerAddress` and never sees a `ConnID`.
- `peerSession.authOK` (the completed-handshake state of an outbound session: `auth_ok` arrived) joins the three fields above and for the same reason, but it is what actually closes their window. A capability is NEGOTIATED on the `welcome` and IN FORCE only once this flag is set, so `sessionHasCapability` — the one helper every capability gate of the dialled receive path goes through — refuses while it is false. Written exactly once, by `markSessionHandshakeComplete` under `peerMu`; read under `peerMu.RLock`. **The write is under the lock because the reader is another goroutine:** `readPeerSession` has been dispatching since before the `welcome`, so a peer that pipelines a `datagram` behind its own `welcome` puts a reader on this flag at the instant the handshake goroutine writes it. Two node-side writes are ordered against it rather than gated by it: the backlog replay and the connect-time full sync are both RETURNED by `handleAuthSession` and run by its caller only after `auth_ok` is enqueued — a full sync that overtakes `auth_ok` is one the dialler's own gate refuses. The transition is one-way: a session that needs a different set is a new session on a new socket.
- `peerSession.admission` (`peerSessionAdmission`, `peer_session_admission.go` — the RESPONSE-plane per-neighbour admission of one outbound session: the raw byte and frame budget charged around every read, the unsolicited-`push_message` sub-budget, the outstanding-reply record and the violation ledger) — guarded by its OWN embedded `sync.Mutex`, deliberately outside the seven-domain split, as a **leaf**. It is taken by exactly two goroutines — the session's reader (`readPeerSession`, once or twice per frame) and the request helper on the serve loop (`peerSessionRequest`, which registers the reply it is waiting for) — is never held across I/O, a callback or a domain mutex, and guards nothing but four floats and a string, so it adds no edge to the canonical lock order. It is NOT under `peerMu`, unlike every other `peerSession` field that outlives the handshake, and the reason is the hot path: this is the receive path of every peer session on the node, and routing a per-frame arithmetic update through the node's busiest writer lock would serialise the whole network against unrelated peer-state writers. The state is held BY VALUE and its zero value is a live controller with full buckets, so no construction site can forget to build one and a missing controller can never silently mean "this neighbour has no budget".
- `peerSession.closedBy` (`atomic.Pointer[peerSessionCloser]`, `service.go` — who closed the session FIRST: its owner, or a ConnectionManager local eviction or shutdown; nil while open) — deliberately outside the seven-domain split: it is written exactly once, inside the session's `closeOnce` and before the transport is torn down, and every later read only compares the value. The CM writes it on its event loop in `tearDownSession`, after `cm.mu` is released and before `OnSessionTeardown` runs; the session goroutine writes it whenever it closes the session itself. Neither writer holds a domain mutex, and the atomic adds no edge. Readers either read it after their own `Close` returned (`sync.Once` orders them after the winning close) or under `peerMu` at registration (`registerCMSession`, see the session-map section for why that is race-free against `onCMSessionTeardown`).
- `contactVerifyBudgets` (`contactVerifyRegistry`, `contact_verify_budget.go` — the node-scoped, per-remote WORK budget of the `contacts` reply: one refilling token bucket per remote endpoint, one token per `identity.VerifyBoxKeyBinding`) — guarded by its OWN embedded `sync.Mutex`, deliberately outside the seven-domain split, as a **leaf**. It is taken by the two contact importers (`syncContactsViaSession` on a session goroutine, `syncPeer` on a recovery-pass goroutine), is never held across I/O, a callback or a domain mutex, and guards nothing but arithmetic and a bounded map, so it adds no edge to the canonical lock order. Two consequences of "no callback and no I/O under it" are structural rather than conventional: the injectable clock is an `atomic.Pointer`, resolved BEFORE the lock is taken (the datagram plane's `PeerAdmission` has the same shape), and the saturated-registry warn is decided under the lock but LOGGED by the caller after the unlock — `charge` returns the facts instead of emitting them, because a log sink under this lock would stall contact verification for every remote on the node. It is NOT a per-session field, unlike the budget it replaces: a bucket that lived on `peerSession.admission` was born full with every reconnect, and the fresh recovery dial has no session at all — both resets were a budget the metered party could re-buy by opening a connection. The state is held BY VALUE on `Service` and its zero value is a live registry (map built on first use, nil clock = wall clock), so no construction site — production or the struct-literal test services — can forget to build one, and a missing registry can never silently mean "this remote has no budget".
- `relayDeliveredTo` (the per-`MessageID` set of peer identities that ack_delete-confirmed they hold the message — Phase 2 gossip-storm suppression, `relay_delivered.go`) — guarded by its OWN dedicated `relayDeliveredMu` leaf mutex, deliberately outside the seven-domain split. The mutex is only ever taken alone (`recordRelayDeliveredTo`, `forgetRelayDelivered`) or snapshotted via `relayDeliveredSnapshot` BEFORE `peerMu` is acquired in `filterGossipTargetsForEnvelope` — it is never held while acquiring a domain mutex, so it introduces no edge in the canonical lock order. `forgetRelayDelivered` is wired next to every `dropRelayRetryEntries` call (cleanup expiry, transit-cap eviction, `deleteBacklogMessageForRecipient`) so the bounded index is pruned whenever an envelope leaves `topics`; a hard cap (`maxRelayDeliveredMessages`) backstops any missed forget path.

### Lock ordering

All cross-domain sections must acquire locks in this exact order:

```
peerMu → deliveryMu → knowledgeMu → gossipMu → ipStateMu → fileMu → statusMu
```

This order is total: no code path may acquire a later mutex while holding none of the earlier ones, then later try to acquire an earlier one. A section that touches `peerMu` and `statusMu` acquires `peerMu` first, does its read/mutation, then `statusMu`. Never the reverse.

Violating the order is a deadlock bug. The order is enforced by convention today; a vet-style linter may be added later.

#### Why this order

The order places the most-contended domain first so that less-contended domains never hold their lock while waiting on a contended one. Measured hotness (write frequency) decreases roughly along the chain:

1. **peerMu** — every connect / disconnect / markPeerConnected / markPeerDisconnected mutates it; reconnect storms hit it hardest.
2. **deliveryMu** — every inbound / outbound message, every relay retry.
3. **knowledgeMu** — writes only during handshake and when a new identity binding is learned. Also owns the node's own signed identity record (`selfRecord` / `selfRecordBody`): the record is built and PERSISTED (trust-store file I/O) strictly outside the mutex, and only the field swap happens under `knowledgeMu.Lock` — the reserve → persist → publish order of `self_record.go`.
4. **gossipMu** — writes on topic publish / subscribe; reads on every `fetch_messages`.
5. **ipStateMu** — writes on ban events and observed-IP convergence; reads on every accept.
6. **fileMu** — writes only during active transfers; cold outside that.
7. **statusMu** — writes only when aggregate status actually changes.

### Cross-domain transaction patterns

Most Service methods touch a single domain. The sections below are **representative** patterns, not an exhaustive list: every cross-domain call site must follow the canonical order from §"Lock ordering" regardless of whether it appears here. The examples exist to teach the shape; absence from this list is not permission to reverse the order.

#### `markPeerConnected` / `markPeerDisconnected`
Both hold `peerMu.Lock` for their whole body (health, identity and version maps) and nest the other domains inside it, one section at a time:
- `updatePeerStateLocked` — `deliveryMu.RLock` for the rest of its body, with `statusMu.Lock` nested inside around the aggregate-status publish (see `updatePeerStateLocked` below): `peerMu → deliveryMu → statusMu`.
- `ipStateMu.Lock` — `markPeerConnected` clears the IP from `bannedIPSet` and, with `statusMu.Lock` nested, drops the peer from `versionPolicy.incompatibleReporters`: `peerMu → ipStateMu → statusMu`. `markPeerDisconnected` deletes the peer's `observedAddrs` entry: `peerMu → ipStateMu`.
- `statusMu.Lock` — `recomputeVersionPolicyLocked`: `peerMu → statusMu`.

The hot-read snapshot refresh and the `ebus` publish run after `peerMu` is released.

#### `onCMSessionEstablished`
The callback has two halves with different rules: the first runs synchronously ON the `ConnectionManager` event loop, the second in the session goroutine it launches.

On the event loop. CM calls it after the slot has entered Initializing and after `cm.mu` is released (`ConnectionManagerConfig.OnSessionEstablished`). The slot stays as handed over — in the table, Initializing, at `info.SlotGeneration`, its session open — until the callback returns: every slot mutation (eviction by `shrinkToLimit`, `add_peer`, `RetainOnly` and shutdown included) and every `OnSessionTeardown` runs on the same event loop, so none can interleave with the callback. No two domain mutexes are held at once here, so this half adds no edge between domains; each step takes one domain for its own short section and releases it:
- `ipStateMu` — the dialled IP is cleared from `bannedIPSet`; later `recordObservedAddress` writes `observedAddrs`.
- `peerMu` — `learnIdentityFromWelcome` (`promotePeerAddress`, `rememberPeerType`, `addPeerID` / `addPeerVersion` / `addPeerBuild`), `resolveHealthAddress` (RLock), then `addPeerID` / `addPeerVersion` / `addPeerBuild` under the health key.
- `knowledgeMu` — `addKnownIdentity`, `learnWireIdentityKeys` (`addKnownPubKey` / `addKnownBoxKey` / `addKnownBoxSig`), and `knownBoxKey` (RLock), reached through `notifyIdentityKeysImported` → `identityResolver.usableNow`.
- Outside the domain split: `PeerProvider.mu` (`Add` / `MarkFresh` from `promotePeerAddress`, after `peerMu` is released), the `identityResolver`'s own mutex, `ebus.PublishIdentityAdded` (after `knowledgeMu` is released) and `ebus.PublishIdentityResolutionChanged` (`identityResolver.emit`, after the resolver's mutex is released).

`deliveryMu`, `gossipMu`, `fileMu` and `statusMu` are not taken on the event loop. The callback must not run under `cm.mu`: `PeerProvider.Candidates` / `KnownPeers` hold `pp.mu.RLock` while calling `QueuedFn` → `ConnectionManager.QueuedIPs` (`cm.mu.RLock`), an edge `pp.mu → cm.mu`, and this half takes `pp.mu.Lock` in `PeerProvider.Add`; under `cm.mu` that would close a cycle, on top of adding edges from `cm.mu` into the Service domain mutexes.

In the session goroutine (off the event loop, so blocking I/O is allowed, never under a domain mutex). The list names the locks this function takes itself and the order of the calls that shape the domain picture; every callee follows its own section or doc comment:
- setup aborted by a local eviction — the CM closed the session (shrink, `add_peer` eviction, `RetainOnly` or the pin rule, shutdown) while `initPeerSession` ran, or before the session could be registered: one `peerMu.Lock` section that only deletes the session's own `dialOrigin` entry (left alone when another session is registered under the address), then the control-frame bucket is dropped. No setup failure is recorded, no route quarantine is armed, the setup-failure counter is not cleared, the session is not published and nothing is reported to the CM (the slot is already gone). Logged as `cm_session_setup_aborted_local_eviction`;
- setup failure — the peer answers for it: one `peerMu.Lock` section (`dialOrigin`, `recordSetupFailureLocked`, `armRouteQuarantineLocked`), then `ActiveSessionLost`;
- setup success — registration of the session under `peerMu` OUTER → `deliveryMu` INNER together with `clearSetupFailuresLocked`, guarded by the close-reason check (see the session-map section below), then the `SessionInitReady` emission, `refuseLegacyIdentity` (the pin store's leaf mutex, then `peerMu.RLock`, never together), `markPeerConnected` and `flushPendingPeerFrames` with the orders their own sections give, `onPeerSessionEstablished` (one `peerMu` section for the session counters with the record-protection leaf mutex inside; routing, withdrawal-grace and presence work run after `peerMu` is released), the full table sync and `servePeerSession`;
- after `servePeerSession` returns — the owned cleanup, again `peerMu` OUTER → `deliveryMu` INNER, then the per-session cleanup helpers and routing deregistration (`onPeerSessionClosed*`), which only this goroutine performs.

Who closed the session decides every charge. `peerSession.closedBy` records the FIRST closer inside the session's `closeOnce`, before the transport is torn down: the session's owner (`Close`) or a CM local eviction. (When the CM deactivates a slot after a loss the goroutine reported, the goroutine has already closed the session, so the CM's close changes nothing; were it ever first, it is recorded as the owner's, which never excuses the peer.) The goroutine reads it after its own `Close` returned — the failed-setup path, `retirePeerSession` in the serve loop and the post-serve cleanup all close first, and `sync.Once` orders them after a CM close that won — or under `peerMu` at registration. A session closed by a local eviction is never charged: no setup failure, no route quarantine, `markPeerDisconnectedByLocalDecision` instead of a failed `markPeerDisconnected`, and routing deregistration attributed as `sessionCloseLocalEviction`. First closer is not first cause: if the peer's failure is already waiting on `errCh` when an eviction wins `closeOnce`, that failure goes uncharged — accepted, since the eviction was closing the session anyway and the error this guards against is the opposite one.

#### `handleAuthSession`
Touches `peerMu` (bind identity to session) and `knowledgeMu` (cache pubkey). Order: `peerMu` → `knowledgeMu`.

#### `accumulateInboundTraffic`
Touches `peerMu` (update health byte counters) only. No cross-domain hold.

#### `handleConnectionNotice{code=peer-banned}`
Touches `ipStateMu` (record IP ban) and optionally `peerMu` (evict sessions from that IP). Order: `peerMu` → `ipStateMu`.

#### File-transfer lifecycle and the `file_command` receive path
`fileMu` rarely meets another domain. When it does — a transfer failed because the peer left — the order is `peerMu` → `fileMu`.

The peer-session receive path adds a second, HOTTER reader of the same domain, and it takes NEITHER lock nested inside the other: `sessionFileCommandIsAdmissible` (`peer_session_admission.go`) asks `sessionHasCapability` under `peerMu.RLock`, releases it, and only then reads `fileRouter` under `fileMu.RLock` (`fileCommandHasConsumer`). Two sequential single-domain reads add no edge to the canonical order; nesting them would, and would put the busiest lock on the node around a domain the dispatch below reads on its own anyway. The same two facts are read a second time one gate later, by the dispatch itself — deliberately, because a verdict carried forward from the admission gate would be a fact that can go stale between the two.

#### `flushPeerState` (peer state persistence snapshot)
Touches peer-domain (`persistedMeta`, `health`, `peerTypes`, `peerVersions`, `peerBuilds`, …) and `ipStateMu` (snapshots `bannedIPSet` and `remoteBannedIPs` for disk). Order: `peerMu.Lock` outer, `ipStateMu.RLock` nested inside. Both locks are released before disk I/O; afterwards `peerMu.Lock` is re-acquired briefly to update `lastPeerSave`. The two ipStateMu loops (local and remote bans) live inside the same RLock window so the persisted file represents a consistent snapshot of both tables.

Invocation discipline (coalescing): `flushPeerState` is expensive — a full `buildPeerEntriesLocked` snapshot plus `StaticSnapshotAll`, `trimPeerEntries`, a JSON marshal, and a disk write — so it MUST NOT be called synchronously per state-change event. Every path that mutates persisted peer state outside the periodic catch-all — add_peer, remote-ban record (`handlePeerBannedNotice`) and remote-ban clear (`clearRemoteBansOnAuth`) — instead calls `markPeerStateDirty` (sets `peerStateDirty` under `peerMu`); the 2s `bootstrapLoop` tick runs `maybeSavePeerState`, which flushes when EITHER the dirty flag is set and `peerStateDebounceSeconds` has elapsed since the last save (debounced burst collapse) OR the periodic `peerStateSaveMinutes` catch-all interval has elapsed (captures health/score/version-policy drift that mutates without an explicit mark). Any NEW call site that changes a persisted peer field must use `markPeerStateDirty`, never a synchronous `flushPeerState`. `flushPeerState` clears `peerStateDirty` under the FIRST `peerMu.Lock` (at snapshot time, not after the write) so a mutation landing during the disk write re-marks the state; a failed `savePeerState` re-marks dirty and leaves `lastPeerSave` untouched so the next tick retries on the debounce path. Only shutdown (`bootstrapLoop` ctx-done) calls `flushPeerState` directly and unconditionally. Before this discipline, startup bootstrap priming called `flushPeerState` once per primed peer, making persistence O(peers²) in snapshot+marshal+disk cost.

Cross-lock constraint: `flushPeerState` MUST NOT call any `peerProvider.*` method from under `peerMu`. `PeerProvider.Candidates()` already runs under `pp.mu.RLock` and reaches back into Service via `RemoteBannedFn` / `BannedIPsFn` / `SetupFailureBannedFn` (edge `pp.mu → peerMu/ipStateMu`). Taking the reverse edge (`peerMu → pp.mu`) from inside `buildPeerEntriesLocked` would close the cycle and deadlock under Go's writer-preferring RWMutex in the three-goroutine interleaving: candidate refresher holds `pp.mu.RLock` and waits on `peerMu.RLock`; a concurrent `Promote`/`Add` queues on `pp.mu.Lock` blocking new pp.mu readers; `flushPeerState` holds `peerMu.Lock` and tries to enter `pp.mu.RLock` as a new reader. Snapshot `peerProvider.StaticSnapshotAll()` BEFORE taking `peerMu.Lock` and feed the snapshot into `buildPeerEntriesLocked`.

The `SetupFailureBannedFn` callback (gate 6c.3 in `PeerProvider.Candidates`) joins the existing `pp.mu → peerMu` edge family — same shape as `RemoteBannedFn`. `Service.IsSetupFailureBanned` takes `peerMu.RLock` to read `setupFailures` and returns immediately, so the lock window is short and contains no further cross-domain calls. No new cycle is introduced; the cross-lock constraint above (snapshot before taking `peerMu`) continues to cover the reverse direction.

#### `recordOutboundAuthSuccess` (post-handshake ban recovery)
Touches peer-domain (`persistedMeta` via `clearRemoteBanLocked`) and `ipStateMu` (`remoteBannedIPs` AND the volatile `remoteIPBanOffenders` set, both via `clearRemoteIPBanLocked`). Order: `peerMu.Lock` outer → `ipStateMu.Lock` nested. The `ipStateMu` acquisition is an explicit `Lock/Unlock` around `clearRemoteIPBanLocked` because that helper requires the caller to already hold the ipStateMu write lock. Note `clearRemoteIPBanLocked` drops the pre-escalation offender set for the IP as a side effect, but returns `true` only when a PERSISTED `remoteBannedIPs` entry was removed — clearing the volatile set alone does not trigger a `flushPeerState`.

#### `storeIncomingMessage` (knowledge write + gossip dedup)
Touches `knowledgeMu` (write `known` for sender / recipient, read `pubKeys` for the non-DM spoof gate) and `gossipMu` (`seen` dedup check, `topics` append). Order: `knowledgeMu.Lock` FIRST, release, THEN `gossipMu.Lock` — canonical `knowledgeMu → gossipMu`. The two sections are SEQUENTIAL, not nested; splitting is semantically safe because the `known` writes are idempotent and the dedup decision reads only `seen`, not `known`, so a concurrent writer cannot produce a different outcome across the gap. The gossip section also temporarily releases `gossipMu` around the external `messageStore.StoreMessage` call (SQLite I/O must never happen under a domain mutex); the re-acquired window appends to `topics` and collects duplicate-diagnostic IDs before the final release.

The DM branch earlier in `storeIncomingMessage` reads `pubKeys`/`boxKeys`/`boxSigs` for signature verification under `knowledgeMu.RLock` as a standalone snapshot — no cross-domain hold, verification proceeds outside the lock.

Control DMs (`msg.Topic == protocol.TopicControlDM` — see `docs/dm-commands.md`) reuse this exact code path with three storage-side divergences:

1. The chatlog `messageStore.StoreMessage` call inside the gossip section is gated on `msg.Topic != protocol.TopicControlDM`.
2. The `s.topics[msg.Topic]` append is gated on `msg.Topic != protocol.TopicControlDM`. Control envelopes therefore never accumulate in `s.topics`. This avoids a memory leak — `retryableRelayMessages` reads only `s.topics["dm"]`, so any control envelope put into `s.topics["dm-control"]` would be unread by every retry consumer and grow unbounded. Routing/push fan-out remains unaffected because `executeGossipTargets` and `sendTableDirectedRelay` send frames on the wire on the fly without consulting `s.topics` as a backing store.
3. The LocalChange event branch publishes `LocalChangeNewControlMessage` on `ebus.TopicMessageControl` (instead of `LocalChangeNewMessage` on `ebus.TopicMessageNew`) and only does so when `msg.Recipient == s.identity.Address`. The sender side never receives its own outbound control DM as if it were inbound — sender-side state is updated synchronously inside `DMCrypto.SendControlMessage` / `DMRouter.SendMessageDelete`.

The locking discipline is identical to the data-DM path: `knowledgeMu` → `gossipMu` sequentially, with the same brief unlock around store I/O (now skipped entirely for control DMs, so the `gossipMu` section runs uninterrupted for them). No new mutex is taken and no new cross-domain edge is introduced; the only behavioural difference is which external side-effects run after the gossip section closes.

The relay-retry tracker (`trackRelayMessage` in `relay.go`) likewise rejects control DMs at its entry gate — the application-level retry on the sender side (the delete intents in `message_delete_intents`, driven by `DMRouter`) is the canonical retry mechanism for control DMs and the only one with a complete delivery contract: ack-driven termination and durability in the shared state database, so a restart resumes the same schedule.

#### `retryableRelayMessages` / `deleteBacklogMessageForRecipient` (delivery + gossip)
Touches `deliveryMu` (`relayRetry`) and `gossipMu` (`topics["dm"]`). Canonical order `deliveryMu → gossipMu`: `deliveryMu` OUTER, `gossipMu` INNER. In `retryableRelayMessages` the gossip side is a read-only snapshot (`gossipMu.RLock`) scoped tightly around the `topics["dm"]` copy; in `deleteBacklogMessageForRecipient` the gossip side is a write (`gossipMu.Lock`) that spans the entire filter loop because each matched envelope invalidates its `relayRetry` entry in the same iteration — the two mutations must stay atomic together. The snapshot is returned with `deliveryMu` released, so any deletion path (receipt ack, cancel, transit eviction via `dropRelayRetryEntries`) may remove a snapshotted message and its entry before `retryRelayDeliveries` gets to it. `noteRelayAttempt` therefore records the attempt only on an entry that still exists and reports absence; the loop skips the send. Re-creating the entry there produced a permanent orphan: every reaper walks the live backlog, which no longer holds the message, so nothing could ever reach the entry again.

#### `CancelOutgoingDelivery` (withdraw an unsent DM: peer + delivery + gossip + status)
Takes `peerMu.RLock → deliveryMu.Lock → gossipMu.Lock → statusMu.Lock`, canonical order throughout, and releases LIFO. `peerMu` is read-only and is held solely because `refreshAggregatePendingLocked` iterates the peer domain; `deliveryMu` covers `pending` / `pendingKeys` / `outbound` / `awaitingDelivered` / `relayRetry`; `gossipMu` covers the `topics["dm"]` backlog; `statusMu` is the innermost aggregate-pending recount. Everything is emptied inside ONE section on purpose: a backlog envelope dropped while a retry tick still holds its `awaitingDelivered` entry would re-enter the wire on the next tick. `TopicPeerPendingChanged` / `TopicAggregateStatusChanged` are published after every mutex is released, per the standard side-effect rule. See `docs/dm-commands.md` §"Withdrawing an unsent message".

#### `CancelOutgoingDeliveriesTo` (withdraw a whole conversation)
Same section and same canonical order as `CancelOutgoingDelivery` — `peerMu.RLock → deliveryMu.Lock → gossipMu.Lock → statusMu.Lock`, released LIFO, events published afterwards — but scoped by RECIPIENT instead of by message id, and it walks each structure once rather than once per message. That is the reason it exists: the per-message form takes the whole stack and rescans the backlog on every call, so wiping a thread of a thousand messages through it would be a thousand full scans under a writer mutex. Foreign envelopes (transit traffic addressed to the same peer) are skipped inside the same pass — a wipe of OUR conversation is not a licence to purge other people's messages.

#### `retryDueDeliveries` / `registerAwaitingDeliveredLocked` / `registerAwaitingSeenAckLocked` (sender-side e2e retry)
`recipientPassState` is the same domain and holds what the previous retry tick MEASURED for each recipient with a delivery awaiting its receipt, plus that recipient's VISIT counter (and `deliverySeq`, the registration order deliveries are numbered with, is the same domain) — the stretch between two absences, bumped when a pass measures a recipient it could previously reach as unreachable. The accelerated attempt a return is worth is counted against that visit ON THE DELIVERY (`deliveryRetryEntry.AcceleratedInVisit`), so the two writers never contend for one cell: a monotone bump on one side, a compare-and-set on the other. It is read by that pass (`planDueDeliveries`) and written by two others: `finishRecipientReading`, at the END of the pass and as a MERGE over the deliveries that still exist, and `wakeOverdueForReturningPeer` on a session event. The merge is what makes two writers safe — the pass must not replace a mark a session event has just recorded — and keying it by the live awaiting set is what keeps it bounded without a sweep. The merge alone is not enough for the READING itself: the record also carries a presence count (`recipientPassRecord.presence`), bumped inside the section by every observation of the recipient being here that did not come from a pass, captured by the reading before the measurement, and stamped onto every spend (`deliveryRetryEntry.AcceleratedAtPresence`). A commit that ends a visit carries forward the spends stamped after its own reading (`carryAccelerationsIntoNewVisitLocked`), because a send made between the measurement and the commit could only count against the visit being closed. The measurement itself runs with NO delivery mutex held (`recipientHasPath` reads `gossipMu` and the routing table's own lock, and `resolveRouteNextHopAddress` takes `peerMu`, so measuring under `deliveryMu` would invert `peerMu → deliveryMu`); only the compare-and-replace is inside the section.

`deliveryRetryEntry.ClaimedAt` is the same domain and is how two senders stay off one message: it is stamped inside the section by whoever takes the message through the pre-wire claim (`markEntryEmitted`), and read there by the retry pass, which stands down while another sender's claim is in flight (`emissionInFlight`). It needs no release, so no path can leak one — see the field's own comment. Who must stand down for it is decided by the call site (`emissionSender`): the three senders that START a send ask, the writers carrying out a decision that already passed do not. Its instant is read inside the section, never on the way in: the wait for this mutex is time, and a stamp read before it can be older than the window it will be measured against.

`markedNeverEmitted` is the same domain and names the ids this process has a durable never-emitted claim standing for. It exists because the backlog replay reaches past the retry engine: it can emit a message whose `awaitingDelivered` entry is already gone — its own TTL expired, or a receipt removed it — and without this the claim would stay on the row while the peer holds the message. Entries leave the set on the three events that end a claim: a withdrawal that takes the frame out (`clearEmissionMarks`), a confirmation or receipt that disproves it, and the author withdrawing the message, whose row is destroyed with the mark on it (`CancelOutgoingDelivery` / `CancelOutgoingDeliveriesTo`, memory only — there is no row left to write to, and released by SCOPE for the same reason `clearFreezeLocked` is: the set outlives the retry entry, so releasing only what a pass found in `awaitingDelivered` would strand every id whose entry had already gone). A TTL expiry deliberately leaves the claim standing: the row survives as failed, and it never went out.

`markedNeverEmitted` is the only companion state the emission flags still need, and there is no queue beside it any more. The durable side is TWO monotone bits, each written in one direction (chatlog/emission.go): `never_emitted` is written by the row's INSERT and cleared once, before the first frame; `on_wire` is written once, after a sink confirms. Because neither is ever reversed, nothing has to be decided, queued, re-read or corrected — the version that kept a single reversible flag needed all four and still had a race left.

Neither bit is ever reversed, so there is nothing to decide at write time: a refusal writes nothing at all, a confirmation writes one fact in the one direction its bit moves, and at every instant the row already says both of the things its two readers need. That is what removed the queue, the per-attempt stamp, the re-read and the correction that a single reversible flag required.

`frozenDeliveries` is the same domain and holds the ids a conversation wipe is deciding about. Every path that could emit consults it under the same lock that would mark the emission (`claimEmissionLocked`, `confirmEmission`), so "may this go out" and "is a wipe deciding about it" are answered from one snapshot. The retry tick consults it TWICE for that reason: once when it picks candidates (`pickQueueHeadLocked`), where a frozen entry stops its recipient's queue for the tick, and again immediately before the wire — the planning pass, the lock-free route lookup and the dispatch are three separate windows, and a freeze can land in any of them. Neither consultation can cost the message anything, because the tick charges nothing at all: the attempt is spent by `confirmEnvelopeOnWire`, called by the SINK that accepted the frame, so a freeze landing in any window simply finds nothing spent. The refusal path (`holdDeliveryRetry`) restores the schedule the pass displaced for a frozen entry, for the same reason — a thawed message must go out at once rather than pay a poll interval for a decision its recipient had no part in. Unlike `cancelledDeliveries` it never expires: the freeze ends when the wipe commits — `CancelOutgoingDeliveriesTo` clears it, over the caller's whole SCOPE rather than over what it happened to find, since most of a long thread has no delivery state left to withdraw — or aborts, and `ThawOutgoingDeliveries` puts the deliveries back. A single-message delete takes the same freeze for one id and its withdrawal clears it; every other exit — an immutable message, an unreadable row, a route with nothing to withdraw — releases it explicitly, because the freeze has no TTL and nothing else would. An expiry would be a deletion guarantee with a timeout attached. See docs/dm-commands.md §"Bulk wipe".

`cancelledDeliveries` is the same domain and exists because one pair of operations CANNOT share a lock hold: building a subscriber's backlog frame reads the gossip domain and then the delivery domain, in that order, which is the reverse of the canonical one, so the snapshot and the emission mark are two separate windows. A withdrawal landing between them would report "never emitted" — the router then recalls the message and schedules nothing — while the snapshot still holds the envelope and sends it. `CancelOutgoingDelivery` / `CancelOutgoingDeliveriesTo` therefore record the id under `deliveryMu` (`noteDeliveryCancelledLocked`), and `noteOwnEnvelopesEmitted` reports back, in the SAME lock hold as the marking, which of the ids it was asked about are shadowed; the backlog writer skips those. Entries are pruned by age on write and only have to outlast one push.

`emissionLane` is NOT a domain mutex and does not appear in the canonical order — it guards no `Service` state, only the order in which this node's own journal writes reach SQLite. It is deliberately held across that disk I/O, which needs saying because the mutex it replaced was condemned for exactly that.

The difference is priority, and priority is the whole point. Both writers set a monotone bit in a different metadata key with one self-contained conditional UPDATE, so nothing needs ordering for CORRECTNESS. What needs ordering is need: `clearEmissionMarks` withdraws the born-with claim BEFORE a frame goes out, so a message the user is waiting on cannot leave until it lands, and a clear that runs out of `busy_timeout` withholds that message; `markDeliveryOnWire` records a frame already gone. SQLite takes one writer at a time and the pool is not clamped, so with no order of ours a reconnect stamping a replayed conversation competes with the clear in the busy handler and can beat it repeatedly. The lane is a QUEUE, not a lock: turns go to withdrawals before bookkeeping, in arrival order within each class, and a turn writes at most `maxIdsPerLaneWrite` ids — a writer with more rejoins the BACK for the rest. Each kind of writer is bounded differently, because only one of them can be refused: a stamp the lane will not queue writes nothing and is re-derived by `repairLocalDeliveryRecord`, while withdrawals, which may not be refused without withholding a message, are COALESCED up to one statement's worth when one takes its turn. `storeDeliveryReceipt` is deliberately NOT one of the lane's callers at all: `delivered` outranks the stamp everywhere the stamp is read, so that path writes no journal. A status write that fails leaves the receipt UNHANDLED, and nothing about it was committed: `finishReceipt` (deliveryMu) writes the dedup key and deletes the retry entry only after the write lands, so the sender keeps retrying the message and the next receipt tries the write again.

Deadlock-freedom is the same one line it always was: the lane is entered OUTSIDE every domain mutex and NEVER while one is held. Call sites obey it — the clear in `noteOwnEnvelopesEmitted` and the stamp in `confirmEnvelopeOnWire` / `storeDeliveryReceipt` all run AFTER `deliveryMu` is released — and that is the general rule for disk I/O rather than anything specific to this journal. `TestEveryJournalWriteGoesThroughTheEmissionLane` fails the build if a write appears outside the lane.

The delivery retry scheduler (`delivery_retry.go`) owns `awaitingDelivered` / `awaitingSeenAck`, both delivery-domain fields. `retryDueDeliveries` never holds a mutex across network I/O; it alternates between four steps, and the `deliveryMu.Lock` of each one ends before the next begins:

1. `planDueDeliveries` — one `deliveryMu.Lock`: sweeps the awaiting set, deletes the messages whose own TTL expired (`classifyAbandonedLocked` — the only terminal verdict there is), and picks AT MOST ONE candidate per recipient (`selectQueueHeadsLocked` → `pickQueueHeadLocked`, which reads `frozenDeliveries` in the same hold).
2. lock-free: `router.Route` per candidate. It reads routing and peer state under its own locks, so running it under `deliveryMu` would invert the canonical `peerMu → deliveryMu` order.
3. `armDueDeliveries` — one `deliveryMu.Lock`: writes `Held` atomically with the schedule, so no `kickDeliveryRetriesForReachable` observes a half-updated entry, and runs `resetBackoffOnReturn` for the entries whose recipient just came back.
4. no mutex: `emitDueDelivery` per envelope, which hands the envelope to the sinks and writes NOTHING. Each sink calls `confirmEnvelopeOnWire` (a short `deliveryMu.Lock`) if it accepted the frame — inline for a relay enqueue, from a background goroutine for a subscriber push. An entry no sink confirms simply stays `holdUnconfirmed`.

`confirmEnvelopeOnWire` is the single place a delivery becomes "sent", and it is called by the SINK that accepted the frame — a relay enqueue inline, a subscriber push from its background goroutine — never by the code that merely decided to try. It takes `deliveryMu` alone, charges the attempt, clears the hold and stamps `LastEmittedAt`; the `dispatchedAt` argument makes several sinks confirming one dispatch charge it once. The announcement (`publishMessagesEmitted`) claims `Announced` under the same mutex and publishes after releasing it, per the standard side-effect rule — a subscriber callback can come back into the Service — and gives the claim back when the bus sheds the event.

`markEntryEmitted`, by contrast, writes only `Emitted`, which is the conservative "might the peer have this?" flag and is deliberately set BEFORE the wire. Neither the hold nor `LastEmittedAt` may be written there: doing so would make a confirmation see its own attempt as already answered.

`lastReachabilityKickAt` is the same domain and exists for one race: the tick samples reachability with no mutex held, and a kick landing in that window finds the entry not yet `Held` — invisible to it — while the tick goes on to park the entry on an answer the kick has just invalidated. `kickDeliveryRetriesForReachable` stamps it under `deliveryMu` BEFORE its scan and regardless of what the scan finds, precisely because the case it exists for is the one where the scan finds nothing; `armDueDeliveries` compares the stamp against the start of its pass and keeps the entry due. One timestamp rather than a per-identity map: a false positive costs one local routing-table lookup on the next tick.

The one-per-recipient rule in step 1 is the queue discipline, not an optimisation: sends are handed to background goroutines, so a tick that emitted a whole backlog would deliver it in the order the scheduler happened to run it, and a Go map gives no order to iterate it in either. `deliveryRetryEntry.LastEmittedAt` (delivery domain, same entry) is what holds a recipient's slot between the emission and its receipt; it only ever moves forward, because one emission is stamped by both the tick and the background push and they do not share a clock. `storeDeliveryReceipt` frees the slot and pulls the next message forward (`promoteQueueHeadLocked`) inside its existing canonical `peerMu → deliveryMu` window.

The `*Locked` helpers require the caller to hold `deliveryMu.Lock`; registration call sites (`storeIncomingMessage` for own outgoing DMs, `storeDeliveryReceipt` for own seen receipts) take `deliveryMu` with no other domain mutex held, or inside that same canonical window. `storedMessageStatus`, which answers the local sender whether their message went out or is queued, takes `deliveryMu.RLock` alone.

#### `fetchInboxFrame` (gossip topics read + delivery receipt lookup)
Touches `gossipMu` (read `topics[topic]`) and `deliveryMu` (`receipts` via `hasReceiptForMessageLocked`). The two are expressed as SEQUENTIAL lock windows, not nested: take `gossipMu.RLock`, copy the topic slice, release; then for each DM envelope take a fresh `deliveryMu.RLock` just long enough to check receipt presence. Sequential splitting works because the topics slice is a local copy by the time the delivery read happens — there is no data-flow dependency that requires the gossip lock to remain held. It also keeps the canonical `deliveryMu → gossipMu` order from being violated: taking `deliveryMu.RLock` while holding `gossipMu.RLock` would be the reverse edge and is forbidden.

`removeSubscriberConnID` / `removeSubscriberByID` use the same sequential split for a WRITE pair: they remove subscribers under `gossipMu.Lock`, collect any recipients whose last subscription just disappeared, RELEASE `gossipMu`, and only then call `dropReceiptBacklogForOfflineRecipients`, which takes `deliveryMu.Lock` to delete those recipients' `receipts` backlog (and clear the `seenReceipts` / `relayRetry` shadows). Entering with `gossipMu` still held would be the forbidden reverse edge. Inside the drop, while holding `deliveryMu.Lock`, it takes `gossipMu.RLock` for the ENTIRE check+delete loop (reading `s.subs[recipient]` directly, NOT via the momentary `hasSubscriber` probe) — this is `deliveryMu` OUTER → `gossipMu` INNER, the canonical order, so the nesting is deadlock-free, released LIFO. Holding `gossipMu.RLock` across the whole loop closes a reconnect race: the caller already released `gossipMu`, so a concurrent `registerHelloRoute` may re-subscribe the same recipient in the gap; a momentary subscriber sample followed by a later delete would let a reconnect landing between sample and delete wipe a freshly online subscriber's backlog. Keeping the read lock held for the duration makes the "still offline?" test and the delete atomic against `s.subs` writers (`registerHelloRoute` takes `gossipMu.Lock` and cannot interleave). The body does only in-memory work, so the held window stays short. The re-registration path (`registerHelloRoute` → `removeSubscriberConnIDLocked`) deliberately does NOT drop the backlog: the peer is re-subscribing in the same critical section, not going offline.

#### `queuePeerFrame` (peer→delivery cross-domain write)
Entry point for every outbound DM frame routed through the pending-queue backlog. Touches peer-domain (`s.resolveHealthAddress` reading `health`/`peerIDs`), `deliveryMu` (`pending`, `pendingKeys`, `outbound` via `noteOutboundQueuedLocked`), and status-domain (`s.aggregateStatus.PendingMessages` refreshed via `refreshAggregatePendingLocked`). Canonical order `peerMu → deliveryMu → statusMu`: `peerMu.Lock` OUTER → `deliveryMu.Lock` MIDDLE → `statusMu.Lock` INNERMOST around the aggregate-pending refresh and `aggregateStatus` snapshot read. All three locks observe the same delivery snapshot so that an enqueue, its dedup check against `pendingKeys`, and the aggregate pending-count refresh are atomically consistent. Every exit path — no-key, dup, per-peer overflow, global overflow, normal enqueue — releases the locks in LIFO order before emitting the post-unlock side effects (pending-count ebus events).

#### `flushPendingPeerFrames` / `flushPendingFireAndForget`
Drain the backlog for a peer once a session is available. Read peer-domain state (`resolveHealthAddress`, session lookup) and mutate `deliveryMu` (remove or requeue entries in `pending`/`pendingKeys`); refresh the aggregate status under `statusMu` when the backlog size changes. Canonical order `peerMu → deliveryMu → statusMu`: `peerMu.Lock` OUTER → `deliveryMu.Lock` MIDDLE → `statusMu.Lock` INNERMOST around the aggregate refresh. The requeue case (send failed, frames put back) re-takes the nested stack rather than holding the original window across network I/O — network writes must never happen under any domain mutex. The drain-empty fast path takes `peerMu.Lock` + `deliveryMu.RLock` + `statusMu.Lock` around `refreshAggregatePendingLocked` because the aggregate-pending recount reads delivery-domain fields and writes status-domain state.

#### `onCMSessionEstablished` session goroutine / `onCMSessionTeardown` (session map registration and cleanup)
An outbound CM session is entered in `sessions` (peer domain) and `upstream` (delivery domain) together and removed from both together, with `dialOrigin` (peer domain) removed alongside. Every such write holds `peerMu.Lock` OUTER with a nested `deliveryMu.Lock` INNER, canonical `peerMu → deliveryMu`, so a reader that takes both never sees the session in one map but not the other. The session goroutine started by `onCMSessionEstablished` registers the session once `initPeerSession` succeeds and removes it when `servePeerSession` returns; `onCMSessionTeardown`, which CM calls on its event loop after releasing `cm.mu`, removes it when CM deactivates the slot. Removal compares the session pointer, so a replacement session registered for the same address is left alone. Routing registration and deregistration (`onPeerSessionEstablished` / `onPeerSessionClosed*`) are NOT tied to who removes the entry: the session goroutine does both, in that order, exactly once per session, and `onCMSessionTeardown` never touches routing — a teardown that ran between the registration and `onPeerSessionEstablished` could otherwise deregister a route before it was added and leave it registered for a closed session.

Registration vs. a concurrent CM close. The CM stores the close reason (`peerSession.closedBy`, atomic, inside `closeOnce`) in `tearDownSession`, on its event loop with `cm.mu` released, BEFORE it calls `onCMSessionTeardown`, which removes the entry under `peerMu`. The goroutine checks the reason and registers in ONE `peerMu` section (`registerCMSession`). Either the teardown's `peerMu` section comes first — then the goroutine's section is ordered after the reason was stored, sees it and does not register — or the goroutine's section comes first, and the teardown that follows finds the entry and withdraws it. A session the CM has closed is therefore never left in `sessions` / `upstream`, and a session closed before registration is never marked connected or counted in `identitySessions`. No lock is added for this: neither side holds `cm.mu` (see `connBudget` above for what is taken under it), and the reason is an atomic.

What this does not cover is an eviction that lands AFTER `registerCMSession` returned and before `markPeerConnected` / `onPeerSessionEstablished`. That session is published — registered, marked connected, counted — and unwound moments later by the goroutine's own withdrawal once the serve loop sees the closed socket. Guaranteed even then: the accounting balances (the goroutine registers and deregisters, in order, exactly once), and the peer is not charged. Not guaranteed: that no reader sees the session as live during that window. A re-check before each later step would only narrow the window, so none is made. Invariant B is therefore exactly: a session closed by a local decision is never charged to the peer, and a session closed BEFORE its registration is never published. Neither side touches `pending`: the backlog for the peer is drained by `flushPendingPeerFrames` (section above) after registration.

#### `rebuildPeerHealthSnapshot` (hot-reads refresher for fetch_peer_health)
Builds the atomic snapshot consumed lock-free by the `fetch_peer_health` RPC. Reads peer-domain state (`health`, `peerIDs`, `peerVersions`, session map, capabilities) and delivery-domain state (`pending` for per-peer queued-count). Order: `peerMu.RLock` OUTER → `deliveryMu.RLock` INNER, canonical `peerMu → deliveryMu`. Both locks are released before the snapshot is `atomic.Pointer.Store`'d so the swap itself is lock-free. The cross-domain scope is intentional: the handler must render the per-peer pending count against the same peer roster it observed, otherwise a newly-arrived peer would appear with zero pending even when `queuePeerFrame` had already enqueued for it microseconds earlier.

#### `penalizeOldProtocolPeer` / `applySelfIdentityCooldown` (peer-delta emission callers)
Both call `emitPeerHealthDeltaLocked` after mutating peer-domain state. `emitPeerHealthDeltaLocked` requires the caller to hold BOTH `peerMu` and `deliveryMu` at least for read, because its body reaches into `publishAggregateStatusChangedLocked` → `refreshAggregatePendingLocked`, which counts `pending`. Both callers wrap the emit with a short `deliveryMu.RLock`/`RUnlock` nested inside their existing `peerMu.Lock` region, preserving canonical `peerMu → deliveryMu` order. Version-policy mutations inside `penalizeOldProtocolPeer` (`recordIncompatibleObservationLocked`, `setVersionLockoutLocked`, `recomputeVersionPolicyLocked`) wrap `statusMu.Lock` INNERMOST around the full version-policy section since `versionPolicy` now lives under `statusMu`. The emit helper itself does not take `deliveryMu.RLock` — every caller already holds it (see `updatePeerStateLocked` below), and a recursive RLock deadlocks under Go's writer-preferring RWMutex once a writer queues in between.

#### `updatePeerStateLocked` / `emitPeerHealthDeltaLocked` (aggregate-status recompute)
`updatePeerStateLocked` holds `peerMu.Lock` and, for the full duration of its body, `deliveryMu.RLock` via `defer`. The RLock covers the `s.pending` log line AND the downstream `publishAggregateStatusChangedLocked` → `refreshAggregatePendingLocked`/`computeAggregateStatusLocked` chain, so every delivery-domain read inside the same scope observes a consistent snapshot. The call to `publishAggregateStatusChangedLocked` is wrapped with a nested `statusMu.Lock`, canonical `peerMu → deliveryMu → statusMu`. `emitPeerHealthDeltaLocked`'s contract is documented as "caller holds both peerMu and deliveryMu at least for read"; it relies on the caller's scope rather than nesting its own RLock because every caller already holds `deliveryMu` for read — `updatePeerStateLocked` through its own deferred RLock, `penalizeOldProtocolPeer` and `applySelfIdentityCooldown` through a short RLock around the call — and a recursive RLock inside the helper would deadlock under Go's writer-preferring RWMutex whenever a writer queues between the two acquisitions.

#### Aggregate-status helpers (`computeAggregateStatusLocked`, `refreshAggregateStatusLocked`, `refreshAggregatePendingLocked`, `publishAggregateStatusChangedLocked`)
All four require the caller to hold `peerMu` AND `deliveryMu` at least for read (delivery domain — `pending`; peer domain — `health` via `computeAggregateStatusLocked`). `computeAggregateStatusLocked` reads only peer-domain and delivery-domain fields and does NOT require `statusMu`. The other three (`refreshAggregateStatusLocked`, `refreshAggregatePendingLocked`, `publishAggregateStatusChangedLocked`) additionally require `statusMu.Lock` because they write `aggregateStatus`, `lastPublishedAggregateStatus`, or `lastAggregateStatusPublishAt`. Canonical order `peerMu → deliveryMu → statusMu`: OUTER → MIDDLE → INNERMOST. None of the helpers takes `deliveryMu.RLock` internally; a self-nested RLock is unsafe under writer-preferring semantics if a writer queues between acquisitions, and multiple callers already hold `deliveryMu.Lock` exclusively. The non-Locked entry point `refreshAggregateStatus` acquires `peerMu.Lock` then `deliveryMu.RLock` then `statusMu.Lock`, releases in LIFO order, and is the only place in the helper family where the full stack is acquired fresh.

Pure aggregate-status readers (`AggregateStatus`, `aggregateStatusFrame`, `VersionPolicySnapshot`) take ONLY `statusMu.RLock` — they read `aggregateStatus` / `versionPolicy` without touching peer or delivery state. This is the central Phase 2 win for Desktop-UI RPCs: a writer storm on `peerMu` no longer blocks a status read, because the reader holds a disjoint mutex.

#### `peerSession.sendMu` — the outbound queue fence

There are TWO queues on the outbound session path: `peerSession.sendCh` (upper — produced by arbitrary goroutines, consumed only by `servePeerSession`) and `NetCore.sendCh` (lower — consumed only by the connection writer goroutine). A frame may carry an outbound contract (`netcore.WriteTicket`: a send deadline and a per-frame write grace, and nothing else — the ticket travels one way and reports nothing back). Each queue must still discard the whole residue it holds at the moment it dies: without the drain, the frames of a dead session stay referenced by the buffered channel for as long as anything holds the session, and a flapping peer leaves one such buffer per attempt.

`peerSession.sendMu` (`sync.Mutex`, `peer_send_queue.go`) guards exactly one boolean — `sendClosed` — and fences the non-blocking send into `sendCh`. It sits OUTSIDE the seven-domain split, as a **leaf**: it is never held while acquiring a domain mutex, and no domain mutex is held across `enqueueSend`. `dispatchOutboundAnnouncePlaneFrameWithCaps` captures the session under `peerMu.RLock` and enqueues only after releasing it; `enqueuePeerSendItem` resolves the session (`activePeerSession`) and the peer state (`peerState`) through their own short lock sections and enqueues afterwards. The fence therefore adds no edge to the canonical order.

Why a fence and not `close(sendCh)`: producers run on arbitrary goroutines and must neither block nor panic, and a producer racing a `close` panics on send. Flipping the flag under the same mutex the producers hold during their non-blocking send waits out any in-flight producer and refuses every later one, so the drain that follows provably sees the whole residue.

The SAME rule holds one layer down, and for the same reason: `NetCore.sendCh` is never closed either. It cannot use a mutex fence, because one of its producers (`queueFrameBlocking`, behind `SendRawSyncBlocking`) waits inside the offer for a slot that only the writer can free — a fence would make `Close` wait for a producer that is waiting for `Close`. It uses a monotonic atomic gate instead, read by every producer on both sides of its offer, and `NetCore.Close` raises that gate BEFORE it touches the socket or signals the writer. The writer's exit signal is a separate `closing` channel, so the queue itself is never closed under a live sender. A frame a racing producer still deposits is answered by the gate and released with the buffer when the `NetCore` is collected. The gate is also what NAMES the teardown to a producer already past the door: both the socket failure and the orderly `Close` wake it on the same `writerDone` channel, so the reason is read off the gate (`teardownStatus`) instead of being inferred from the wakeup — otherwise a caller's own `Close` came back as `SendWriterDone`, which is the answer that invites another `Close`. See `docs/protocol/network_core.md`, "Queue ownership".

**There is no terminal callback to keep out of the locks.** The outbound contract is data, not a hook: the writer reads `SendUntil` and `WriteGrace` off the ticket and nothing calls back up. `enqueueSend` still splits the guarded offer into `offerSend` (no `*Locked` suffix — it takes `ps.sendMu` itself), so the mutex is held for the offer and for nothing else, and `closeSendQueue` still drains after releasing `sendMu`. Refusal is reported to the producer as `false` rather than through a callback, because the producer owns the fallback policy (pending ring, inbound fallback).

Who drains what, per death path (every path must cover BOTH queues):

| Path | Upper queue (`sendCh`) | Lower queue (`NetCore.sendCh`) |
|---|---|---|
| socket write error / write-grace expiry | serve loop exits → `defer closeSendQueue` | writer shuts the gate (`gateSocketFailed`), drains what is buffered, then stays in drain-only mode |
| `servePeerSession` exit (ctx cancel, peer error, writer death, heartbeat stall, panic through `crashlog.DeferRecover`) | `defer closeSendQueue` | `peerSession.Close` → `NetCore.Close` |
| `peerSession.Close` before the serve loop ever runs (handshake failure, CM generation mismatch) | `closeSendQueue` first, then the transport | `NetCore.Close` shuts the gate and signals `closing`; the writer drains the queue before `Close` returns |
| `NetCore.Close` | — | gate shut first (producers get `SendChanClosed`), then the socket, then `closing`, then wait on `writerExited` (NOT `writerDone`: after a write failure the writer still owns `sendCh`) |
| queue refusal (no session, stalled peer, saturated queue, closed channel, marshal error) | `enqueueSend` / `enqueuePeerSendItem` answer `false` at the door, so the frame provably never started a write | `SendRawTracked` answers a non-`SendOK` status. Refusals AT THE DOOR (`SendBufferFull`, `SendMarshalError`, the gate read before the offer) prove the frame never entered the queue; a refusal read AFTER the offer proves only that the queue will not write it — see `docs/protocol/network_core.md`, "Tracked sends" |

An expired `SendUntil` is deliberately absent from that table: it is not a queue death at all. The writer skips the frame immediately before `rawConn.Write`, the connection stays up, and the frames behind it keep going.

`markPeerDisconnected` deliberately appears nowhere in that table either: it only mutates health/state and owns no queue. Every path that reaches it also reaches either the serve-loop exit or `peerSession.Close`, which are the two owners of the fence.

**Ordering contract — the fence is raised BEFORE the peer is published as gone.** A producer reads two facts as one decision: the peer-state gate (`peerAcceptsOutboundFrames`, written by `markPeerDisconnected`) and the queue's own answer. Only this order makes the pair honest. Published first, the disconnect leaves a window in which a producer admitted a moment earlier still deposits its frame into a queue the same teardown is about to discard — and the datagram emitter, which treats "the queue accepted it" as a delivery, ENDS its walk over the peer's remaining connections there, so the frame reaches neither this socket nor the next candidate. The two teardowns that own a queue implement it: `retirePeerSession` (`closeSendQueue` → `markPeerDisconnected`) on the dialled tier and `trackInboundDisconnect` (`NetCore.ShutSendQueue` → `markPeerDisconnected`) on the accepted one. Both fence UNCONDITIONALLY — the accepted tier does so even when this was not the last reference holding the health row up — and both do it outside every mutex, so the pair adds no edge to the canonical lock order.

The contract is ENFORCED rather than documented. `send_admission_race_test.go` interleaves one producer and one teardown through two seams that are nil in production: `Service.sendAdmissionBarrier` parks the PRODUCER inside the admission window (past the peer-state gate, before the queue offer), and `Service.peerTeardownBarrier` parks the TEARDOWN, on a goroutine of its own, BETWEEN its two publications. Both halves are needed and neither substitutes for the other: without the producer half the reversed order is simply refused by the gate and looks correct; without the teardown half the teardown runs to completion inside the producer's barrier and the resumed producer sees the same world whichever way round the two statements are written — which is exactly how an earlier version of these tests stayed green on the reversed implementation. Swapping the two publications on either tier turns the corresponding test red.

#### `gossipMu` — the local-change subscriber fence

`s.events` (gossip domain) is a set of subscriber inboxes, and the cancel returned by `SubscribeLocalChanges` CLOSES the inbox it registered. That makes the publisher's lock discipline part of the channel's safety, not just of the map's: `emitLocalChange` offers the event to every inbox while holding `gossipMu.RLock`, so the closer — which takes `gossipMu.Lock` — waits out every publisher already inside an offer and refuses every later one, because by then the map entry is gone. Snapshotting the set under the lock and offering after releasing it is NOT equivalent: the snapshot names channels the cancel is free to close in the gap, and a send on a closed channel is a panic in whichever goroutine happened to emit the event.

Holding a domain mutex over the offers does not breach the "no I/O under a lock" rule: every offer is non-blocking (`select` with `default`), so the section is bounded by the number of subscribers and cannot re-enter `Service`. The side effect — the warn line for a full inbox — is emitted by `emitLocalChange` AFTER `offerLocalChangeToSubscribers` has released the lock, per the cross-domain rule above.

### Reader path invariants

RPC hot paths that already read atomic snapshots (`fetch_network_stats`, `fetch_peer_health`, `get_peers`) remain lock-free; Phase 2 does not change them. What Phase 2 changes is the *refresher* goroutine's exposure to unrelated-domain contention.

Per-snapshot refresher lock footprint today:

- `networkStatsSnapshot` / `peerHealthSnapshot` — short `peerMu.RLock` (plus `deliveryMu.RLock` nested where per-peer queued-count is rendered). No IP-state callbacks, no `statusMu` hold.
- `cmSlotsSnapshot` — `cm.mu.RLock` only (separate mutex inside `ConnectionManager`, not covered by this split).
- `peersExchangeSnapshot` — more complex. `rebuildPeersExchangeSnapshot` takes a short `peerMu.RLock` for `persistedMeta` / `health`, releases it, then calls `peerProvider.Candidates()`. That Candidates call fires callbacks back into the Service: `BannedIPsFn` acquires `ipStateMu.RLock`, and `RemoteBannedFn` acquires `peerMu.RLock → ipStateMu.RLock` in the canonical order. A burst of IP-state writers (ban updates, observed-IP convergence) can therefore still delay this particular rebuild.
- `routingSnapshot` — `routing.Table.t.mu.Lock` (exclusive: `SnapshotIncremental` consumes the per-identity snap dirty-set and updates the reuse cache; separate mutex inside the `routing` package, not covered by this split). The projection build is gated by `routing.Table.ConsumeDirty()` (CAS true→false) so a steady-state idle node skips the rebuild entirely; the publisher rebuilds only when some writer flagged the table dirty since the last consume. The binding rule is "any change to a published snapshot field (`Routes`, `FlapState`, `Health`, `CapStats`) sets the coarse dirty flag"; the writers fall into two non-exhaustive groups — *route-projection writers* that change `Routes` and so also mark the per-identity incremental dirty-set (`UpdateRoute`, `WithdrawRoute` / `InvalidateUplinkClaim`, `AddDirectPeer`, `ConfirmHopAck` promotion; `RemoveDirectPeer`, `InvalidateTransitRoutes`, `TickTTL` expiry force a full re-copy), and *snapshot-field-only writers* that change `FlapState` / `Health` / `CapStats` but not the routes, so the incremental build still reuses every route slice (`MarkHopAck`, `MarkProbeAck` / `MarkProbeFailure`, `MarkHopFailure`, `TickHealth`, black-hole cooldown clear, `RecordSuccessfulRouteAdd`, and the SeqNo flap-cap engage on armed `AnnounceTo` / `AnnounceTargetFor`). The publisher derives reachability and the presence `hasTransit` classification together in one O(routes+health) pass with one Dead-health index and one classification map; the lock-free identity-only cache is a compact immutable slice, not a second full-size map. Bulk reachability readers clone or iterate that slice instead of calling `BestRoute` per identity. Cached consumers (`Service.RoutingSnapshot()` for RPC, `Service.reachableIDsFrame()` for desktop remote-RPC, the file router's `RouteSnap` callback used by transit forwarding inside `HandleInbound`) take no routing-table mutex on the read path. If a witnessed final-route transition updates a trusted contact's `last_online_at`, the refresher queues `trustStore.recordLastOnlineAt` through the tracked `Service.goBackground` runner after publishing the snapshot. The JSON marshal/write/rename therefore performs no filesystem I/O on the refresher goroutine; `WaitBackground` joins it during shutdown and tests. `routeTableHandler` additionally enriches each unique next-hop identity through `RoutingProvider.PeerTransport`, which currently takes `peerMu.RLock` — that handler therefore stays exposed to peer-domain writer storms even after the routing-table coupling was eliminated; migrating `PeerTransport` onto a cached peer-transport view is tracked separately. Three production callsites deliberately bypass the cache and read the routing table directly via `routing.Table.Lookup(peer)` — a per-destination read that takes `t.mu.RLock` for an O(K) slice scan over only that destination's routes, not for the whole table: `file_integration.isPeerReachable` (gates user-initiated file transfers), `filerouter.Router.SendFileCommand` (locally-originated send path, wired through `RouterConfig.RouteLookup` to the same Lookup), and `filerouter.Router.ExplainRoute` (diagnostic surface, must mirror the live send). All three need immediate visibility of a route accepted seconds before the call — an ~2–2.5 s-stale view (`routingSnapshotMinInterval`'s 2 s floor plus the next refresh tick) would surface as "isPeerReachable says yes, SendFile fails" or as "ExplainRoute shows a path the live send cannot use". `isPeerReachable` holds `s.peerMu.RLock` only for the peer-domain probe and releases it before the routing read, so the two locks remain sequential, not nested; the file-router callsites take no Service-domain mutex at all on the locally-originated path. The transit forwarding path inside `HandleInbound` keeps using the cached `RouteSnap` because in-flight frames carry their own metadata and an ~2–2.5 s delay (the routing snapshot's coalescing floor plus a refresh tick) on a freshly added route is harmless there. Since the copy-on-write incremental snapshot landed, the publisher calls `routing.Table.SnapshotIncremental` (which takes `t.mu.Lock`, not `RLock`, for the brief projection build: it consumes a per-identity dirty-set the mutation wrappers maintain and reuses the unchanged buckets of the previous snapshot, so the per-rebuild allocation is proportional to the churned identities rather than the whole table). The exclusive hold is bounded — at most once per `routingSnapshotMinInterval` and shorter than the old full deep copy — and stays inside the routing package's own mutex, so the canonical Service lock order is unaffected. The single-threaded publisher contract is load-bearing here: `SnapshotIncremental` caches the previous projection and consumes the dirty-set, so no second concurrent caller may use it — any other consumer that needs an always-complete copy calls `routing.Table.Snapshot` (still `RLock`, still a full deep copy). Bulk mutations (`RemoveDirectPeer`, `InvalidateTransitRoutes`, `TickTTL`) force a full re-copy, and the publisher additionally upgrades a rebuild that is happening anyway (the table was dirty) to a full re-copy once `routingSnapshotFullInterval` of wall-clock time has elapsed since the last full one, as a self-heal net for any mutation site that failed to mark its identity dirty. This never wakes a clean table — a missed mark can only stale the published snapshot if a rebuild ran at all (coarse `dirty` set, per-identity mark missed), so the heal only rides along on a future dirty rebuild and the idle-skip invariant above is preserved. The wall-clock cadence (driven by the `atomic.Int64 Service.lastRoutingFullSnapAtNanos` timestamp, set on the single snapshot refresher plus the sequential startup prime) is deliberate: a pass counter would drift with the refresher tick rate because idle clean-skips do not advance `lastRoutingSnapAtNanos`, so the throttle lets every 500 ms tick through and a counter would fire the full roughly twice as often as intended.

What Phase 2 eliminates is shared contention *across domains*: a `fileMu` or `statusMu` write no longer blocks any of the five refreshers (`networkStatsSnapshot`, `peerHealthSnapshot`, `peersExchangeSnapshot`, `cmSlotsSnapshot`, `routingSnapshot`). What Phase 2 does **not** eliminate is the intra-domain dependency above — debugging a `get_peers` staleness spike must still consider IP-state writer traffic, not just peer-domain traffic. That intra-domain coupling is intentional because `BannedIPsFn` / `RemoteBannedFn` are correctness gates on the candidate list; the trade-off is that the 500 ms staleness window on the snapshot absorbs those short blocks without reaching the RPC handler.

Last-online persistence is node-owned rather than bus-owned. A direct peer loss
confirmed by clean remote EOF is timestamped when the session closes and observed after `RemoveDirectPeer`; the mutation returns post-removal reachability under the table lock and the same predicate as `Snapshot.ReachableIdentitiesWithTransit`. A witnessed transit
final-route loss is observed by the snapshot comparison. The serialized `presenceProjection` records whether each previously reachable identity had direct and/or transit sources. Direct teardown removes its source under the same lock that serializes snapshot capture; lifecycle consumes the entire transition only when it actually publishes a confirmed final EOF, while an ambiguous direct close leaves any transit source snapshot-owned. Thus ownership is independent of whether direct and transit losses are captured in one snapshot generation or two, and no cross-goroutine dedup marker is needed. Both paths queue
`trustStore.recordLastOnlineAt` through `Service.goBackground` exactly once and
then publish `identity.presence.changed` as a best-effort notification. The
event carries the observing node identity as `Source`; desktop consumers on a
shared bus filter by it. No filesystem I/O runs under a routing lock, and only
the snapshot-reason route subscriber writes `ReachableIDs`.

#### Cluster-mesh Phase 2 — `routing.Table.mu` ownership of `RouteHealthState`

Phase 2 of the cluster-mesh plan (separate from the Service-mutex
Phase 2 above — names collide by accident; wire-protocol contract
lives in `docs/protocol/route_health.md`, ranking contract in
`docs/routing.md` "Route health and composite scoring") introduces
a new per-`(Identity, Uplink)` quality-signal layer:
`RouteHealthState` (Good→Questionable→Bad→Dead state machine),
per-pair RTT EWMA, and the `CompositeScore` ranking function. The
locking ownership decision is enforced as follows:

- `healthStore` lives **inside `routing.Table`** as a leaf data structure (no own mutex). `t.mu` protects it, exactly the same way it already protects `store` and `flap`. A Lookup-path can therefore read uplinks, RTT, and health under a single `t.mu.RLock()` without cross-mutex coordination — this matters because `sync.RWMutex` in Go gives writer priority (a queued writer blocks all new readers), so a "cross-mutex snapshot" pattern would risk deadlocks under load.
- Writer methods that touch health (`MarkHopAck`, `MarkProbeAck`, `MarkProbeFailure`, `TickHealth` — landing in PR 11.2 / 11.3 / 11.4) acquire `t.mu.Lock()` in W mode. They must not perform any blocking I/O (socket write, disk write, peer-callback) while holding the lock — the canonical protocol is "take t.mu, mutate, release, then optionally call `sendFrameViaNetwork[Sync]` outside the lock".
- The `fetchRouteHealth` AND `fetchRouteLookup` RPC handlers (in `internal/core/rpc/routing_commands.go`) call `RoutingProvider.HealthSnapshot()` synchronously per request. That call lands in `routing.Table.HealthSnapshot`, which takes `t.mu.RLock()`, deep-copies every `RouteHealthState` via `healthStore.snapshotLocked`, releases the lock, and returns the value slice. `fetchRouteLookup` joined this path when `Snapshot.Health` was narrowed to the `{Dead ∪ cooled}` routing-relevant subset (its CompositeScore ranking needs the full per-pair tiers); it gates the call on the target having at least one live route, so a lookup miss takes no health lock. Each such RPC invocation therefore briefly grabs `t.mu` in R mode — there is currently NO `atomic.Pointer[healthSnapshot]` cache between RPC and storage. The lock window is one full walk + deep copy of the health store — O(total tracked `(Identity, Uplink)` pairs), which scales with the whole routing table (hundreds of thousands of pairs on a dense node, NOT bounded by the direct-peer count). It runs under R mode so it does not block other readers, but `fetchRouteLookup` now rides this same path on a hit, so a high rate of these diagnostics is real copy/lock pressure (`fetchRouteLookup` gates on a live route to skip misses). Writer paths that need an exclusive lock (`MarkHopAck`, `MarkProbeAck`, `TickHealth`, `UpdateRoute`'s health bookkeeping) compete with concurrent `fetchRouteHealth` calls as they would with any other reader, but Go's `sync.RWMutex` writer-preference still applies so a queued writer blocks new RPC reads.
- Eviction in storage drives health cleanup, at the removal chokepoints. `routeStore.onClaimDropped` (wired to `healthStore.evictUplinkLocked` in `NewTable`) fires under the same `t.mu.Lock()` for every claim that physically leaves storage: in-place cap displacement in `AdmitNew` / `AdmitDirect` and TTL compaction in `CompactExpired`. There is no separate reconcile pass — the previous one ran only when `CompactExpired` removed something, so a cap replacement whose winner kept refreshing its TTL leaked one health entry per displaced uplink indefinitely (28 510 health entries against 3 585 claims on a five-day relay). `RemoveDirectPeer` and `InvalidateTransitRoutes` additionally evict eagerly on tombstoning. `WithdrawRoute` / `InvalidateUplinkClaim` do NOT: the withdrawn claim becomes a tombstone (`Hops=HopsInfinity`, `Withdrawn=true`) and its health entry is dropped when `CompactExpired` removes the tombstone. `Lookup` filters withdrawn claims before health is consulted, so a health entry behind a tombstone never influences ranking, and it is bounded 1:1 by the tombstone it shadows. The invariant is `health keys ⊆ storage keys`; `Table.Usage` publishes `route_health_orphans` (a saturation gauge, O(N_health) walk under `t.mu.RLock`) so a running node can prove it holds. There is no separate health-only TTL.
- Probe and query send paths (PR 11.3 / 11.4) prepare their target lists under `t.mu.RLock()` (snapshot of Questionable pairs / target identity), release the lock, then iterate the snapshot calling `sendFrameViaNetwork`. Holding `t.mu` across the wire send would couple routing-state critical sections to socket I/O latency — explicitly forbidden.

#### Cluster-mesh Phase 3 — `routing.Table.mu` ownership of reputation fields

Phase 3 of the cluster-mesh plan (see `docs/cluster-mesh/phase-3-multipath-reputation.md` for the full working document, ranking contract update in `docs/routing.md` "Route health and composite scoring") extends the per-`(Identity, Uplink)` quality-signal layer with hop-ack reputation: `HopAckAttempts`, `HopAckSuccesses`, `ReliabilityScore` (EWMA of binary outcomes), `ConsecutiveFailures`, and `CooldownUntil` (black-hole arm). The decision to keep these fields under the same `routing.Table.t.mu` as the Phase 2 `RouteHealthState` is documented in §2.5 of the Phase 3 working document and enforced as follows:

- The reputation fields are **embedded directly in `RouteHealthState`**, not stored in a parallel `reputationStore` with its own mutex. The Lookup path reads `(uplinks, health, RTT, reputation)` atomically under one `t.mu.RLock()`; a cross-mutex coordination would have re-introduced the writer-priority pitfall already navigated by Phase 2 (a queued writer on a sibling mutex would have blocked Lookup readers, defeating the bounded-latency goal).
- Writer methods that touch reputation (PR 12.2 will land `Table.MarkHopAck` extension and the new `Table.MarkHopFailure`; PR 12.4 hooks `applyCooldownExpiryLocked` into `Table.TickHealth`) acquire `t.mu.Lock()` in W mode. Like Phase 2, they must not perform any blocking I/O while holding the lock — multi-path failover (PR 12.3) snapshots the ranked uplink set under `t.mu.RLock()`, releases the lock, then calls `sendFrameToAddressVia` / `sendRelayMessage` outside the critical section.
- The `fetchRouteReputation` RPC handler (PR 12.7, in `internal/core/rpc/routing_commands.go`) mirrors `fetchRouteHealth`: `t.mu.RLock()` + deep copy through `Table.ReputationSnapshot`, no `atomic.Pointer` cache. The cost stays O(N) where N is the number of tracked pairs (≤24 per identity in densely-connected meshes); promotion to a snapshot pointer is deferred until field telemetry shows contention.
- Eviction follows the Phase 2 contract verbatim: reputation fields live inside `RouteHealthState`, so the same `evictUplinkLocked` that drops a health entry also drops its reputation counters. Reputation is not persisted across restart (Phase 3 §4.9 decision #6) — process wipe = cold-start warmup for every uplink.

### Migration strategy

The split is implemented domain-by-domain, starting from the least-coupled domain. Each step is a self-contained commit:

1. `fileMu` — smallest surface, easiest to verify. **[done]**
2. `ipStateMu` — isolated from delivery paths. **[done]**
3. `knowledgeMu` — writes only during handshake. **[done]**
4. `gossipMu` — covers the `fetch_messages` reader path, cleanly bounded. **[done]**
5. `deliveryMu` — covers the relay / outbound queues. **[done]**
6. `peerMu` — largest domain; folded `statusMu` into the same commit. **[done]**
7. `statusMu` — folded in with `peerMu` (aggregate status is derived from peer + delivery state). **[done]**

Phase 2 is complete. The legacy `s.mu` field no longer exists on `Service`; every `*Locked` helper's doc-comment names exactly which domain mutex (or mutexes, in canonical order) the caller must hold. A reader must not assume any prior-era default; consult the helper's doc-comment.

### Testing contract

Every migration step must keep the existing node test suite green. Targeted regression tests from Phase 1 (reader-starvation reproducers in `*_starvation_test.go`) are re-run after every step to confirm the no-starvation property is preserved or improved.

### Мотивация

`node.Service` исторически защищал всё in-memory состояние единым `sync.RWMutex` (`s.mu`). Этот мьютекс покрывал как минимум семь разных доменов — peer-подключения, очереди доставки сообщений, криптографическое «знание», gossip-топики, IP-политики, файловый трансфер и агрегированный статус. `sync.RWMutex` в Go отдаёт приоритет писателям: один поставленный в очередь writer блокирует всех новых readers до тех пор, пока не завершатся уже активные readers. Любая запись в любой домен сериализовала чтения во всех остальных.

Под штормом переподключений это давало класс багов reader-starvation: `fetch_network_stats`, `fetch_peer_health`, `get_peers` и другие read-mostly RPC стояли 10–15 с пока дренировалась очередь peer-management writers.

Фаза 1 решила проблему горячих read-путей через atomic snapshots вне `s.mu`. Фаза 2 атакует корень: сам мьютекс. Поля `Service` естественно раскладываются по семи независимым доменам — запись в один домен не должна блокировать чтения в другом.

### Карта доменных мьютексов

Каждое поле, ранее защищённое `s.mu`, переезжает ровно в один из мьютексов ниже. Все мьютексы — `sync.RWMutex`; read-dominated домены выигрывают от split RWMutex, и единообразная форма упрощает ревью.

Таблица полей — см. английскую секцию выше.

**Штрафные записи ключуются `penaltySubject`, а не названной identity.** `peerQuarantine`, `peerDisconnectHistory`, `peerAnnounceHistory` и `lastResyncAccepted` (все под `peerMu`), корзины `announceLimiter` и записи hop в `nonDMKeySync` ключуются `penaltySubject` (`penalty_subject.go`): identity — только если её доказала v2-сессия на этом соединении, иначе — адрес, который набрал этот узел, TCP-IP источника или само соединение для loopback. Вычисление субъекта не добавляет рёбер блокировок. Для исходящей сессии это `peerSession.penaltySubject()` по полям, записанным в литерале структуры (`address`, `proven`) и больше не переписываемым, — блокировка не нужна. Для принятого соединения — `penaltySubjectOfCore`, который читает только собственное синхронизированное состояние NetCore (`Auth()`, `RemoteAddr()`); поэтому `trackInboundDisconnectWithPresenceEvidence` вычисляет его из уже полученного core, не входя в `peerMu` повторно. `connPenaltySubject` берёт `peerMu.RLock` через `netCoreForID` и вызывается только диспетчером приёма, вне всех доменных мьютексов. Путь закрытия получает субъект закрывающейся сессии параметром (`onPeerSessionClosedWithAttribution`), поэтому `maybeArmRouteQuarantineOnCloseLocked` начисляет его в той же секции `peerMu`, что и раньше. Транзитный гейт (`isPeerTransitQuarantinedLocked`) читает только запись доказанной identity под той же блокировкой, что и раньше. См. `docs/protocol/network_security.md` §13.

**Legacy-заявки identity, которой нужен v2** (`v2_identity_claims.go`). `identityRequiresV2` читает pin-хранилище под его листовым `mu`, а затем отдельно берёт `peerMu.RLock`, чтобы найти живое v2-соединение (`identityHasProvenConnection`); вместе они не удерживаются никогда, а вызывающий не держит доменных мьютексов — вызовы идут из обработчиков приёма, `refuseLegacyIdentity` (hello, welcome, повторная проверка в `auth_session` и исходящая повторная проверка сразу после регистрации legacy-сессии), `ReactionsSupportOf` (до того, как он сам берёт `peerMu.RLock`) и путей hop-ack. `onIdentityProvenV2` выполняется в `openInboundTransport` / `provenTransport` после записи pin и ДО регистрации v2-соединения, без доменных мьютексов: `closeLegacyClaimsOf` снимает снапшот legacy-соединений с этой identity под `peerMu.RLock`, освобождает его и только потом закрывает их (закрытие проходит через собственный читатель соединения, который берёт `peerMu`); затем `unprovenRouting.waitDrained` ждёт — не держа никаких мьютексов, — пока каждый legacy-обработчик маршрутного входа этой identity, допущенный до pin, не закончит запись; и только после этого `forgetUnprovenRoutingResidue` вызывает `routing.Table.ForgetUplink` (только `t.mu`) и реестр анонсов, не удерживая доменных мьютексов. Обработчик допускается через `admitRoutingInput`, который учитывает его (`enter`) ДО повторного чтения `identityRequiresV2`: либо обработчик видит pin и отказывается, либо доказательство видит учтённый обработчик и ждёт его — окна «проверка прошла, запись легла после очистки» нет. Учтённый обработчик не держит доменных мьютексов, а его запись берёт только собственный лок таблицы маршрутов, поэтому ожидание цикла не замыкает. Если контекст вызывающего закончился раньше (таймаут dial, а не только остановка узла), очистка не теряется: `owePurge` передаёт её последнему выполняющемуся обработчику, чей `release` (`releaseRoutingInput`) вызывает `forgetUnprovenRoutingResidue`, оставаясь учтённым как выполняющийся, — поэтому доказательство, ждущее в это время, просыпается после неё, — а отменённое доказательство завершается ошибкой, и его соединение не регистрируется. Поэтому `release` вызывается без доменных мьютексов: каждый обработчик отпускает допуск после записи и вне своих локов, а колбэк таймера hop-ack выполняется после освобождения `rs.mu`. `unprovenRouting` (`unprovenRoutingWriters`) владеет листовым мьютексом вне доменной схемы — см. ниже.

Вне схемы остаются:

- `listener` — пишется один раз в `Run` до `Accept`. Существующая дисциплина «один writer» сохраняется.
- `done`, `connWg`, `backgroundWg`, `peerActivityNanos`, `trafficMu` / `lastTrafficSnap`, `*Snap` atomic pointers — уже имеют собственную синхронизацию (chan, WaitGroup, `sync.Mutex`, `atomic.Pointer`). Не входят в доменное разделение.
- `backgroundMu` (`sync.Mutex`) / `backgroundClosed` (`service.go`) — ВОРОТА ДОПУСКА перед `backgroundWg`. Вне семидоменного разделения, с собственной синхронизацией: `backgroundMu` — leaf, охраняет только `backgroundClosed` и упорядочивает `backgroundWg.Add`, который `goBackground` делает под ним; никакой другой мьютекс под ним не берётся, через I/O и callback он не удерживается, поэтому рёбер в канонический порядок не добавляет. `goBackground` проверяет флаг и делает `Add(1)` в одной критической секции и сообщает, принята ли задача; `Run` взводит флаг в САМОМ ПЕРВОМ зарегистрированном defer, то есть он выполняется ПОСЛЕДНИМ — после дренажа входящих соединений, после того как `stopRunLifecycle` дождался всех циклов жизненного цикла и горутин исходящих сессий, после остановки подсистем и `close(s.done)`. Работа, которую ставит сам teardown, поэтому ещё принимается и дожидается `WaitBackground`; работа, запрошенная после возврата из `Run`, отклоняется и не стартует. Именно это не даёт `WaitBackground` — его вызывают после `Run`, прямо перед закрытием хранилищ и удалением каталога данных — гоняться с `Add`, поднимающим счётчик с нуля (неправильное использование `WaitGroup`, о котором сообщает race detector), и не пускает квитанции, дозвоны key-sync и записи trust store на остановленный узел. `WaitBackground` ворота НЕ закрывает: unit-тесты используют его как барьер на Service, у которого `Run` не вызывался, и после него продолжают ставить работу. Отказ логируется на debug с местом вызова; три вызывающих, которые что-то держат под задачу, его обрабатывают: `runSenderKeySyncPass` сам возвращает in-flight слот (`release`), `triggerRouteQueryAsync` освобождает in-flight слот цели (`releaseInFlight`), `tryEnqueueGossipJob` возвращает `gossipPoolShutdownDrop`. Остальные — fire-and-forget на окончательно остановленном узле: отказ для них равен выходу процесса. **Для продолжений исключения нет:** задача, принятая до возврата из `Run` и запросившая продолжение уже после, — `pushBacklogToSubscriber` → `goBackground(confirmEnvelopesDurably)`, `writePushFrame` → `confirmEnvelopeOnWire` → долговременное подтверждение в `goBackground`, — отклоняется как любая другая. Её последствия такие же, как у краша в этот момент (конверт остаётся неподтверждённым на диске), и восстанавливается она так же, как после краша: ретраями доставки на стороне отправителя и долговременными журналами при следующем старте. Лог отказа: `background_job_refused_after_run_returned` на debug, с полями `node`, `op` (`goBackgroundOp` называет операцию; `goBackground` пишет `unnamed`) и `caller`. Закреплено `TestBackgroundJobIsRefusedOnceRunHasReturned`, `TestBackgroundJobIsAdmittedWhenRunWasNeverCalled`, `TestARefusedSenderKeySyncPassReturnsItsSlotExactlyOnce`, `TestTheGossipFallbackDropsAJobOnceRunHasReturned`, `TestARefusedRouteQueryReleasesItsInFlightSlot` и `TestRunServiceForTestDrainReportsUnfinishedBackgroundAsError`. У `WaitBackground` есть предусловие: `Run` не выполняется — после возврата из `Run` ни одна задача не может быть принята, а на Service, у которого `Run` не вызывался, вызывающий сам владеет каждой горутиной, ставящей работу.
- **`Run` не присваивает ни одного поля, которое может прочитать вызывающий Service.** Приложение запускает RPC-сервер и сборщик метрик ДО вызова `Run` (`internal/app/node/app.go`), а desktop- и SDK-рантаймы отдают Service интерфейсу, пока `Run` стартует в собственной горутине, поэтому любой обработчик локальных фреймов и любой метод RPC-провайдера может выполняться одновременно со стартом `Run`. Обычное поле, присвоенное там, публикуется этим читателям без ребра happens-before — это гонка данных, а не деталь порядка старта, и ожидание `connManager.Ready()` лишь прячет её от тех, кто знает, что ждать надо. Значение, нужное таким читателям, строится в `NewService`; значение, которое может построить только `Run`, публикуется атомарной записью, которую читатели загружают первой. Поля под этим правилом:
  - `runCtx` / `runCancel` — контекст жизненного цикла Service и его отмена; создаются в `NewService` (`context.WithCancel(context.Background())`) и после этого иммутабельны; `context.Context` безопасен для конкурентного использования, поэтому чтение идёт без мьютекса. `Run` его не заменяет: он заставляет его СЛЕДОВАТЬ за контекстом вызывающего (`context.AfterFunc(ctx, runCancel)`) и отменяет его на любом выходе, причём страхующий `defer` регистрируется до первого `return`. Два следствия — намеренные: работа, захватившая `runCtx` ДО `Run` (например, горутина восстановления sender-key), всё равно завершается демонтажом `Run`, тогда как прежнее присваивание в `Run` оставляло её на контексте, который никто бы не отменил; дедлайн и значения контекста вызывающего не переносятся — переносится только отмена. `Run` одноразовый (закрывает `done`), так что отменённый `runCtx` после возврата `Run` — окончательное состояние. Закреплено тестами `TestTheLifecycleContextTakenBeforeRunEndsWithRun` и `TestReadingTheLifecycleContextDuringRunStartupIsNotADataRace`.
  - `captureManager` — строится в `NewService` (`newCaptureManager`, привязан к `runCtx`), после этого иммутабелен и синхронизирован собственным мьютексом `capture.Manager`, поэтому читатели (RPC захвата трафика, `peerHealthFrames` за `fetch_peer_health`, тапы соединений) не берут доменных мьютексов. `Run` владеет только его остановкой (`defer s.captureManager.Close()`). Он существует до `Run`, так что RPC захвата, обслуженный до `Run`, попадает в тот же менеджер, а не получает отказ; `nil` остаётся только в Service-литералах тестов, поэтому проверки на nil сохранены. Закреплено тестами `TestTheCaptureManagerExistsBeforeRun` и `TestCaptureRPCDuringRunStartupIsNotADataRace`.
  - `gossipJobs` / `gossipNoticeJobs` — единственное исключение, которое по-прежнему присваивается в `Run` (`startGossipDispatch`), потому что тесты пула запускают его напрямую на Service-литералах. Каналы ПУБЛИКУЮТСЯ записью `gossipPoolUp.Store(true)`, идущей после присваивания, и диспетчер читает канал только после того, как `gossipPoolUp.Load()` вернул true: `tryEnqueueGossipJob` принимает АДРЕС поля и разыменовывает его за этой загрузкой. Чтение поля в месте вызова — прежняя форма — гонялось с `Run` даже у тех, кто ждёт `connManager.Ready()`, потому что пул стартует после него. Закреплено тестом `TestGossipDispatchDuringRunStartupIsNotADataRace`.
  - Присваивания в `Run`, которые остаются безопасными, и почему: `listener` (под `peerMu`), `relayStates.onHopAckTimeout` (пишется до `relayStates.start()`, чей оператор `go` и есть ребро к единственному читателю — TTL-тикеру), дескрипторы файл-трансфера (под `fileMu`). Новое присваивание в `Run` обязано назвать здесь своё ребро в том же коммите.
- `unattributedNonDMDrops` — счётчик `atomic.Uint64` не-DM-пушей, отвергнутых из-за неизвестного ключа автора (`refuseUnattributedNonDM`). Собственная синхронизация, только наблюдаемость.
- `nonDMKeySyncPasses`, `nonDMKeySyncSkipped` — счётчики `atomic.Uint64` бюджета синхронизации ключей для не-DM (`nondm_key_sync.go`). Собственная синхронизация, только наблюдаемость.
- `trustedKeysAtLoad` — что `NewService` сделал с ключами trust store (`classifyContactKeys`: отвергнутые контакты, отброшенные box-пары). Записывается один раз в `NewService`, затем иммутабелен; lock не нужен.
- `inboundClosed` — домен пиров (`peerMu`): выставляется `closeAllInboundConns` при остановке и не сбрасывается; после этого `registerInboundConn` отказывает, поэтому соединение, которое во время закрытия было между первым байтом и регистрацией, не зарегистрируется незамеченным и не задержит `connWg`. `inboundBeforeRegister` — тестовая точка между рукопожатием сессии и регистрацией; задаётся только до `Run`, потом неизменна.
- **Три однонаправленных флага остановки, в том порядке, в каком их взводит teardown `Run`** (все одноразовые, как и сам `Run`): первым `inboundClosed` (`peerMu`) — `closeAllInboundConns` в дренаже входящих; после него ни одно соединение не регистрируется, и `connWg.Wait` ждёт закрытый набор; затем `withdrawalsShutDown` (`peerMu`) — `cancelAllPendingWithdrawalsForShutdown` после дренажа и до join жизненного цикла; после него не взводится ни один таймер отзыва маршрута и не выполняется ни одно тело отзыва; и последним `backgroundClosed` (`backgroundMu`) — первый зарегистрированный defer, после join и остановки всех подсистем; после него не принимается ни одна fire-and-forget задача, и `WaitBackground` ждёт закрытый набор. Каждый отклоняет своего производителя; ни один не берётся под другим, а два флага под `peerMu` пишутся в отдельных критических секциях.
- `secureSessions` — состояние сессии v2 (`session_secure.go`): задаётся один раз в `NewService` и не заменяется. Режим, `sessionv2.Local` и источник сертификата иммутабельны или синхронизируются сами; отметки адресов (`sessionAddressMarks`) владеют листовым мьютексом, под которым ничего не вызывается и доменные мьютексы не берутся. У хранилища защиты от понижения (`secureSessionStore`, `secure_session_store.go`) листовой `mu` для карт (и счётчика отказов `pin_store_full`; `SecureSessionStoreStats`, который читает безблокировочный `fetchRouteSummary`, берёт только этот лист) и отдельный `writeMu`, который упорядочивает запись на диск и держится БЕЗ `mu`: снимок берётся под `mu`, файл пишется после его освобождения, и доменные мьютексы не держатся ни там, ни там. Рукопожатие v2 идёт в `handleConn` и во всех путях дозвона (`openPeerSessionForCM`, `syncPeer`, `sendNoticeToPeer`) ДО регистрации соединения, поэтому не держит доменных мьютексов и не трогает доменное состояние.
- `unprovenRouting` — отметки identity, для которых legacy-соединение записало маршрутный вход, и счётчик legacy-обработчиков маршрутного входа в работе по каждой identity (`v2_identity_claims.go`); отметка расходуется, когда identity доказывает себя по v2, а доказательство ждёт обнуления счётчика. Собственный листовой мьютекс: его трогает каждый маршрутный кадр legacy-соединения на пути приёма, где `peerMu` — самый горячий лок; под ним ничего не вызывается и другие мьютексы не берутся, а ожидающие блокируются на канале ПОСЛЕ его освобождения. Ограничен (4096) БЕЗ вытеснения: отметка не теряется до своего TTL, потому что потерянная отметка означала бы «legacy-остатка нет», когда он есть; при заполнении каждое доказательство на один TTL переключается в режим очистки. Выметается по TTL тиком обслуживания. Закрытие сессии, не доказавшей свою identity, тоже оставляет отметку: закрытие пишет историю флапов и отзыв от имени этой identity.
- `nonDMKeySync` — состояние допуска проходов синхронизации ключей для не-DM. Под `senderKeySyncMu` — тем же листовым мьютексом, что и карты DM-восстановления (`senderKeySyncInFlight`, `senderKeySyncHopInFlight`, `senderKeySyncLastRun`); под ним ничего не вызывается и другие доменные мьютексы не берутся.
- `presenceClock` — один раз задаётся в `NewService` и после этого иммутабелен; он ставит timestamp как direct EOF-наблюдения до withdrawal grace, так и transit-наблюдения при snapshot rebuild. Тесты заменяют его до запуска lifecycle-работы. Lock не нужен.
- `presenceProjection` — leaf-мьютекс и предыдущая карта reachability/`hasTransit`, используемые только для ownership last-online. Snapshot capture берёт `presenceProjection.mu → routing.Table.t.mu` и удерживает leaf-lock на всём эксклюзивном билде `SnapshotIncremental`, одном совмещённом проходе reachability/source-classification и atomic store кэша. Direct teardown берёт `peerMu → presenceProjection.mu → routing.Table.t.mu`; следовательно, teardown в очереди за snapshot capture удерживает `peerMu` всё время ожидания и временно останавливает весь peer-домен. Для самого table build эта зависимость существовала и раньше, но presence-слой не должен удлинять её повторными проходами routes/health. Event publication, persistence и filesystem I/O выполняются после освобождения.
- `presencePublishMu` — мьютекс, сериализующий один проход presence с его публикацией. К `refreshPresenceSnapshot` приходят три писателя: цикл presence, обновлятор маршрутного снапшота (до публикации `TopicRouteTableChanged`, чтобы подписчик не прочитал поколение presence старше маршрутного изменения, которое его разбудило) и каждое событие liveness. Сравнение с предыдущим поколением, решающее, публиковать ли `TopicContactPresenceUpdated` и кто считается вернувшимся для будильника доставки, осмысленно только под одним локом.

  **Это САМЫЙ ВНЕШНИЙ мьютекс, а не leaf, и прошлая редакция этого документа утверждала обратное.** Проход собирает входные данные, УДЕРЖИВАЯ его, а эти данные лежат почти по всему узлу: `presenceLocalConnectivity` → `AggregateStatus` (`statusMu`), `presenceContacts` → собственный мьютекс trust-стора, `presenceRouteStateFor` → `routing.Table`, `presenceContactIsProbeable` → trust-стор, `Reachable` планировщика датаграмм и, при промахе, `startPresenceIdentityResolution`. Будильники в конце добавляют `deliveryMu` дважды (`kickDeliveryRetriesForReachable`, `wakeOverdueForPresenceReturn`). Контракт состоит из двух половин, а записана была только первая:

  1. **Входить, не удерживая ни одного доменного мьютекса.** Все нынешние call site-ы так и делают — поэтому готового дедлока сегодня нет, — но гарантию давали call site-ы, а не лок, и четвёртый вызывающий, пришедший в `refreshPresenceSnapshot` из-под `peerMu` или `deliveryMu`, унаследовал бы инверсию, которую документ объявил невозможной.
  2. **Под ним доменные мьютексы берутся ПО ОДНОМУ и в каноническом порядке**, каждый освобождается до захвата следующего. Двух одновременно здесь не держит никто, поэтому новых рёбер между доменами проход не добавляет; он добавляет ребро от `presencePublishMu` ко всем ним — и именно поэтому его нельзя брать, удерживая любой из них.

  Собственный мьютекс проектора остаётся листом под всем этим по причине из его пункта: `project` собирает внешние ответы до захвата лока.

  `sessionTransitionSeq` перечислен выше под `peerMu` — это счётчик, упорядочивающий закрытие сессии против реконнекта (`nextSessionTransitionLocked`). Он выдаётся внутри той же секции `peerMu`, в которой определяется переход 0 → 1 / 1 → 0, и место здесь и есть смысл: показание часов приходится снимать ДО лока, поэтому две перекрывающиеся сессии могут снять свои показания и дойти до лока в обратном порядке. Присутствие сравнивает номера переходов и никогда — показания.
- `identityResolver` — иммутабелен после `NewService`; всё мутабельное состояние движка identity lookup живёт за собственным мьютексом резолвера (`identity_resolver.go`), а его дисковый I/O (durable-таблица намерений) выполняется вне любых доменных мьютексов.
- `connBudget` (`internal/core/connbudget`) — общий потолок соединений, **leaf по построению**, а не
  по договорённости: внутри пакета нет ни одного вызова наружу, поэтому под его мьютексом нельзя
  взять никакой другой. Именно это позволяет обращаться к нему **с обеих сторон** границы, которую
  канонический порядок пересекать запрещает: `ConnectionManager` берёт его под `cm.mu`, резервируя
  ёмкость под дозвон, а `registerInboundConn` — под `peerMu`, допуская сокет. Друг до друга они не
  дотягиваются, поэтому запрещённое ребро `cm.mu → peerMu` не возникает. Оба берут его ПОСЛЕДНИМ;
  под ним не берётся ничего.

  Этот leaf — единственный lock, который берётся под `cm.mu`. Всё остальное выполняется с
  отпущенным `cm.mu`, на событийном цикле: каждая публикация состояния слота в ebus (синхронный
  подписчик может читать таблицу слотов), закрытие выселенной сессии (`tearDownSession` — закрытие
  это I/O, а `onClose` сессии берёт `peerMu`), оценка жертвы выселения под `add_peer`
  (`slotScoresForEviction` — `PeerProvider.Score` читает здоровье пира под `peerMu`), чтение лимита
  слотов (`MaxSlotsFn`), проверка бана по провалам setup, чтение пина и каждый другой callback
  `ConnectionManagerConfig`.

  Возвращаемая резервация намеренно является значением, которое можно **передать**, а не счётчиком,
  который кто-то обязан не забыть уменьшить: исходящая единица едет вместе с попыткой дозвона, а
  если её слот исчез посреди дозвона — паркуется в `ConnectionManager.orphanReservations` по
  поколению попытки, потому что удаление слота **не отменяет** дозвон, и сокет, который он ещё может
  открыть, обязан оставаться учтённым. Освобождение идемпотентно, поэтому несколько возможных концов
  попытки — отказ, остановка узла, поздний успех, закрывающий устаревший сокет — не могут освободить
  одну единицу дважды и раздуть потолок.

- `identityFileMu` — leaf-мьютекс, сериализующий пару локальных RPC `identity_backup` / `identity_restore`: обе гонят секреты через один предсказуемый `<path>.tmp` (`identity.Save`, `writeSecretFile`), и два конкурентных вызова могли бы перемешать write-then-rename — или удалить чужой temp — и подтвердить содержимое, которое записал другой вызов. Резолв имени в путь (`resolveIdentityBackupPath`) выполняется ВНУТРИ той же секции, а не до неё: его проверка на symlink — это проверка того, что лежит там прямо сейчас, и проверка вне лока, охраняющего запись, — не проверка, а TOCTOU-окно. Держится только внутри двух frame-хендлеров вокруг файлового I/O; доменных мьютексов не берёт, доменные его не берут, ребра в канонический порядок не добавляет.
- Два snapshot-персистируемых стора (`trustStore`, `identityIntentStore`) делят одну дисциплину записи: мутатор берёт собственный state-мьютекс стора, продвигает **счётчик поколений снапшота**, копирует состояние и отпускает мьютекс ДО любого дискового I/O. Сама запись идёт под выделенным `saveMu` стора (они делят один `.tmp`-путь), и снапшот с поколением ≤ последнего персистированного отбрасывается — два мутатора могут добежать до диска в любом порядке, и что лежит в файле, решает поколение, а не удача планировщика. `saveMu` никогда не берётся при удерживаемом state-мьютексе, и ни один доменный мьютекс рядом с этими локами не участвует. Кэш session-record'ов trust store (`sessionRecordCache`, trust_session_records.go) — лист под тем же state-мьютексом: запись не-контакта мержится под `trustStore.mu` и до `saveMu` не доходит вовсе — ни снапшота, ни записи на диск, — что и убирает push от каждого нового пира сессии с I/O-пути; TTL-подметание идёт из bootstrap-цикла только под state-мьютексом. Живое множество кэша — адреса, чей seq-floor обязан пережить TTL и бюджет, — живёт в `recordProtection` (record_protection.go), НЕ в trust store и не в множестве, которое ему периодически передают. Удержание берётся внутри критической секции, делающей его факт истинным: в `peerMu`-секции `onPeerSessionEstablished`, инкрементирующей `identitySessions`, и в `r.mu`-секции `StartResolution` / `reseedFromIntents`, вставляющей в `resolutions`; снятия — в парных секциях `onPeerSessionClosedWithAttribution` и `finishLocked`. `recordProtection.mu` — ЛИСТ, берущийся под этими доменными мьютексами (та же форма, что `seenReceipts` под `deliveryMu`), он не берёт ничего дальше, не делает I/O и никого не зовёт обратно. Кэш не читает множество, чтобы потом удалить: `sessionRecordCache.dropLocked` зовёт `recordProtection.dropIfUnprotected`, который проверяет удержания и выполняет callback удаления внутри ОДНОЙ секции `recordProtection.mu`, поэтому pin упорядочен строго до проверки или строго после удаления. Lock-free чтение с последующим удалением — форма, которую это заменило, — оставляет интерливинг, где pin попадает между ними и запись удаляется под уже живой сессией; перечитывание ответа окно сужает, но не закрывает. Вложенность, таким образом, `trustStore.mu → recordProtection.mu`, а callback трогает только состояние кэша, которым caller уже владеет под `trustStore.mu`. Lock-free `recordProtection.contains` остаётся ровно для одного вызывающего — gauge `identity_record_cache_protected`, где ответ, устаревший на мгновение, ничего не стоит. Ни одна из форм не создаёт `trust.mu → peerMu`, которое легло бы под существующие `presencePublishMu → trust.mu` и `trustMutationMu → trust.mu` и завело бы дисковый I/O intent-store'а resolver'а под state-мьютекс, из-под которого вся схема с поколениями снапшотов I/O как раз убирает. `bootstrapLoop` перед sweep'ом зовёт `reconcileRecordProtection`: тот читает поколение, пересчитывает удержания по `identitySessions` (`peerMu.RLock`) и открытым resolution'ам (собственный мьютекс resolver'а) — каждый берётся и отпускается отдельно, пока сам цикл не держит ничего, — и коммитит, только если поколение не сдвинулось, поэтому сессию, открывшуюся во время сбора, нельзя стереть счётчиками, которые её старше. Три попытки, затем проход сдаётся: то, что он поставил бы, уже поставлено событиями. Это самолечение для пропущенного удержания или двойного снятия, а не механизм.
- `messageStore`, `seenAckJournal`, `deliveryFailureJournal`, `emissionJournal` — регистрируются один раз до `Run` (RegisterMessageStore / RegisterDeliveryOutbox) и далее иммутабельны, поэтому чтения не требуют мьютекса; их SQLite I/O никогда не выполняется под доменным мьютексом. Запись failure-журнала — синхронная после освобождения локов (это durable-граница отказа от ретраев — shutdown не ждёт backgroundWg перед закрытием chatlog); MarkSeenConfirmed может идти через background-пул: его потеря стоит лишь одного избыточного идемпотентного повтора seen. К `emissionJournal` единственному ходят через собственную полосу — `emissionLane`, описанную ниже в разделе про ретраи доставки, — потому что два его писателя конкурируют за одного и того же единственного writer'а SQLite, и один из них лежит на критическом пути исходящего сообщения.
- `conversationControl` — дверь для принятых команд `dm_control` (сегодня — реакции). Регистрируется один раз до `Run` (RegisterConversationControlStore) и далее иммутабельно, ровно как `messageStore`, поэтому чтения не требуют мьютекса. Его SQLite I/O выполняется в горутине приёма датаграмм и НИ ПОД ОДНИМ доменным мьютексом: хендлер в `dm_control.go` не берёт ни одного, а с остальным узлом его связывает только регистрация типа. На стороне десктопа он приходит в `ReactionControlAdapter`, который берёт тот же lease у `removalGate`, что и `MessageStoreAdapter`: иначе факт, записанный во время стирания беседы, пережил бы её строкой, до которой не дотягивается ни один путь удаления. Собственное изменяемое состояние адаптера — одна map `reoffer` (на беседу: следующая страница, текущий интервал бэкоффа и когда периодический проход вправе её взять) за собственным `reofferMu`: её пишет и горутина приёма датаграмм, когда сессия открывает раунд, и reaper-цикл роутера на каждом проходе, и не принадлежит она ни одной из них. Этот мьютекс — лист: под ним не вызывается ничего внешнего, и берут его никогда не из-под доменного мьютекса.
- `dmControl` — исходящий отправитель команд беседы (`dm_control_send.go` — сам проход, `dm_control_outbox.go` — что стоит в очереди, `dm_control_policy.go` — во что мы верим про билд пира; три файла, ОДИН мьютекс, потому что проход читает обе половины и они не должны разъехаться посреди него). Ставится один раз в `NewService` и далее иммутабельно; всё изменяемое состояние живёт за СОБСТВЕННЫМ `sync.Mutex`, поэтому поле стоит вне схемы семи доменов так же, как `identityResolver`. Держат его там два правила.

  1. Ни один путь не входит в него, удерживая доменный мьютекс. Входов ВОСЕМЬ, и именно с этим списком сверяется новый вызывающий: `QueueReactionFacts`, `ReactionsSupportOf`, `QueuedReactionsFor`, `ForgetPeerReactions` и `HoldReactionSends` из сервисного слоя, `answerCommandUnsupported` и `noteCommandRefused` из хендлера датаграмм и `forgetDMControlRefusal` из собственных сессионных путей узла (`peer_sessions.go` и ветка входящего `auth_ok` в `service.go`). Последний единственный внутри узла — к нему проще всего дописать вызов из-под лока. `ForgetPeerReactions` и `HoldReactionSends` — БЛОКИРУЮЩИЕ входы: оба дожидаются кадров этого пира, которые уже запечатываются (см. ниже), поэтому сверх общего правила их нельзя звать из того самого пути отправки, которого они ждут, а вызывающий, который держит что-то своё, держит это ровно на время одной передачи кадра в плоскость. `HoldReactionSends` — это скобка, которой удаление ОДНОГО сообщения обрамляет себя: очередь называет реакции, а не сообщения, поэтому такого удаления она не видит, и кадр, собранный по записи мгновением раньше, иначе ушёл бы про уже стёртое сообщение. Остановленное при этом не теряется, а возвращается в очередь.
  2. Собственный мьютекс никогда не удерживается через внешние вызовы: `takeDue` освобождает его ДО `send`, поэтому поиск box-ключа, запечатывание и передача кадра в плоскость идут без лока. Новый вызывающий, приходящий сюда из-под доменного мьютекса, нарушает первое правило, и добавлять его нельзя. Его ИЗМЕНЯЕМОЕ состояние — ровно `pending`, `refusedAt`, `typeRefusalShown`, `forgot`, `inflight`, `framesOut`, `paused` и `draining`, все восемь за этим одним мьютексом, плюс `quiet` (`sync.Cond` на нём) для одного ожидания, описанного ниже. `pending` держит КЛЮЧИ, а не факты: что реакция говорит сейчас, читается из chatlog в момент сборки кадра, поэтому копии состояния, которое может удалить другой путь, здесь нет. `ForgetPeerReactions` очищает первые три по одному пиру одной секцией при удалении контакта или беседы — сразу, а не дожидаясь, пока следующий флаш обнаружит ключи устаревшими, — а дальше закрывает то, до чего карты не дотягиваются. Пакет, уже вынутый `takeDue` и отданный в `send`, в `pending` не лежит: он помечается через `inflight` на САМОМ пакете (`dmControlOutbox.abandoned` — идентичность по указателю, а не счётчик, который стал бы ABA при первом же sweep), после чего `send` не начинает следующий его кадр, а `requeue` отказывается класть остаток назад. Кадр, уже прошедший эту пометку, в этот момент запечатывается и собирается ВНЕ мьютекса, поэтому удаление ЖДЁТ на `quiet`, пока `framesOut[peer]` не станет нулём, — та же форма, что и `removalGate.begin` уровнем выше, и по той же причине: проверка это не запись. Отсюда следует, что `ForgetPeerReactions` нельзя вызывать из самого пути отправки — она его дожидается. `forgot` — третья часть и относится к тому, что говорит ПИР: ответ на кадр, отправленный до удаления, приходит после него и отклоняется в течение `dmControlForgetGrace` — окна, выведенного из самой длинной такой цепочки (остаток валидности нашего кадра на плоскости, ретраи ответа в очереди пира, обратная дорога этого ответа), и новый факт для пира его намеренно не укорачивает; записи выметаются тем же проходом, что и отказы; остальное на типе (`svc`, `clock`, `jitter`, `dispatch`) ставится до старта цикла отправки и больше не пишется, а сборщик кадров закрыт `sync.Once`. `draining` поднимает цикл `dmControlSendLoop` на время работы, читает его `canSendLocked`; вариант с atomic рядом с мьютексом был опробован и отвергнут: `stop()` обязан опустить флаг и очистить очередь ОДНИМ шагом — с флагом снаружи постановка, попавшая между этими двумя действиями, ложится в map, в который больше никто не заглянет.
- `lastPeerSave`, `lastPeerEvict`, `lastSync` — peer-lifetime timestamps; едут с `peerMu`.
- `reachableGroups` — заполняется ровно один раз функцией `computeReachableGroups` при `New` и считается иммутабельным на весь runtime `Service`. Конкурентные чтения немутировавшейся карты безопасны без lock-а, поэтому мьютекс не назначается. Если в будущем появится runtime-запись, в том же коммите необходимо добавить синхронизацию (либо перевести поле под `ipStateMu` с захватом на каждом читателе, либо дать собственную синхронизацию) — иначе writer гонится со всеми нынешними читателями.
- Семейство ТЕСТОВЫХ ШВОВ — `sendAdmissionBarrier`, `peerTeardownBarrier`, `cmSessionRegisterBarrier`, `faultDuringRunStartup`, `heartbeatIntervalOverride` — находится вне схемы как класс. Каждое из них в проде равно `nil` (или нулю), устанавливается владеющим фикстурой тестом ДО первой горутины, способной его прочитать, и после этого не меняется, то есть пишется одной горутиной без читателей и затем читается многими без писателя — та же дисциплина, что у `listener`. Они не охраняют никакого состояния `Service`, а их call site — это загрузка и ветвление, поэтому они не участвуют ни в одной кросс-доменной транзакции. Три из них дополнительно несут требование к ПОЗИЦИИ, зафиксированное у поля и повторённое там, где это важно: `sendAdmissionBarrier` и `peerTeardownBarrier` обязаны вызываться без единого доменного и без единого leaf-мьютекса, потому что обе переплетаемые ими горутины сразу после этого берут `peerMu`; `cmSessionRegisterBarrier` (горутина сессии CM, после успеха setup и до `registerCMSession`) — так же, потому что выселение, которое он впускает, берёт `peerMu` в `onCMSessionTeardown`. Шов, который когда-либо станет устанавливаемым в runtime, обязан в том же коммите переехать под мьютекс или под `atomic.Pointer`. У `ConnectionManager` есть один шов того же семейства — `ConnectionManagerConfig.RetainOnlyEnqueued` (`nil` в production; `RetainOnly` вызывает его на горутине вызывающего, как только запрос попал в очередь событий слотов). Он живёт в конфигурации, поэтому фиксируется при сборке менеджера и больше не меняется, а тесты, удерживающие событийный цикл, подключают своего наблюдателя через конфигурацию, а не устанавливают его позже.
- `startedAt` — wall-clock timestamp, фиксируется один раз в `NewService` и читается RPC-обработчиком PIP-0001 `getNodeStatus`. Иммутабельно после конструктора, поэтому читается без lock-а. Если когда-нибудь появится runtime-перезапись (например, soft-restart), поле обязано в том же коммите переехать под один из доменных мьютексов — скорее всего `statusMu`.
- `connectOnly` (`atomic.Pointer[domain.PeerAddress]`, пин исходящих к единственному пиру, который ставит команда `connectOnly` / `CORSA_CONNECT_ONLY`, `connect_only.go`) — сознательно вне семидоменного разделения: это один указатель с собственной atomic-синхронизацией. Читается без lock-а на горячем пути дозвона `PeerProvider.Candidates()` через `connectOnlyTarget` (подключён как `ConnectOnlyFn`) — по правилу «горячее чтение = atomic-снапшот, никогда не RLock», которому следуют снапшоты routing/peer-health. Писатели (`enableConnectOnly`, `disableConnectOnly`, fail-closed sentinel при старте) меняют весь указатель одним `Store`, поэтому читатель всегда видит согласованное значение, и поле не добавляет рёбер в канонический порядок захвата. `enableConnectOnly` сначала проверяет цель (`validateAddPeerTarget`, без lock-а и без записи состояния) и записывает пин только для цели, которая будет принята, поэтому неудачная команда никогда не делает свою цель живым пином и ей нечего восстанавливать; лишь ПОСЛЕ записи она зовёт `admitAddPeerTarget` (берёт `peerMu`) и `ConnectionManager.RetainOnly`, никогда под доменным мьютексом. `RetainOnly(ctx, …)` сам таблицу слотов не трогает: он ставит в очередь `retainOnlyRequest` и ждёт, пока событийный цикл CM — единственный писатель таблицы слотов — применит правило пина (выселит остальные слоты, опубликует их удаление, закроет их сессии и выполнит их `OnSessionTeardown`), либо пока не закончится `ctx` или контекст цикла; `false` означает «не подтверждено», в том числе когда цикл не запущен. Правило level-triggered и применяется к ЖИВОМУ пину, который цикл читает через `ConnectionManagerConfig.ConnectOnlyFn` (тот же lock-free `connectOnlyTarget`): пока пин жив, в таблице слотов есть только живой пин. Его запрашивает каждая запись непустого пина — `enableConnectOnly` и fail-closed sentinel при старте, — каждый `fill` применяет его заново ДО сжатия до лимита слотов (так что падение лимита не может выселить ещё дозванивающийся слот пина), удержание, оставившее живой пин без слота, сразу запускает заполнение, а `handleManualPeer` не дозванивается ни до кого, кроме живого пина (ответ `add_peer` говорит об этом, `CodeAddPeerNotDialledConnectOnly`). Раз он ждёт цикл, вызывающий `RetainOnly` НЕ должен держать ни доменный мьютекс, ни `PeerProvider.mu`, ни `cm.mu`, и не должен звать его с событийного цикла (из callback'а CM): цикл берёт всё это, обрабатывая события, стоящие в очереди перед запросом, так что ожидание под любым из них — deadlock. Оба вызывающих этому удовлетворяют — `connectOnlyFrame` на горутине RPC / консоли (с контекстом запроса) и `applyStartupConnectOnly` на горутине `Run` (с контекстом `Run`), ни один не держит lock через `enableConnectOnly`.
- `connectOnlyResolver` (`*net.Resolver`, `connect_only.go`) — резолвер для цели connect_only, заданной DNS-именем. Устанавливается в `net.DefaultResolver` в `NewService`; тест может заменить его после `NewService` и до первого использования Service (дисциплина `networkOverride`), и больше его никто не пишет, поэтому после запуска Service он иммутабелен и не входит ни в один домен; `resolveConnectOnlyHost` читает его без lock-а и резолвит вне любых доменных мьютексов.
- `transportTotals` (`netcore.TransportTotals`, общеузловые счётчики транспортных байтов за `fetch_traffic_totals.transport`, `transport_traffic.go`) — сознательно вне семидоменного разделения. Хранится ПО ЗНАЧЕНИЮ и никогда не заменяется; два счётчика внутри — `atomic.Uint64`, увеличиваются только `netcore.MeteredConn.Read` / `Write` на I/O-горутинах каждого peer-сокета и читаются `TransportTrafficStats` без какого-либо lock-а. Доменный мьютекс на этом пути сериализовал бы весь сокетный I/O узла ради статистики, а в кросс-доменных транзакциях счётчики не участвуют: ни одно решение не читает их вместе с доменным состоянием. Нулевое значение рабочее, поэтому struct-literal фикстуры `Service` считают корректно без шага конструктора. Период начинается в `startedAt`, на диск не пишется. Если когда-нибудь появится сброс в рантайме, поле обязано в том же коммите переехать за `atomic.Pointer` (новый период = новое значение с новым началом) — сброс atomic-ов на месте позволил бы читателю сложить старое начало с новыми счётчиками.
- `datagramMetrics` — набор счётчиков плоскости датаграмм (`internal/core/datagram.Metrics`), назначается один раз в `NewService` и никогда не заменяется; за указателем стоят `atomic.Uint64`, то есть тип синхронизирован сам. Брать доменный мьютекс ради инкремента счётчика на приёмном пути значило бы завести всю плоскость датаграмм под `peerMu` без единой выгоды, а в кросс-доменных транзакциях метрика не участвует. Все методы nil-safe, поэтому struct-literal фикстуры `Service` в тестах видят no-op счётчик, а не панику. Если поле станет заменяемым в рантайме (например, RPC сброса метрик), в том же коммите оно обязано переехать в `atomic.Pointer` либо под `statusMu`.
- `datagramPlane` (`atomic.Pointer[datagramLayer]`) — собранная плоскость транспорта датаграмм (строгий конвейер §4.1 спеки, планировщик маршрута §4.4, лимиты и очереди §5; `datagram_layer.go`, читается через аксессор `datagramLayer()`) — сознательно вне семидоменного разделения, на тех же основаниях, что и `datagramMetrics`. `nil` — это и есть фиче-флаг (`CORSA_ENABLE_DATAGRAM_V1` выключен), поэтому любой читатель отделён от додатаграммного поведения ровно одной nil-проверкой. Это АТОМАРНЫЙ УКАЗАТЕЛЬ, а не обычное поле, потому что приёмный путь читает его параллельно с единственной записью, которую делает `NewService`; **указатель пишется ровно один раз, а публикуемый им объект неизменяем** — ни одно поле опубликованного `datagramLayer` не переписывается, читатель берёт указатель один раз и работает по этому снимку всё своё решение. Пути пересборки больше нет: плоскость, которую можно было ЗАМЕНИТЬ в рантайме, существовала ради перечитывания durable-поколения загрузки за барьером восстановления, а durable-половина слоя — профильные хранилища, машина попыток, восстановление и boot-поколение — вырезана. Компоненты за указателем синхронизированы сами (мьютекс базового кэша реплея, мьютекс таблицы reverse-состояния, мьютекс взвешенной очереди, copy-on-write поколение через `atomic.Pointer` у реестра типов, `atomic.Uint64`-счётчики бюджета допуска), поэтому доменный мьютекс ради доступа не берётся и новых рёбер в каноническом порядке захвата поле не создаёт. НИ ОДИН из них не удерживается ЧЕРЕЗ вызов обратно в `Service`, и слой вообще больше не зовёт узел нигде, кроме эмиттера: наблюдательские швы переходов fail-closed (`ProfileWithdrawn` / `ProfileRestored`) ушли вместе с профилями. Читают его приёмный путь (`handleDatagramFrame`), исходящий эмиттер (`datagramFrameEmitter.EmitTo`), четыре фоновые петли и RPC-диагностика; собственная точка отправки слоя (`Pipeline.SendLocal`) — это **точка расширения**, а не продакшн-путь в `node`: пока ни один протокол не переехал на слой (§8 спеки датаграмм), она достижима только из тестов, и комментарий к полю обязан быть пересмотрен вместе с первым адаптером, который её позовёт.
  Адаптеры самой плоскости `peerMu` берут — и всегда как самый внешний и единственный доменный мьютекс: `datagramSendTargetsLocked` вызывается под `peerMu.RLock` из `datagramPeerMetadata.SendableConnection` и `datagramDirectSession.LookupDirectSession`, из `datagramFrameHeadTargetLocked`, а из `datagramFrameEmitter.EmitTo` — через `datagramFrameSendTargetsLocked`, тот же упорядоченный список с применёнными per-соединение гейтами самого кадра. Гейтов теперь ровно два: РОЛЕВОЙ (`mesh_datagram_v1`, плюс `mesh_datagram_transit_v1`, если пир не является адресатом) и LAST-HOP по `dtype`; третий, по `req_caps` конверта, ушёл вместе с полем, поэтому ничто из записанного ОТПРАВИТЕЛЕМ в кадр не решает, по какому из наших сокетов его можно нести. Каждый из этих хелперов ОСВОБОЖДАЕТ lock до любых дальнейших действий. Это не вопрос вкуса: эмиттер дальше вызывает `sendTrackedFrameToSession` / `sendTrackedFrameToConn`, которые берут `peerMu` сами (гейт stalled через `peerState`, чтение реестра через `netCoreForID`), так что удержание lock-а через передачу дало бы самодедлок; передача к тому же заканчивается поставленной в очередь записью в сокет, а держать это под доменным мьютексом запрещает правило «никакого сетевого I/O под доменным мьютексом». Эти два хелпера адресуют СОЕДИНЕНИЕ, выбранное отбором, — объект `peerSession` на исходящем ярусе и `domain.ConnID` на принятом, — а не адрес пира: между отбором и передачей `peerMu` отпущен, пир за это окно может переподключиться, и тогда `s.sessions[address]` (или tracked-inbound соединение под данным `remoteAddr`) называет уже ДРУГОЙ сокет — с другим handshake и другим `ConnID`. Сессия или соединение, умершие в этом окне, отказывают собственным забором, и это ровно тот ответ, который нужен обходу кандидатов. Резолвер маршрутов доменных мьютексов не берёт вовсе: `FreshRoutes` идёт в `routing.Table.Lookup` (собственный `RWMutex` таблицы), `CachedRoutes` — в снапшот за `atomic.Pointer`, то есть ровно тот паттерн горячего чтения, который этот документ уже предписывает.
  **Ни барьера восстановления, ни стартового дискового I/O на этом пути больше нет.** `startDatagramLayer` запускает расписания и ничего больше: вся память слоя — анти-реплейный кэш в памяти, стартующий пустым и корректный с первого кадра, поэтому нет ни durable-прохода перед открытием слушателя, ни `datagram_boot.json`, который надо читать или писать, ни fail-closed-снятия, которое надо публиковать, ни возможности, которую узел мог бы потерять в рантайме. `localDatagramAdvertise`, которую читает каждый сборщик hello/welcome, отвечает из фиче-флага и типа узла через `datagramPlaneReady` — а это nil-проверка указателя, не берущая мьютекса вовсе. `localAdvertisedCapabilities`, снапшот времени конструирования, отдаваемый транзитному гейту конвейера, читает `datagramPlaneCapability` по той же причине, что и всегда: он снимается ДО того, как указатель записан, и снапшот, учитывающий готовность, оказался бы закрытым навсегда.
  Четыре фоновые петли, стартующие в `startDatagramSchedules` (насос исходящей классовой очереди, сборка просроченных кадров очереди, сборка reverse-состояния и петля обслуживания, подметающая базовый кэш реплея), останавливаются по контексту `Run` и доменных мьютексов не держат: наружу, в узел, ходит только насос — и делает это через эмиттер, соблюдающий дисциплину выше. `forgetDatagramPeer` — освобождение бакетов допуска §5 на последней сессии соседа — вызывается из `onPeerSessionClosedWithCause` ПОСЛЕ освобождения `peerMu`, рядом с остальными побочными эффектами закрытия.

- `runLoopsWg` (`sync.WaitGroup`, `service.go`) — ЕДИНСТВЕННАЯ группа жизненного цикла: на ней лежит каждая долгоживущая горутина, которую запускает `Run`, и других таких групп нет. Событийный цикл CM, `bootstrapLoop`, `hotReadsRefreshLoop`, цикл анонсов, тикер TTL маршрутов, отправитель проб, закрыватель слушателя, пул рассылки gossip (тридцать шесть воркеров плюс супервизор остановки), четыре расписания плоскости датаграмм (`startDatagramSchedules`) И три горутины каждой исходящей сессии CM — сторож рукопожатия и читатель сессии, которых запускает `openPeerSessionForCM`, и обслуживающая горутина, которую запускает `onCMSessionEstablished`, — все через единственную обёртку `goRunLoop`. Горутины сессии — более короткоживущие члены группы: они заканчиваются по тому же контексту жизненного цикла (`servePeerSession`, сторож рукопожатия) или по сокету, который CM закрывает в своём shutdown (читатель не смотрит ни на какой контекст и останавливается только на ошибке чтения), а их `Add` никогда не поднимает счётчик с нуля под `Wait` в `stopRunLifecycle`, но по двум разным причинам: обслуживающая горутина запускается НА событийном цикле CM — члене группы; сторож и читатель запускаются на dial-воркере CM, который членом группы НЕ является, — они опираются на то, что событийный цикл CM дожидается `cm.dialWg` перед возвратом, то есть член группы жив, пока жив хоть один dial-воркер. Читатель в группе потому, что делает собственную работу мимо цикла обслуживания — фреймы `file_command` идут прямо в файловый роутер, датаграммы в плоскость датаграмм, — и не должен оставаться внутри неё, когда `Run` останавливает подсистему передачи файлов. Join опирается на то, что к этому моменту закрыт каждый сокет исходящей сессии: CM закрывает сессии своих слотов и отброшенных результатов дозвона (`tearDownSession`, `drainChannels`), dial-воркер закрывает результат, который цикл уже не принимает, а `openPeerSessionForCM` закрывает свой на каждом пути ошибки. Обслуживающая горутина и читатель раньше запускались голым `go`: `Run` возвращался, пока они ещё обслуживали фреймы, и эти фреймы ставили квитанции и проходы key-sync в `goBackground` уже после того, как узел был объявлен остановленным (закреплено `TestRunWaitsForAnOutboundSessionGoroutineInsideAFrame`; читатель и сторож рукопожатия — `TestNoLongLivedGoroutineEscapesTheLifecycleGroup`, который больше не освобождает `openPeerSessionForCM`). Вне семидоменного разделения, потому что `WaitGroup` синхронизирует себя сам и не охраняет никакого состояния `Service`. Он существует потому, что отмена только ПРОСИТ: просто отменённый цикл может в момент возврата из `Run` находиться внутри сетевой отправки, слива TTL, записи `peers.json` или вызова в слой датаграмм, — а возврат из `Run` рантайм трактует как разрешение закрыть всё это под ним. Получить ту же гарантию ожиданием `backgroundWg` изнутри `Run` нельзя: та группа отслеживает fire-and-forget задачи всего сервиса, часть которых запускается прямо во время того же демонтажа, поэтому ожидание её изнутри `Run` обменяло бы этот баг на дедлок остановки. `WaitBackground` ждёт ОБЕ группы, поэтому у вызывающих и тестов по-прежнему ровно одна точка присоединения. Ожидание сознательно НЕ ограничено таймаутом: каждый цикл группы ограничен на отмене собственным контрактом (см. аудиты в комментариях к `startDatagramSchedules` и к пулу gossip), поэтому не заканчивающееся ожидание — это компонент, игнорирующий переданный ему контекст, а таймаут превратил бы это обратно в использование-после-демонтажа, ради предотвращения которого присоединение и вводилось. Группа ожидания, а не done-каналы, ровно по одной причине: она корректна для цикла, который НИКОГДА НЕ ЗАПУСКАЛСЯ, поэтому остановку можно вооружить до появления любого из них, тогда как канал, который никто не закроет, заставил бы её ждать вечно.

  **Группа ОДНА и ожидание ОДНО, а было две.** У плоскости датаграмм был собственный `datagramWg` со своим контекстом и своей остановкой (`armDatagramPlaneShutdown`, `goDatagramWorker`), потому что плоскость владела ДОЛГОВЕЧНЫМИ ХРАНИЛИЩАМИ и `Run` обязан был присоединить именно тех воркеров прежде, чем остановят владельца хранилищ. Хранилищ больше нет — четыре расписания это две сборки мусора в памяти, насос очереди и проход по истечению кэша реплея, — и каждую гарантию той второй группы обеспечивает `stopRunLifecycle`: (i) *присоединено до возврата из `Run`* — остановка выполняется на любом выходе, включая раскрутку паники, потому что это `defer`; (ii) *присоединено до всех defer-ов подсистем* — `stopFileTransfer`, `relayStates.stop`, `captureManager.Close`, `close(s.done)` — и это ПОЗИЦИЯ единственного `defer s.stopRunLifecycle(runCancel)`: он регистрируется после этих defer-ов и до первого `go`, поэтому LIFO ставит присоединение впереди них; (iii) *сначала отмена, потом присоединение* — первый оператор `stopRunLifecycle`; присоединение без отмены — дедлок в тот же момент, когда хоть один проход в полёте. Единственное, что вторая группа добавляла сверх этого — присоединять воркеров плоскости РАНЬШЕ циклов узла, — не несло ничего: оба набора просит остановиться ОДНА И ТА ЖЕ отмена, и между двумя ожиданиями не выполняется ни один шаг демонтажа, поэтому `wait(A); wait(B)` отпускает вызывающего ровно в тот же момент, что и `wait(A ∪ B)`. Стоила же она второго места, где порядок обязан был быть верным.

  **Слива входящих соединений в этом списке НЕТ, и он выполняется РАНЬШЕ присоединения.** `closeAllInboundConns` + `connWg.Wait` лежат в defer-е, зарегистрированном НИЖЕ `defer s.stopRunLifecycle(runCancel)`, поэтому LIFO выполняет их первыми — при ещё живых циклах жизненного цикла. Это верный порядок, а не случайность, и причин три: (а) слив НЕ ОСТАНАВЛИВАЕТ НИ ОДНОЙ ПОДСИСТЕМЫ, в которую заходит цикл, — а ровно от этого присоединение и защищает. Он закрывает сокеты и чистит строки, относящиеся к соединению (реестр соединений, подписчиков, авторизацию соединения, входящие health-ссылки); до соединения цикл добирается только через реестр netcore, который на закрытый `ConnID` отвечает «неизвестное соединение», а не выдаёт освобождённый хендл, и отсутствие строки соединения — обычное состояние, которое порождает любой разрыв с пиром. (б) Несущая зависимость направлена в другую сторону: обработчики соединений — ПРОДЮСЕРЫ для того, что потребляют циклы (событийный цикл CM через `EmitSlot`, полосы gossip, плоскость анонсов), и свою последнюю работу они производят на выходе (`trackInboundDisconnect` → `markPeerDisconnected`, `removeSubscriberConnID`, учёт закрытия сессии в маршрутизации), поэтому присоединять обработчики, пока эти потребители живы, — тот порядок, при котором работа ещё может быть принята. (в) Слив в любом случае обязан идти раньше `cancelAllPendingWithdrawalsForShutdown`, чей defer стоит между этими двумя, — то есть отмена выполняется ПОСЛЕ дренажа и ДО join. После дренажа — потому что обработчики входящих сообщают о закрытии сессий, пока не завершатся, и каждый взведённый ими отзыв к моменту отмены ещё висит. До join — потому что join длится, пока закрываются сокеты исходящих сессий, и таймер, ещё висящий в этот момент, сработал бы внутри него и вырвал бы прямой маршрут, пока останавливаются циклы, потребляющие отзыв. Закрытия, о которых сообщают во время join или после — горутины исходящих сессий, разматывающиеся в нём, или вызывающий, переживший `Run`, — приходят после отмены, и флаг, который она взводит, `withdrawalsShutDown` (под `peerMu`), отклоняет их на обоих путях, а не взводит таймер, который никто не отменит: `maybeScheduleDeferredWithdrawal` проверяет его под тем же `peerMu`, под которым взводит таймер, а `executeDeferredWithdrawal` — в своей первой секции под `peerMu`, рядом с перепроверкой relay-сессий и под тем же мьютексом, что и мутация маршрута; это покрывает синхронный путь (grace отключён) и таймер, забравший свою запись до отмены, без окна между проверкой и мутацией. Закреплено `TestAWithdrawalArmedBeforeShutdownDoesNotFireInsideTheJoin`, `TestAWithdrawalAskedForAfterRunReturnedIsNotArmed` и `TestASynchronousWithdrawalOnAStoppedNodeIsDropped`. Порядок закреплён тестом `TestTheInboundDrainRunsBeforeTheLifecycleJoin`, который наблюдает закрытие входящего сокета в момент, когда цикл жизненного цикла ещё припаркован; перестановка двух defer-ов делает тест красным.

  Порядок внутри `Run` несущий и за четыре раунда породил четыре дефекта, поэтому он не свойство того, где случайно оказался очередной `defer`: у `Run` ОДНА упорядоченная остановка, `stopRunLifecycle` (отменить → присоединить), вооружаемая в ОДНОЙ точке. Голая `runCancel` в начале `Run` остаётся страховкой на случай паники, поднятой до этой точки. Отмена, зарегистрированная ТОЛЬКО сверху, выполнялась после ожиданий и заставляла выход по ошибке — например, listen, падающий из-за уже занятого адреса, — навсегда зависнуть в собственном демонтаже; а присоединение циклов только на двух штатных возвратах позволяло выходу по ошибке вернуться, пока `bootstrapLoop` ещё дописывал `peers.json` на выходе, то есть когда вызывающий уже вправе удалить каталог данных.

  Именно пул gossip показывает, почему группу нужно определять по СВОЙСТВУ, а не по месту вызова: его запускает вспомогательная функция (`startGossipDispatch`), а не сам `Run`, поэтому страж, искавший операторы `go` внутри `Run`, его не видел, — и он висел на `backgroundWg`, которую `Run` сознательно не ждёт, тогда как его задания дозваниваются, делают рукопожатия и пишут в сокеты. Присоединение ограничено, потому что воркер отказывается НАЧИНАТЬ задание после отмены контекста: ожидание покрывает только уже запущенные задания, а каждое из них ограничено таймаутом дозвона (2 с), таймаутом рукопожатия (2 с / 1,5 с для sync) и дедлайном записи в netcore. Правило не задокументировано, а ПРИНУДИТЕЛЬНО: `TestNoLongLivedGoroutineEscapesTheLifecycleGroup` разбирает каждый нетестовый файл пакета и падает на любой горутине, которая ЧИТАЕТ из `Done`-канала контекста (наблюдаемое свойство долгоживучести), будучи запущенной голым `go` или на `backgroundWg`. Слепые зоны стража перечислены в самом тесте: долгоживущая горутина, вовсе не читающая контекст; горутины в других пакетах; динамическая диспетчеризация; и то, что он доказывает ЧЛЕНСТВО, а не факт ожидания группы (эту половину доказывают блокирующие тесты жизненного цикла в `datagram_lifecycle_test.go`). Покрытие стража описано в самом тесте, а не объявлено полным: дважды список, читавшийся как исчерпывающий, не содержал ту форму, которая ломалась следующей, — но теперь страж классифицирует КАЖДЫЙ оператор `go` в пакете и падает на любой форме, которую не смог разрешить, поэтому ничто не пропускается неназванным.

  Горутины, принадлежащие БОЛЕЕ КОРОТКОЙ жизни, присоединяются ТАМ — одна горутина, один владелец: обработчик соединения к `connWg`; входящий heartbeat — к обработчику своего соединения, который ждёт пер-соединенческую `WaitGroup` перед возвратом (закрытие стоп-канала только ПРОСИТ: цикл может находиться внутри отправки пинга, ограниченной дедлайном записи netcore, и после этого он ещё трогает Network и `peerMu`); дозвоны ConnectionManager — к `cm.dialWg`; пять тикеров снапшотов горячих чтений — к локальной `WaitGroup`, которую ждёт `hotReadsRefreshLoop`, а сам этот цикл живёт в `runLoopsWg`. Горутин исходящих сессий в этом списке НЕТ: CM в своём shutdown только закрывает сокет сессии и никогда не ждёт обслуживающие её горутины, поэтому они сами живут в `runLoopsWg`. **Известное исключение:** УСТАРЕВШИЙ путь сессий — `ensurePeerSessions` → `runPeerSession` → `openPeerSession`, неактивный, пока подключён ConnectionManager, — запускает свою горутину на дозвон, сторож контекста и читатель сессии голыми `go`, и `Run` их НЕ дожидается. Вызывающие этого пути не входят в `runLoopsWg`, поэтому перенос туда мог бы поднять счётчик с нуля под `Wait` в `stopRunLifecycle`; путь записан как исключение в `TestNoLongLivedGoroutineEscapesTheLifecycleGroup`, а не как присоединённый. Их задачи `goBackground` после возврата из `Run` отклоняются. **Остаточное, тоже без join:** колбэк таймера отзыва, уже прошедший проверку shutdown внутри `executeDeferredWithdrawal` к моменту отмены, доводит его вне join; таймеры `probeRegistry` (`routing_probe_loop.go`) срабатывают и после `Run` и вызывают `routingTable.MarkProbeFailure` — только состояние в памяти.

- `peerSession.declarations` — зеркало сырого самоописания из рукопожатия (валидированные сырые имена возможностей §2.2 и объявленный набор `dtypes` §6.1). Это поле не `Service`, но дисциплина у него ровно как у `peerSession.capabilities` и `peerSession.peerIdentity`: пишется один раз в `applyWelcomeMetadata` и читается под `peerMu` (через `sessionDeclarations`, `sessionHasCapability`, `sessionPeerIdentity`). **Запись тоже под `peerMu`, и это не перестраховка.** В момент записи сессия НЕ принадлежит только goroutine-дозвонщику: `readPeerSession` запущен ещё до начала рукопожатия — именно он и доставил `welcome` — и читает те же поля на capability-гейтах своего приёмного пути (`datagram`, `file_command`). Пир, который шлёт кадр вплотную за собственным `welcome`, ставит читателя на поле ровно в тот момент, когда его присваивает горутина рукопожатия; детектор гонок это подтверждает. Поэтому `applyWelcomeMetadata` вызывается с удерживаемым `peerMu` в обеих исходящих точках (`openPeerSession`, `openPeerSessionForCM`); реклама датаграмм вычисляется ДО захвата лока, потому что обращается к слою датаграмм. Сессия, не дошедшая до записи, отвечает пустым набором возможностей и нулевой identity — но безопасность окна держится НЕ на этом, и считать иначе было дефектом: набор публикуется на `welcome`, а рукопожатие заканчивается на круг позже, на `auth_ok`. Авторитетная копия живёт в `netcore.NetCore` с его собственным внутренним `RWMutex`; зеркало существует лишь потому, что исходящий диспетчер адресуется по `PeerAddress` и не видит `ConnID`.
- `peerSession.authOK` — состояние «рукопожатие исходящей сессии завершено» (пришёл `auth_ok`). Присоединяется к трём полям выше по той же дисциплине, но именно он закрывает их окно. Возможность СОГЛАСОВАНА на `welcome`, а В СИЛЕ — только после установки этого флага, поэтому `sessionHasCapability` (единственный хелпер, через который проходит каждый capability-гейт приёмного пути набранного направления) отказывает, пока флаг false. Пишется ровно один раз, в `markSessionHandshakeComplete` под `peerMu`; читается под `peerMu.RLock`. **Запись под локом потому, что читатель — другая горутина:** `readPeerSession` диспатчит ещё до `welcome`, поэтому пир, отправивший `datagram` вплотную за собственным `welcome`, ставит читателя на флаг ровно в момент записи. Две наши собственные записи упорядочены относительно него, а не гейтятся им: и повтор backlog, и connect-time full sync ВОЗВРАЩАЮТСЯ из `handleAuthSession` и запускаются вызывающим только после постановки `auth_ok` в очередь — full sync, обогнавший `auth_ok`, дозвонщик отвергнет собственным гейтом. Переход односторонний: сессии, которой нужен другой набор, соответствует новая сессия на новом сокете.

### Порядок захвата

Во всех кросс-доменных секциях locks должны захватываться в точно этом порядке:

```
peerMu → deliveryMu → knowledgeMu → gossipMu → ipStateMu → fileMu → statusMu
```

Порядок — тотальный: ни один путь кода не может захватить более поздний мьютекс не держа более раннего, и затем попытаться захватить более ранний. Секция, которая трогает `peerMu` и `statusMu`, сначала берёт `peerMu`, делает свою работу, отпускает; потом берёт `statusMu`. Никогда наоборот.

Нарушение порядка — deadlock-баг. Порядок сейчас держится соглашением; позже возможно добавить vet-линтер.

#### Почему именно такой порядок

Самый конкурируемый домен стоит первым, чтобы менее конкурируемые никогда не держали свой lock ожидая более конкурируемого. Измеряемая «горячесть» (частота записи) убывает примерно по цепочке:

1. **peerMu** — каждое connect/disconnect/mark* пишет сюда; шторма переподключений бьют сильнее всего.
2. **deliveryMu** — каждое входящее/исходящее сообщение, каждый relay-retry.
3. **knowledgeMu** — пишет только при handshake и при обучении нового identity binding. Также владеет собственной подписанной записью узла (`selfRecord` / `selfRecordBody`): запись строится и ПЕРСИСТИТСЯ (файловый I/O trust store) строго вне мьютекса, под `knowledgeMu.Lock` происходит только подмена полей — порядок reserve → persist → publish из `self_record.go`.
4. **gossipMu** — пишет на publish/subscribe; читает каждый `fetch_messages`.
5. **ipStateMu** — пишет на ban events и observed-IP convergence; читает каждый accept.
6. **fileMu** — пишет только при активных трансферах; холодный вне этого.
7. **statusMu** — пишет только когда агрегированный статус реально меняется.

### Паттерны кросс-доменных транзакций

Большинство методов Service трогают один домен. Секции ниже — **репрезентативные**, а не исчерпывающие: любой кросс-доменный call site обязан соблюдать канонический порядок из §«Порядок захвата» независимо от того, попал он в список или нет. Примеры нужны чтобы показать форму; отсутствие пути ниже — не разрешение обратного порядка.

#### `markPeerConnected` / `markPeerDisconnected`
Оба держат `peerMu.Lock` на всё тело (health, identity и version map'ы) и вкладывают остальные домены внутрь, по одной секции за раз:
- `updatePeerStateLocked` — `deliveryMu.RLock` до конца своего тела, с вложенным `statusMu.Lock` вокруг публикации агрегатного статуса (см. `updatePeerStateLocked` ниже): `peerMu → deliveryMu → statusMu`.
- `ipStateMu.Lock` — `markPeerConnected` удаляет IP из `bannedIPSet` и, с вложенным `statusMu.Lock`, убирает пира из `versionPolicy.incompatibleReporters`: `peerMu → ipStateMu → statusMu`. `markPeerDisconnected` удаляет запись пира в `observedAddrs`: `peerMu → ipStateMu`.
- `statusMu.Lock` — `recomputeVersionPolicyLocked`: `peerMu → statusMu`.

Обновление hot-read снапшотов и публикация в `ebus` идут после освобождения `peerMu`.

#### `onCMSessionEstablished`
У callback'а две половины с разными правилами: первая выполняется синхронно НА событийном цикле `ConnectionManager`, вторая — в горутине сессии, которую он запускает.

На событийном цикле. CM вызывает его после того, как слот перешёл в Initializing, и после освобождения `cm.mu` (`ConnectionManagerConfig.OnSessionEstablished`). Слот остаётся ровно таким, каким передан, — в таблице, в Initializing, на `info.SlotGeneration`, с открытой сессией — пока callback не вернётся: каждая мутация слотов (включая выселение через `shrinkToLimit`, `add_peer`, `RetainOnly` и shutdown) и каждый `OnSessionTeardown` выполняются на том же событийном цикле, поэтому ни одна не может вклиниться в callback. Два доменных мьютекса здесь одновременно не удерживаются, поэтому эта половина не добавляет рёбер между доменами; каждый шаг берёт один домен на свою короткую секцию и отпускает его:
- `ipStateMu` — IP, по которому шёл дозвон, удаляется из `bannedIPSet`; позже `recordObservedAddress` пишет `observedAddrs`.
- `peerMu` — `learnIdentityFromWelcome` (`promotePeerAddress`, `rememberPeerType`, `addPeerID` / `addPeerVersion` / `addPeerBuild`), `resolveHealthAddress` (RLock), затем `addPeerID` / `addPeerVersion` / `addPeerBuild` по health-ключу.
- `knowledgeMu` — `addKnownIdentity`, `learnWireIdentityKeys` (`addKnownPubKey` / `addKnownBoxKey` / `addKnownBoxSig`) и `knownBoxKey` (RLock), до которого доходит `notifyIdentityKeysImported` → `identityResolver.usableNow`.
- Вне доменного разделения: `PeerProvider.mu` (`Add` / `MarkFresh` из `promotePeerAddress`, после освобождения `peerMu`), собственный мьютекс `identityResolver`, `ebus.PublishIdentityAdded` (после освобождения `knowledgeMu`) и `ebus.PublishIdentityResolutionChanged` (`identityResolver.emit`, после освобождения мьютекса резолвера).

`deliveryMu`, `gossipMu`, `fileMu` и `statusMu` на событийном цикле не берутся. Callback нельзя выполнять под `cm.mu`: `PeerProvider.Candidates` / `KnownPeers` держат `pp.mu.RLock` и при этом зовут `QueuedFn` → `ConnectionManager.QueuedIPs` (`cm.mu.RLock`) — ребро `pp.mu → cm.mu`, а эта половина берёт `pp.mu.Lock` в `PeerProvider.Add`; под `cm.mu` это замкнуло бы цикл, вдобавок к рёбрам из `cm.mu` в доменные мьютексы Service.

В горутине сессии (вне событийного цикла, поэтому блокирующий I/O допустим, но никогда под доменным мьютексом). Список называет локи, которые эта функция берёт сама, и порядок вызовов, определяющих доменную картину; каждый вызываемый следует своей секции или doc-комментарию:
- setup прерван локальным выселением — CM закрыл сессию (shrink, выселение под `add_peer`, `RetainOnly` или правило пина, shutdown), пока шёл `initPeerSession`, или до того, как сессию успели зарегистрировать: одна секция `peerMu.Lock`, которая только удаляет собственную запись `dialOrigin` сессии (не трогая её, если под этим адресом зарегистрирована другая сессия), затем сбрасывается бакет управляющих фреймов. Провал setup не записывается, route quarantine не взводится, счётчик провалов setup не сбрасывается, сессия не публикуется, в CM ничего не сообщается (слота уже нет). Логируется как `cm_session_setup_aborted_local_eviction`;
- провал setup — за него отвечает пир: одна секция `peerMu.Lock` (`dialOrigin`, `recordSetupFailureLocked`, `armRouteQuarantineLocked`), затем `ActiveSessionLost`;
- успех setup — регистрация сессии под `peerMu` СНАРУЖИ → `deliveryMu` ВНУТРИ вместе с `clearSetupFailuresLocked`, под защитой проверки причины закрытия (см. секцию о map'ах сессий ниже), затем эмиссия `SessionInitReady`, `refuseLegacyIdentity` (leaf-мьютекс хранилища пинов, затем `peerMu.RLock`, никогда вместе), `markPeerConnected` и `flushPendingPeerFrames` в порядке, указанном в их собственных секциях, `onPeerSessionEstablished` (одна секция `peerMu` для счётчиков сессий с leaf-мьютексом record-protection внутри; работа маршрутизации, withdrawal-grace и presence идёт после освобождения `peerMu`), полная синхронизация таблицы и `servePeerSession`;
- после возврата `servePeerSession` — собственная очистка, снова `peerMu` СНАРУЖИ → `deliveryMu` ВНУТРИ, затем хелперы очистки сессии и дерегистрация маршрута (`onPeerSessionClosed*`), которую выполняет только эта горутина.

Кто закрыл сессию, решает каждое начисление. `peerSession.closedBy` записывает ПЕРВОГО закрывшего внутри `closeOnce` сессии, до разборки транспорта: владельца сессии (`Close`) или локальное выселение CM. (Когда CM деактивирует слот после потери, о которой сообщила горутина, горутина уже закрыла сессию, и закрытие CM ничего не меняет; окажись оно когда-нибудь первым, оно записывается как закрытие владельца, что пира никогда не оправдывает.) Горутина читает его после возврата собственного `Close` — путь провала setup, `retirePeerSession` в serve-цикле и очистка после serve сначала закрывают сессию, и `sync.Once` упорядочивает их после победившего закрытия CM, — либо под `peerMu` при регистрации. Сессия, закрытая локальным выселением, никогда не вменяется пиру: ни провала setup, ни route quarantine, `markPeerDisconnectedByLocalDecision` вместо неудачного `markPeerDisconnected`, а дерегистрация маршрута атрибутируется как `sessionCloseLocalEviction`. Первый закрывший — не обязательно первая причина: если собственный сбой пира уже ждёт в `errCh`, когда выселение выигрывает `closeOnce`, этот сбой остаётся не вменённым — это принято, потому что выселение всё равно закрывало сессию, а защищаемся мы от противоположной ошибки.

#### `handleAuthSession`
Трогает `peerMu` (привязка identity к сессии) и `knowledgeMu` (кеш pubkey). Порядок: `peerMu` → `knowledgeMu`.

#### `accumulateInboundTraffic`
Трогает только `peerMu` (обновление байтовых счётчиков health). Кросс-доменного hold'а нет.

#### `handleConnectionNotice{code=peer-banned}`
Трогает `ipStateMu` (записать IP-бан) и опционально `peerMu` (выкинуть сессии с этого IP). Порядок: `peerMu` → `ipStateMu`.

#### Жизненный цикл файл-трансфера и приёмный путь `file_command`
`fileMu` редко взаимодействует с другими доменами. Когда взаимодействует (отказ трансфера из-за ухода пира), порядок — `peerMu` → `fileMu`.

Приёмный путь peer-сессии добавляет второго, БОЛЕЕ ГОРЯЧЕГО читателя того же домена, и он не вкладывает один лок в другой: `sessionFileCommandIsAdmissible` (`peer_session_admission.go`) спрашивает `sessionHasCapability` под `peerMu.RLock`, отпускает его и только затем читает `fileRouter` под `fileMu.RLock` (`fileCommandHasConsumer`). Два последовательных однодоменных чтения не добавляют ребра в канонический порядок; вложенные — добавили бы и обернули бы самый нагруженный лок узла вокруг домена, который диспетчеризация ниже всё равно читает сама. Те же два факта читаются повторно одним гейтом позже, самой диспетчеризацией, — сознательно: вердикт, пронесённый от гейта приёма, был бы фактом, который между двумя точками может устареть.

#### `flushPeerState` (снапшот peer state для персистентности)
Трогает peer-домен (`persistedMeta`, `health`, `peerTypes`, `peerVersions`, `peerBuilds`, …) и `ipStateMu` (снапшотит `bannedIPSet` и `remoteBannedIPs` для диска). Порядок: `peerMu.Lock` снаружи, `ipStateMu.RLock` внутри. Оба lock'а освобождаются до дискового I/O; после записи `peerMu.Lock` берётся повторно кратко, только для обновления `lastPeerSave`. Оба цикла под `ipStateMu.RLock` (локальные и удалённые баны) живут в одном окне RLock'а, чтобы файл на диске представлял согласованный снапшот обеих таблиц.

Кросс-lock-ограничение: `flushPeerState` НЕ ДОЛЖЕН вызывать любые методы `peerProvider.*` изнутри `peerMu`. `PeerProvider.Candidates()` уже выполняется под `pp.mu.RLock` и возвращается в Service через `RemoteBannedFn` / `BannedIPsFn` (ребро `pp.mu → peerMu/ipStateMu`). Обратное ребро (`peerMu → pp.mu`) изнутри `buildPeerEntriesLocked` замкнёт цикл и под writer-preferring `sync.RWMutex` Go приведёт к deadlock'у в тройной гонке: candidate refresher держит `pp.mu.RLock` и ждёт `peerMu.RLock`; параллельный `Promote`/`Add` встаёт в очередь на `pp.mu.Lock`, блокируя новых читателей pp.mu; `flushPeerState` держит `peerMu.Lock` и пытается стать новым читателем `pp.mu.RLock`. Снапшоть `peerProvider.StaticSnapshotAll()` ДО взятия `peerMu.Lock` и прокидывай снапшот параметром в `buildPeerEntriesLocked`.

#### `recordOutboundAuthSuccess` (восстановление после handshake)
Трогает peer-домен (`persistedMeta` через `clearRemoteBanLocked`) и `ipStateMu` (`remoteBannedIPs` И волатильный набор `remoteIPBanOffenders`, оба через `clearRemoteIPBanLocked`). Порядок: `peerMu.Lock` снаружи → `ipStateMu.Lock` внутри. Внутри одного внешнего `peerMu`-региона `ipStateMu.Lock/Unlock` явно оборачивает вызов `clearRemoteIPBanLocked`, потому что этот helper требует от вызывающего уже держать write-lock `ipStateMu`. `clearRemoteIPBanLocked` попутно сбрасывает pre-escalation offender-набор для этого IP, но возвращает `true` только когда удалена ПЕРСИСТЕНТНАЯ запись `remoteBannedIPs` — очистка одного волатильного набора не триггерит `flushPeerState`.

#### `storeIncomingMessage` (knowledge-запись + gossip-dedup)
Трогает `knowledgeMu` (запись `known` по sender / recipient, чтение `pubKeys` для non-DM spoof-gate) и `gossipMu` (`seen`-dedup, `topics`-append). Порядок: СНАЧАЛА `knowledgeMu.Lock`, отпустить, ПОТОМ `gossipMu.Lock` — канонический `knowledgeMu → gossipMu`. Секции ПОСЛЕДОВАТЕЛЬНЫЕ, не вложенные; расщепление семантически безопасно: записи в `known` идемпотентны, а решение dedup читает только `seen`, не `known`, поэтому конкурентный writer не может получить другой итог в щели между секциями. В gossip-секции дополнительно происходит временный release/reacquire `gossipMu` вокруг внешнего вызова `messageStore.StoreMessage` (SQLite I/O не должно выполняться под доменным lock'ом); после возврата окно заново захватывается для append'а в `topics` и сбора диагностических ID до финального release.

DM-ветка раньше в `storeIncomingMessage` читает `pubKeys`/`boxKeys`/`boxSigs` для верификации подписи под `knowledgeMu.RLock` как standalone-снапшот — никакого кросс-доменного hold'а, верификация идёт уже вне lock'а.

#### `retryableRelayMessages` / `deleteBacklogMessageForRecipient` (delivery + gossip)
Трогают `deliveryMu` (`relayRetry`) и `gossipMu` (`topics["dm"]`). Канонический порядок `deliveryMu → gossipMu`: `deliveryMu` СНАРУЖИ, `gossipMu` ВНУТРИ. В `retryableRelayMessages` gossip-часть — это read-only snapshot (`gossipMu.RLock`), сжатый до копии `topics["dm"]`; в `deleteBacklogMessageForRecipient` gossip-часть — write (`gossipMu.Lock`) через весь цикл фильтрации, потому что каждое совпадение отменяет соответствующий `relayRetry` в той же итерации — обе мутации должны оставаться атомарно согласованными. Snapshot возвращается уже с отпущенным `deliveryMu`, поэтому любой путь удаления (receipt ack, cancel, transit-eviction через `dropRelayRetryEntries`) может убрать снапшотированное сообщение и его запись до того, как до него дойдёт `retryRelayDeliveries`. Поэтому `noteRelayAttempt` записывает попытку только в существующую запись и сообщает об отсутствии; цикл пропускает отправку. Пересоздание записи там давало вечного сироту: каждый reaper обходит живой backlog, в котором сообщения уже нет, и до записи больше никто не добирался.

#### `CancelOutgoingDelivery` (отзыв неотправленного DM: peer + delivery + gossip + status)
Берёт `peerMu.RLock → deliveryMu.Lock → gossipMu.Lock → statusMu.Lock` — канонический порядок целиком — и освобождает в LIFO. `peerMu` только на чтение и удерживается исключительно потому, что `refreshAggregatePendingLocked` обходит peer-домен; `deliveryMu` закрывает `pending` / `pendingKeys` / `outbound` / `awaitingDelivered` / `relayRetry`; `gossipMu` — backlog `topics["dm"]`; `statusMu` — самый внутренний пересчёт aggregate pending. Всё чистится в ОДНОЙ секции намеренно: конверт, выброшенный из backlog в момент, когда retry-тик ещё держит его `awaitingDelivered`, вернулся бы в сеть на следующем тике. `TopicPeerPendingChanged` / `TopicAggregateStatusChanged` публикуются после освобождения всех мьютексов, по общему правилу побочных эффектов. См. `docs/dm-commands.md` §«Отзыв неотправленного сообщения».

#### `CancelOutgoingDeliveriesTo` (отзыв всей переписки)
Та же секция и тот же канонический порядок, что и у `CancelOutgoingDelivery` — `peerMu.RLock → deliveryMu.Lock → gossipMu.Lock → statusMu.Lock`, освобождение LIFO, события после, — но с фильтром по ПОЛУЧАТЕЛЮ вместо id сообщения и одним проходом по каждой структуре вместо прохода на сообщение. Ради этого он и существует: per-message форма берёт весь стек и заново сканирует backlog на каждый вызов, поэтому очистка треда из тысячи сообщений через неё была бы тысячей полных сканов под писательским мьютексом. Чужие конверты (транзит, адресованный тому же пиру) пропускаются в том же проходе — очистка НАШЕЙ переписки не даёт права вычищать чужие сообщения.

#### `retryDueDeliveries` / `registerAwaitingDeliveredLocked` / `registerAwaitingSeenAckLocked` (sender-side e2e retry)
`markedNeverEmitted` — тот же домен; в нём id, по которым у этого процесса стоит долговременное утверждение «не уходило». Он существует потому, что backlog-реплей проходит мимо движка ретраев: он может отправить сообщение, чьей записи в `awaitingDelivered` уже нет — истёк собственный TTL или её снял receipt, — и без этого утверждение осталось бы на строке, пока копия лежит у пира. Запись покидает набор на трёх событиях, заканчивающих утверждение: снятие ради отправки кадра (`clearEmissionMarks`), подтверждение или receipt, которые его опровергают, и отзыв сообщения автором — его строка уничтожается вместе с отметкой (`CancelOutgoingDelivery` / `CancelOutgoingDeliveriesTo`, только память: писать уже некуда; освобождается по SCOPE по той же причине, что и `clearFreezeLocked`, — набор переживает retry-запись, поэтому освобождение только того, что проход нашёл в `awaitingDelivered`, оставило бы висеть каждый id, чья запись уже ушла). Истечение TTL намеренно оставляет утверждение стоять: строка сохраняется как проваленная, и она действительно не уходила.

`markedNeverEmitted` — единственное сопутствующее состояние, которое ещё нужно флагам эмиссии; никаких очередей рядом больше нет. Долговременная сторона — ДВА монотонных бита, каждый пишется в одну сторону (chatlog/emission.go): `never_emitted` пишет INSERT строки и один раз снимает гейт перед первым кадром; `on_wire` пишется один раз, после подтверждения приёмника. Поскольку ни один не разворачивается обратно, ничего не нужно решать, ставить в очередь, перечитывать и исправлять — версия с одним обратимым флагом требовала всех четырёх вещей и всё равно оставляла гонку.

Ни один из битов не разворачивается обратно, поэтому решать при записи нечего: отказ не пишет вообще ничего, подтверждение пишет один факт в единственную свою сторону, а строка в каждый момент уже говорит обе вещи, нужные её двум читателям. Именно это и убрало очередь, штамп попытки, перечитывание и коррекцию, которые требовались одному обратимому флагу.

`frozenDeliveries` — тот же домен; в нём лежат id, о которых сейчас принимает решение очистка переписки. Каждый путь, способный отправить, сверяется с ним под тем же захватом, под которым ставил бы отметку об отправке (`claimEmissionLocked`, `confirmEmission`), — поэтому «можно ли это отправлять» и «не решает ли про это очистка» отвечаются из одного снапшота. Тик ретраев сверяется ДВАЖДЫ именно поэтому: при выборе кандидатов (`pickQueueHeadLocked`), где замороженная запись останавливает очередь своего получателя на этот тик, и ещё раз непосредственно перед проводом — отбор, lock-free вычисление маршрута и диспатч это три разных окна, и заморозка может прийти в любое из них. Ни одна из сверок не может стоить сообщению ничего, потому что тик не списывает вообще ничего: попытку тратит `confirmEnvelopeOnWire`, вызываемый ПРИЁМНИКОМ, принявшим фрейм, — поэтому заморозка в любом окне просто не находит потраченного. Путь отказа (`holdDeliveryRetry`) по той же причине возвращает замороженной записи расписание, которое сдвинул проход: оттаявшее сообщение должно уйти немедленно, а не оплачивать интервал опроса за решение, к которому получатель не имеет отношения. В отличие от `cancelledDeliveries` заморозка не истекает: она заканчивается коммитом очистки — `CancelOutgoingDeliveriesTo` снимает её по всему SCOPE вызывающего, а не по тому, что нашёл, потому что у большей части длинного треда никакого состояния доставки уже нет, — или откатом, и тогда `ThawOutgoingDeliveries` возвращает доставки. Удаление одного сообщения берёт ту же заморозку на один id, и снимает её его отзыв; любой другой выход — immutable-сообщение, нечитаемая строка, маршрут без отзыва — освобождает её явно, потому что TTL у заморозки нет и больше её снять некому. Истечение было бы гарантией удаления с приделанным таймаутом. См. docs/dm-commands.md §«Массовая очистка».

`cancelledDeliveries` — тот же домен, и существует он потому, что одна пара операций НЕ может уместиться в один захват: сборка backlog-фрейма подписчика читает gossip-домен, а затем delivery-домен, то есть в порядке, обратном каноническому, поэтому снапшот и отметка об отправке — это два разных окна. Отмена, попавшая между ними, отрапортует «не отправлялось» — роутер отзовёт сообщение и ничего не запланирует, — а снапшот всё ещё держит конверт и отправит его. Поэтому `CancelOutgoingDelivery` / `CancelOutgoingDeliveriesTo` записывают id под `deliveryMu` (`noteDeliveryCancelledLocked`), а `noteOwnEnvelopesEmitted` в ТОМ ЖЕ захвате, где ставит отметки, сообщает, какие из спрошенных id затенены; писатель backlog их пропускает. Записи чистятся по возрасту при записи и должны пережить лишь один push.

`emissionLane` — НЕ доменный мьютекс и в каноническом порядке не участвует: она охраняет не состояние `Service`, а порядок, в котором собственные записи узла в журнал доходят до SQLite. Она намеренно удерживается на этом дисковом I/O — и это стоит проговорить, потому что заменённый ею мьютекс был осуждён ровно за это.

Разница — в приоритете, и приоритет здесь и есть всё. Оба писателя ставят монотонный бит в разном ключе metadata одним самодостаточным условным UPDATE, поэтому ради КОРРЕКТНОСТИ упорядочивать нечего. Упорядочивать надо нужду: `clearEmissionMarks` снимает врождённое утверждение ДО выхода кадра, поэтому сообщение, которого ждёт пользователь, не уйдёт, пока снятие не ляжет, а снятие, исчерпавшее `busy_timeout`, это сообщение придержит; `markDeliveryOnWire` же записывает уже ушедший кадр. SQLite пишет по одному writer'у за раз, пул не ограничен, и без нашего порядка реконнект, штампующий переигранную переписку, соревнуется со снятием в busy-handler'е и может выигрывать раз за разом. Полоса — ОЧЕРЕДЬ, а не лок: ходы достаются снятиям раньше учёта, внутри класса — в порядке прихода, а ход пишет не больше `maxIdsPerLaneWrite` id; у кого осталось больше, тот встаёт в КОНЕЦ. Каждый род писателя ограничен по-своему, потому что отказать можно только одному: не поставленный полосой в очередь штамп не пишет ничего и заново выводится `repairLocalDeliveryRecord`, а снятия, которым нельзя отказать, не придержав сообщение, КОАЛЕСЦИРУЮТСЯ — но не больше чем на один statement. `storeDeliveryReceipt` намеренно НЕ вызывает полосу вообще: `delivered` старше штампа везде, где штамп читают, поэтому этот путь в журнал не пишет. Неудавшаяся запись статуса оставляет квитанцию НЕОБРАБОТАННОЙ, и ничего по ней не закоммичено: `finishReceipt` (deliveryMu) пишет dedup-ключ и удаляет retry-запись только после того, как запись легла, — поэтому отправитель продолжает ретраить сообщение, а следующая квитанция снова пробует запись.

Отсутствие дедлока держится на той же одной строке, что и раньше: в полосу входят СНАРУЖИ всех доменных мьютексов и НИКОГДА при удерживаемом доменном. Call site-ы это соблюдают — снятие в `noteOwnEnvelopesEmitted` и штамп в `confirmEnvelopeOnWire` / `storeDeliveryReceipt` идут ПОСЛЕ освобождения `deliveryMu`, — и это общее правило для дискового I/O, а не что-то специфичное для этого журнала. `TestEveryJournalWriteGoesThroughTheEmissionLane` роняет сборку, если запись появится вне полосы.

Scheduler ретраев доставки (`delivery_retry.go`) владеет `awaitingDelivered` / `awaitingSeenAck` — оба поля delivery-домена. `retryDueDeliveries` никогда не держит мьютекс на сетевом I/O; он чередует четыре шага, и захват `deliveryMu.Lock` каждого заканчивается до начала следующего:

1. `planDueDeliveries` — один `deliveryMu.Lock`: обходит набор ожидающих, удаляет сообщения, у которых истёк собственный TTL (`classifyAbandonedLocked` — единственный терминальный вердикт, который там есть), и выбирает НЕ БОЛЕЕ ОДНОГО кандидата на получателя (`selectQueueHeadsLocked` → `pickQueueHeadLocked`, который читает `frozenDeliveries` в том же захвате).
2. без мьютекса: `router.Route` на каждого кандидата. Он читает routing- и peer-состояние под своими замками, поэтому вызов под `deliveryMu` перевернул бы канонический порядок `peerMu → deliveryMu`.
3. `armDueDeliveries` — один `deliveryMu.Lock`: пишет `Held` атомарно с расписанием, чтобы `kickDeliveryRetriesForReachable` не увидел полуобновлённую запись, и вызывает `resetBackoffOnReturn` для записей, чей получатель только что вернулся.
4. без мьютекса: `emitDueDelivery` на конверт — раздаёт конверт приёмникам и НЕ пишет ничего. Каждый приёмник, принявший фрейм, вызывает `confirmEnvelopeOnWire` (короткий `deliveryMu.Lock`): relay-enqueue — синхронно, push подписчикам — из фоновой горутины. Запись, которую никто не подтвердил, просто остаётся `holdUnconfirmed`.

`confirmEnvelopeOnWire` — единственное место, где доставка становится «отправленной», и вызывает его ПРИЁМНИК, принявший фрейм: relay-enqueue — синхронно, push подписчикам — из своей фоновой горутины, — но никогда не тот код, который лишь решил попробовать. Берёт только `deliveryMu`, списывает попытку, снимает удержание и ставит `LastEmittedAt`; аргумент `dispatchedAt` делает так, что несколько приёмников одной отправки списывают её один раз. Объявление (`publishMessagesEmitted`) клеймит `Announced` под тем же мьютексом и публикует после освобождения, по общему правилу побочных эффектов — callback подписчика может вернуться в Service, — и возвращает клеймо, если шина сбросила событие.

`markEntryEmitted`, напротив, пишет только `Emitted` — консервативный флаг «может ли копия быть у пира», намеренно выставляемый ДО провода. Ни удержание, ни `LastEmittedAt` там писать нельзя: тогда подтверждение приняло бы собственную попытку за уже отвеченную.

`lastReachabilityKickAt` — тот же домен, и существует ради одной гонки: тик снимает достижимость без мьютекса, и kick, попавший в это окно, видит запись ещё не `Held` — то есть не видит её вовсе, — а тик тем временем паркует запись по ответу, который kick только что сделал устаревшим. `kickDeliveryRetriesForReachable` ставит штамп под `deliveryMu` ДО своего обхода и независимо от того, что обход найдёт, — именно потому, что случай, ради которого поле заведено, это когда обход не находит ничего; `armDueDeliveries` сверяет штамп с началом своего прохода и оставляет запись наступившей. Одна метка времени вместо карты по identity: ложное срабатывание стоит одного локального просмотра таблицы маршрутов на следующем тике.

Правило «один на получателя» из шага 1 — это дисциплина очереди, а не оптимизация: отправки уходят в фоновые горутины, поэтому тик, отправивший весь накопленный хвост разом, доставил бы его в том порядке, в каком планировщику случилось их запустить, а Go-карта и вовсе не даёт порядка обхода. `deliveryRetryEntry.LastEmittedAt` (тот же домен, та же запись) — это то, что удерживает слот получателя между отправкой и квитанцией; двигается он только вперёд, потому что одну отправку штампуют и тик, и фоновый push, а общих часов у них нет. `storeDeliveryReceipt` освобождает слот и подтягивает следующее сообщение (`promoteQueueHeadLocked`) внутри своего существующего канонического окна `peerMu → deliveryMu`.

Хелперы `*Locked` требуют от caller-а `deliveryMu.Lock`; точки регистрации (`storeIncomingMessage` для собственных исходящих DM, `storeDeliveryReceipt` для собственных seen-квитанций) берут `deliveryMu` без других доменных мьютексов либо внутри того же канонического окна. `storedMessageStatus`, который отвечает локальному отправителю, ушло ли его сообщение или лежит в очереди, берёт только `deliveryMu.RLock`.

#### `fetchInboxFrame` (чтение gossip-topics + lookup receipt'а из delivery)
Трогает `gossipMu` (чтение `topics[topic]`) и `deliveryMu` (`receipts` через `hasReceiptForMessageLocked`). Оформлено как ПОСЛЕДОВАТЕЛЬНЫЕ окна lock'ов, а не вложенно: сначала `gossipMu.RLock`, скопировать срез топика, release; затем для каждого DM-envelope отдельно короткий `deliveryMu.RLock` ровно под проверку receipt'а. Последовательное расщепление работает потому, что срез топиков уже локальная копия к моменту delivery-чтения — нет data-flow зависимости, требующей держать gossip-lock дальше. Это же сохраняет канонический порядок `deliveryMu → gossipMu`: захват `deliveryMu.RLock` при уже удерживаемом `gossipMu.RLock` был бы обратным ребром и запрещён.

`removeSubscriberConnID` / `removeSubscriberByID` используют то же последовательное расщепление для ПАРЫ записей: удаляют подписчиков под `gossipMu.Lock`, собирают recipient'ов, у которых пропала последняя подписка, ОСВОБОЖДАЮТ `gossipMu`, и только потом зовут `dropReceiptBacklogForOfflineRecipients`, которая берёт `deliveryMu.Lock` и удаляет backlog `receipts` этих recipient'ов (и чистит тени `seenReceipts` / `relayRetry`). Вход с удерживаемым `gossipMu` был бы запрещённым обратным ребром. Внутри дропа, под `deliveryMu.Lock`, берётся `gossipMu.RLock` на ВЕСЬ цикл check+delete (читая `s.subs[recipient]` напрямую, НЕ через моментальный `hasSubscriber`) — это `deliveryMu` СНАРУЖИ → `gossipMu` ВНУТРИ, канонический порядок, deadlock'а нет, release LIFO. Удержание `gossipMu.RLock` на весь цикл закрывает reconnect-гонку: caller уже отпустил `gossipMu`, поэтому параллельный `registerHelloRoute` мог бы переподписать recipient'а в щели; моментальная выборка подписчика с последующим delete позволила бы reconnect'у между выборкой и delete стереть backlog уже онлайн-подписчика. Держа read-lock на всё время, мы делаем проверку «всё ещё офлайн?» и delete атомарными против писателей `s.subs` (`registerHelloRoute` берёт `gossipMu.Lock` и вклиниться не может). Тело делает только in-memory работу, поэтому окно удержания короткое. Путь ре-регистрации (`registerHelloRoute` → `removeSubscriberConnIDLocked`) намеренно НЕ дропает backlog: пир переподписывается в той же критической секции, а не уходит в офлайн.

#### `queuePeerFrame` (peer→delivery кросс-доменная запись)
Точка входа для каждого исходящего DM-frame, маршрутизируемого через backlog pending-очереди. Трогает peer-домен (`s.resolveHealthAddress` читает `health`/`peerIDs`), `deliveryMu` (`pending`, `pendingKeys`, `outbound` через `noteOutboundQueuedLocked`) и status-домен (`s.aggregateStatus.PendingMessages` через `refreshAggregatePendingLocked`). Канонический порядок `peerMu → deliveryMu → statusMu`: `peerMu.Lock` СНАРУЖИ → `deliveryMu.Lock` В СЕРЕДИНЕ → `statusMu.Lock` В САМОЙ СЕРДЦЕВИНЕ вокруг пересчёта агрегатного pending и чтения снапшота `aggregateStatus`. Все три lock'а видят один и тот же delivery-снапшот, поэтому enqueue, dedup-проверка по `pendingKeys` и пересчёт агрегатного pending атомарно согласованы. Все exit-пути — no-key, dup, per-peer overflow, global overflow, normal enqueue — освобождают lock'и в LIFO-порядке до побочных эффектов (ebus-события pending-count) после разблокировки.

#### `flushPendingPeerFrames` / `flushPendingFireAndForget`
Дренируют backlog пира, когда сессия стала доступна. Читают peer-домен (`resolveHealthAddress`, поиск сессии) и мутируют `deliveryMu` (удаление или requeue элементов в `pending`/`pendingKeys`); рефрешат агрегатный статус под `statusMu` при изменении размера backlog'а. Канонический порядок `peerMu → deliveryMu → statusMu`: `peerMu.Lock` СНАРУЖИ → `deliveryMu.Lock` В СЕРЕДИНЕ → `statusMu.Lock` В САМОЙ СЕРДЦЕВИНЕ вокруг refresh'а. Requeue-кейс (отправка провалилась, кадры возвращаются) берёт вложенный stack заново, а не держит исходное окно через network I/O — сетевые записи не должны происходить ни под одним доменным мьютексом. Быстрый путь drain-empty берёт `peerMu.Lock` + `deliveryMu.RLock` + `statusMu.Lock` вокруг `refreshAggregatePendingLocked`, потому что пересчёт агрегатного pending читает delivery-доменные поля и пишет status-доменное состояние.

#### Горутина сессии `onCMSessionEstablished` / `onCMSessionTeardown` (регистрация и очистка сессии в map'ах)
Исходящая CM-сессия заносится в `sessions` (peer-домен) и `upstream` (delivery-домен) вместе и вместе же из них удаляется, заодно с `dialOrigin` (peer-домен). Каждая такая запись держит `peerMu.Lock` СНАРУЖИ с вложенным `deliveryMu.Lock` ВНУТРИ, канонический `peerMu → deliveryMu`, поэтому читатель, берущий оба, никогда не видит сессию в одной map'е без другой. Горутина сессии, которую запускает `onCMSessionEstablished`, регистрирует сессию после успеха `initPeerSession` и удаляет её, когда возвращается `servePeerSession`; `onCMSessionTeardown`, который CM вызывает на своём событийном цикле после освобождения `cm.mu`, удаляет её, когда CM деактивирует слот. Удаление сравнивает указатель сессии, поэтому сессия-замена, зарегистрированная на тот же адрес, не трогается. Регистрация и дерегистрация маршрута (`onPeerSessionEstablished` / `onPeerSessionClosed*`) НЕ привязаны к тому, кто удалил запись: обе выполняет горутина сессии, в этом порядке, ровно один раз на сессию, а `onCMSessionTeardown` маршрутизацию не трогает никогда — иначе teardown, пришедший между регистрацией и `onPeerSessionEstablished`, мог бы дерегистрировать маршрут до его добавления и оставить его зарегистрированным за закрытой сессией.

Регистрация против конкурентного закрытия CM. CM записывает причину закрытия (`peerSession.closedBy`, atomic, внутри `closeOnce`) в `tearDownSession`, на своём событийном цикле с отпущенным `cm.mu`, ДО вызова `onCMSessionTeardown`, который удаляет запись под `peerMu`. Горутина проверяет причину и регистрирует сессию в ОДНОЙ секции `peerMu` (`registerCMSession`). Либо секция `peerMu` teardown'а идёт первой — тогда секция горутины упорядочена после записи причины, видит её и не регистрирует, — либо первой идёт секция горутины, и последующий teardown находит запись и снимает её. Поэтому сессия, которую CM закрыл, никогда не остаётся в `sessions` / `upstream`, а сессия, закрытая до регистрации, никогда не помечается подключённой и не учитывается в `identitySessions`. Lock для этого не добавляется: ни одна из сторон не держит `cm.mu` (что берётся под ним — см. `connBudget` выше), а причина — atomic.

Не покрывается выселение, пришедшее ПОСЛЕ возврата `registerCMSession` и до `markPeerConnected` / `onPeerSessionEstablished`. Такая сессия публикуется — регистрируется, помечается подключённой, учитывается — и спустя мгновение снимается собственной очисткой горутины, когда serve-цикл видит закрытый сокет. Гарантировано и в этом случае: учёт сходится (горутина регистрирует и дерегистрирует, по порядку, ровно один раз), и пиру ничего не вменяется. Не гарантировано: что ни один читатель не увидит сессию живой в этом окне. Повторная проверка перед каждым следующим шагом лишь сузила бы окно, поэтому её нет. Инвариант B, таким образом, ровно такой: сессия, закрытая локальным решением, никогда не вменяется пиру, а сессия, закрытая ДО регистрации, никогда не публикуется. Ни одна из сторон не трогает `pending`: backlog пира дренирует `flushPendingPeerFrames` (секция выше) после регистрации.

#### `rebuildPeerHealthSnapshot` (hot-reads refresher для fetch_peer_health)
Собирает atomic-снапшот, lock-free потребляемый RPC `fetch_peer_health`. Читает peer-домен (`health`, `peerIDs`, `peerVersions`, session map, capabilities) и delivery-домен (`pending` для per-peer queued-count). Порядок: `peerMu.RLock` СНАРУЖИ → `deliveryMu.RLock` ВНУТРИ, канонический `peerMu → deliveryMu`. Оба lock'а освобождаются до `atomic.Pointer.Store`, поэтому сам swap — lock-free. Кросс-доменный scope осмыслен: хендлер обязан рендерить per-peer pending-счётчик против того же roster'а пиров, который наблюдал, иначе только что появившийся пир был бы показан с нулём pending, хотя `queuePeerFrame` уже успел туда положить несколько микросекунд назад.

#### `penalizeOldProtocolPeer` / `applySelfIdentityCooldown` (вызыватели peer-delta emit)
Оба дёргают `emitPeerHealthDeltaLocked` после мутации peer-домена. Контракт `emitPeerHealthDeltaLocked` требует от вызывающего держать ОБА `peerMu` и `deliveryMu` как минимум на чтение, потому что его тело спускается в `publishAggregateStatusChangedLocked` → `refreshAggregatePendingLocked`, которая считает `pending`. Оба вызывателя оборачивают вызов коротким `deliveryMu.RLock`/`RUnlock`, вложенным в уже удерживаемое `peerMu.Lock`-окно — канонический порядок `peerMu → deliveryMu` сохраняется. Мутации version-policy внутри `penalizeOldProtocolPeer` (`recordIncompatibleObservationLocked`, `setVersionLockoutLocked`, `recomputeVersionPolicyLocked`) оборачивают всю version-policy-секцию `statusMu.Lock` В САМОЙ СЕРДЦЕВИНЕ, потому что `versionPolicy` теперь живёт под `statusMu`. Сам helper `emitPeerHealthDeltaLocked` внутри `deliveryMu.RLock` не берёт — каждый вызыватель его уже держит (см. `updatePeerStateLocked` ниже), а рекурсивный RLock под writer-preferring `sync.RWMutex` Go deadlock'ится, как только между захватами встаёт writer.

#### `updatePeerStateLocked` / `emitPeerHealthDeltaLocked` (пересчёт агрегатного статуса)
`updatePeerStateLocked` держит `peerMu.Lock` и, на всю длительность тела функции, `deliveryMu.RLock` через `defer`. RLock покрывает и log-строку с `s.pending`, и нижележащую цепочку `publishAggregateStatusChangedLocked` → `refreshAggregatePendingLocked`/`computeAggregateStatusLocked`, поэтому все delivery-чтения внутри scope наблюдают согласованный снапшот. Вызов `publishAggregateStatusChangedLocked` обёрнут вложенным `statusMu.Lock`, канонический `peerMu → deliveryMu → statusMu`. Контракт `emitPeerHealthDeltaLocked` задокументирован как «caller держит и peerMu, и deliveryMu как минимум на чтение»; helper полагается на scope вызывающего, а не вкладывает RLock сам, потому что каждый вызыватель уже держит `deliveryMu` на чтение — `updatePeerStateLocked` через собственный отложенный RLock, `penalizeOldProtocolPeer` и `applySelfIdentityCooldown` через короткий RLock вокруг вызова, — а рекурсивный RLock внутри helper'а под writer-preferring `sync.RWMutex` Go deadlock'ится всякий раз, когда writer встал между двумя acquisition'ами.

#### Хелперы агрегатного статуса (`computeAggregateStatusLocked`, `refreshAggregateStatusLocked`, `refreshAggregatePendingLocked`, `publishAggregateStatusChangedLocked`)
Все четыре требуют от caller'а держать `peerMu` И `deliveryMu` как минимум на чтение (delivery-домен — `pending`; peer-домен — `health` через `computeAggregateStatusLocked`). `computeAggregateStatusLocked` читает только peer- и delivery-доменные поля и НЕ требует `statusMu`. Остальные три (`refreshAggregateStatusLocked`, `refreshAggregatePendingLocked`, `publishAggregateStatusChangedLocked`) дополнительно требуют `statusMu.Lock`, потому что пишут `aggregateStatus`, `lastPublishedAggregateStatus` или `lastAggregateStatusPublishAt`. Канонический порядок `peerMu → deliveryMu → statusMu`: СНАРУЖИ → В СЕРЕДИНЕ → В САМОЙ СЕРДЦЕВИНЕ. Ни один из хелперов не берёт `deliveryMu.RLock` сам; self-nested RLock небезопасен под writer-preferring семантикой если writer встал между acquisition'ами, и часть вызывателей уже держит `deliveryMu.Lock` эксклюзивно. Не-Locked точка входа `refreshAggregateStatus` захватывает `peerMu.Lock`, затем `deliveryMu.RLock`, затем `statusMu.Lock`, отпускает LIFO — это единственное место в семействе хелперов, где весь stack берётся заново изнутри.

Чистые читатели агрегатного статуса (`AggregateStatus`, `aggregateStatusFrame`, `VersionPolicySnapshot`) берут ТОЛЬКО `statusMu.RLock` — они читают `aggregateStatus` / `versionPolicy`, не трогая peer- или delivery-состояние. Это центральный выигрыш Фазы 2 для Desktop-UI RPC: писательский шторм на `peerMu` больше не блокирует чтение статуса, потому что читатель держит непересекающийся мьютекс.

- `peerSession.admission` (`peerSessionAdmission`, `peer_session_admission.go` — приём RESPONSE-плоскости на одного соседа в рамках одной исходящей сессии: сырой байтовый и кадровый бюджет, списываемый вокруг каждого чтения, отдельный подбюджет для незапрошенного `push_message`, запись об ожидаемом ответе и журнал нарушений) — защищён СОБСТВЕННЫМ встроенным `sync.Mutex`, сознательно вне семидоменного разделения, как **лист**. Его берут ровно две горутины — читатель сессии (`readPeerSession`, один-два раза на кадр) и помощник запроса на serve-петле (`peerSessionRequest`, регистрирующий ожидаемый ответ), — он никогда не удерживается через I/O, колбэк или доменный мьютекс и защищает лишь четыре float-а и строку, поэтому новых рёбер в каноническом порядке захвата не создаёт. Он НЕ под `peerMu`, в отличие от остальных полей `peerSession`, переживающих рукопожатие, и причина — горячий путь: это приёмный путь каждой peer-сессии узла, и проводить поframe-арифметику через самый нагруженный писательский лок узла значило бы сериализовать всю сеть против несвязанных писателей peer-состояния. Состояние хранится ПО ЗНАЧЕНИЮ, а его нулевое значение — живой контроллер с полными вёдрами, поэтому ни одна точка конструирования не может забыть его создать, и отсутствующий контроллер никогда не означает молча «у этого соседа нет бюджета».
- `peerSession.closedBy` (`atomic.Pointer[peerSessionCloser]`, `service.go` — кто закрыл сессию ПЕРВЫМ: её владелец либо локальное выселение или shutdown ConnectionManager; nil, пока сессия открыта) — сознательно вне семидоменного разделения: пишется ровно один раз, внутри `closeOnce` сессии и до разборки транспорта, а каждое последующее чтение лишь сравнивает значение. CM пишет его на своём событийном цикле в `tearDownSession`, после освобождения `cm.mu` и до вызова `OnSessionTeardown`; горутина сессии — всякий раз, когда закрывает сессию сама. Ни один писатель не держит доменный мьютекс, и atomic рёбер не добавляет. Читатели читают его либо после возврата собственного `Close` (`sync.Once` упорядочивает их после победившего закрытия), либо под `peerMu` при регистрации (`registerCMSession`, почему это свободно от гонки с `onCMSessionTeardown` — см. секцию о map'ах сессий).

- `contactVerifyBudgets` (`contactVerifyRegistry`, `contact_verify_budget.go` — узловой бюджет РАБОТЫ на ответ `contacts` в разрезе удалённой точки: одно пополняемое ведро токенов на endpoint, один токен на `identity.VerifyBoxKeyBinding`) — защищён СОБСТВЕННЫМ встроенным `sync.Mutex`, сознательно вне семидоменного разделения, как **лист**. Его берут два импортёра контактов (`syncContactsViaSession` на горутине сессии, `syncPeer` на горутине прохода восстановления), он никогда не удерживается через I/O, колбэк или доменный мьютекс и защищает лишь арифметику и ограниченную карту, поэтому новых рёбер в каноническом порядке захвата не создаёт. Два следствия правила «под ним нет ни колбэков, ни I/O» закреплены структурно, а не по договорённости: внедряемые часы — это `atomic.Pointer`, читаемый ДО захвата лока (та же форма, что у `PeerAdmission` плоскости датаграмм), а warn о насыщении реестра решается под локом, но ЛОГИРУЕТСЯ вызывающим уже после освобождения — `charge` возвращает факты, а не печатает их, потому что sink логов под этим локом останавливал бы проверку контактов для всех удалённых точек узла. Он НЕ поле сессии — в отличие от бюджета, который заменил: ведро, жившее в `peerSession.admission`, рождалось полным с каждым реконнектом, а у свежего восстановительного дозвона сессии нет вовсе, и оба сброса были бюджетом, который тарифицируемая сторона могла выкупить заново, просто открыв соединение. Состояние хранится ПО ЗНАЧЕНИЮ в `Service`, а его нулевое значение — живой реестр (карта создаётся при первом использовании, nil-часы = стенные), поэтому ни одна точка конструирования — ни продакшн, ни тестовые Service из структурных литералов — не может забыть его создать, и отсутствующий реестр никогда не означает молча «у этой удалённой точки нет бюджета».

#### `peerSession.sendMu` — забор исходящей очереди

На исходящем пути сессии ДВЕ очереди: `peerSession.sendCh` (верхняя — в неё пишут произвольные горутины, читает только `servePeerSession`) и `NetCore.sendCh` (нижняя — читает только горутина-writer соединения). Кадр может нести контракт отправки (`netcore.WriteTicket`: дедлайн отправки и write-грейс на один кадр — и больше ничего, тикет едет в одну сторону и ничего не сообщает обратно). Каждая очередь всё равно обязана выбросить весь свой остаток в момент своей смерти: без дренажа кадры мёртвой сессии остаются подвешенными на буферизованном канале, пока сессию хоть кто-то держит, и мигающий пир оставляет по такому буферу на попытку.

`peerSession.sendMu` (`sync.Mutex`, `peer_send_queue.go`) защищает ровно один булев флаг `sendClosed` и огораживает неблокирующую отправку в `sendCh`. Он живёт ВНЕ семидоменной схемы, как **лист**: он никогда не удерживается при захвате доменного мьютекса, и ни один доменный мьютекс не удерживается на время `enqueueSend`. `dispatchOutboundAnnouncePlaneFrameWithCaps` захватывает сессию под `peerMu.RLock` и ставит в очередь только после освобождения; `enqueuePeerSendItem` резолвит сессию (`activePeerSession`) и состояние пира (`peerState`) через их собственные короткие секции и ставит в очередь после них. Новых рёбер в каноническом порядке забор не создаёт.

Почему забор, а не `close(sendCh)`: продюсеры работают на произвольных горутинах и не имеют права ни блокироваться, ни паниковать, а продюсер, гонящийся с `close`, паникует на отправке. Флип флага под тем же мьютексом, который продюсеры держат во время своей неблокирующей отправки, выжидает уже вошедшего продюсера и отказывает всем последующим — поэтому идущий следом дренаж по построению видит весь остаток.

ТО ЖЕ правило действует слоем ниже и по той же причине: `NetCore.sendCh` тоже никогда не закрывается. Мьютекс-забор ему не подходит: один из его продюсеров (`queueFrameBlocking` под `SendRawSyncBlocking`) ждёт внутри отправки слот, освободить который может только writer, — забор заставил бы `Close` ждать продюсера, который ждёт `Close`. Вместо забора там монотонный атомарный gate, который каждый продюсер читает по обе стороны своей отправки, и `NetCore.Close` взводит этот gate ДО того, как трогает сокет и сигналит writer'у. Сигнал выхода writer'а — отдельный канал `closing`, поэтому сама очередь никогда не закрывается под живым отправителем. Кадр, который гонящийся продюсер всё же положил, получает ответ от gate и освобождается вместе с буфером, когда собирается `NetCore`. Gate же и НАЗЫВАЕТ teardown продюсеру, уже прошедшему дверь: и отказ сокета, и штатный `Close` будят его одним и тем же каналом `writerDone`, поэтому причина читается из gate (`teardownStatus`), а не выводится из того, на чём проснулись, — иначе собственный `Close` caller'а возвращался как `SendWriterDone`, то есть как приглашение закрыть ещё раз. См. `docs/protocol/network_core.md`, раздел «Владение очередью».

**Терминальных колбэков, которые надо держать вне локов, здесь нет.** Контракт отправки — это данные, а не хук: writer читает с тикета `SendUntil` и `WriteGrace`, и наверх ничто не вызывается. `enqueueSend` по-прежнему выносит защищённое предложение в `offerSend` (без суффикса `*Locked` — он сам берёт `ps.sendMu`), чтобы мьютекс удерживался на предложении и ни на чём больше, а `closeSendQueue` по-прежнему дренирует после освобождения `sendMu`. Отказ сообщается продюсеру возвратом `false`, а не колбэком, потому что политикой отката владеет продюсер (pending-кольцо, входящий fallback).

Кто что дренирует на каждом пути смерти (каждый путь обязан закрыть ОБЕ очереди):

| Путь | Верхняя очередь (`sendCh`) | Нижняя очередь (`NetCore.sendCh`) |
|---|---|---|
| ошибка записи в сокет / истёкший write-грейс | выход serve-цикла → `defer closeSendQueue` | writer взводит gate (`gateSocketFailed`), выбрасывает всё буферизованное и остаётся в режиме drain-only |
| выход `servePeerSession` (отмена ctx, ошибка пира, смерть writer'а, залипший heartbeat, паника через `crashlog.DeferRecover`) | `defer closeSendQueue` | `peerSession.Close` → `NetCore.Close` |
| `peerSession.Close` до старта serve-цикла (провал рукопожатия, несовпадение поколения слота CM) | сначала `closeSendQueue`, потом транспорт | `NetCore.Close` взводит gate и сигналит `closing`; writer дренирует очередь до возврата из `Close` |
| `NetCore.Close` | — | сначала взводится gate (продюсеры получают `SendChanClosed`), затем закрывается сокет, затем `closing`, затем ожидание `writerExited` (а НЕ `writerDone`: после ошибки записи writer всё ещё владеет `sendCh`) |
| отказ в постановке (нет сессии, пир stalled, очередь переполнена, канал закрыт, ошибка сериализации) | `enqueueSend` / `enqueuePeerSendItem` отвечают `false` на входе, то есть кадр точно не начинал записи | `SendRawTracked` отвечает не-`SendOK` статусом. Отказы НА ВХОДЕ (`SendBufferFull`, `SendMarshalError`, gate, прочитанный до постановки) доказывают, что кадр в очередь не попал; отказ, прочитанный ПОСЛЕ постановки, доказывает лишь то, что очередь его не запишет — см. `docs/protocol/network_core.md`, «Tracked-отправки» |

Истёкший `SendUntil` в таблице отсутствует сознательно: это вообще не смерть очереди. Writer пропускает кадр непосредственно перед `rawConn.Write`, соединение остаётся живым, и кадры за ним идут дальше.

`markPeerDisconnected` отсутствует в таблице тоже сознательно: он меняет только health/state и не владеет ни одной очередью. Любой путь, доходящий до него, доходит и до выхода serve-цикла либо до `peerSession.Close` — а это и есть два владельца забора.

**Контракт порядка — забор поднимается РАНЬШЕ, чем пир публикуется как ушедший.** Продюсер читает два факта как одно решение: гейт состояния пира (`peerAcceptsOutboundFrames`, который пишет `markPeerDisconnected`) и ответ самой очереди. Честной эту пару делает только такой порядок. Опубликованный первым, disconnect оставляет окно, в котором продюсер, допущенный мгновением раньше, всё ещё кладёт кадр в очередь, которую этот же teardown вот-вот выбросит, — а эмиттер датаграмм, считающий «очередь приняла» доставкой, ЗАВЕРШАЕТ на этом обход остальных соединений пира, и кадр не доходит ни до этого сокета, ни до следующего кандидата. Реализуют контракт два teardown-а, владеющих очередью: `retirePeerSession` (`closeSendQueue` → `markPeerDisconnected`) на исходящем ярусе и `trackInboundDisconnect` (`NetCore.ShutSendQueue` → `markPeerDisconnected`) на принятом. Оба ставят забор БЕЗУСЛОВНО — принятый ярус делает это даже тогда, когда это была не последняя ссылка, удерживающая строку health, — и оба делают это вне всех мьютексов, поэтому пара не добавляет рёбер в канонический порядок захвата.

Контракт ОБЕСПЕЧЕН тестом, а не только описан. `send_admission_race_test.go` переплетает одного продюсера и один teardown через два шва, в проде равных nil: `Service.sendAdmissionBarrier` паркует ПРОДЮСЕРА внутри окна допуска (после гейта состояния пира, до постановки в очередь), а `Service.peerTeardownBarrier` паркует TEARDOWN, на его собственной горутине, МЕЖДУ двумя его публикациями. Нужны обе половины, и одна не заменяет другую: без половины продюсера перевёрнутый порядок просто отсекается гейтом и выглядит корректным; без половины teardown-а teardown целиком отрабатывает внутри барьера продюсера, и возобновлённый продюсер видит один и тот же мир при любом порядке этих двух операторов — именно так более ранняя версия этих тестов оставалась зелёной на перевёрнутой реализации. Перестановка двух публикаций на любом из ярусов делает соответствующий тест красным.

#### `gossipMu` — забор подписчиков local-change

`s.events` (домен gossip) — это множество inbox'ов подписчиков, а cancel, возвращаемый из `SubscribeLocalChanges`, ЗАКРЫВАЕТ зарегистрированный им inbox. Поэтому дисциплина блокировок издателя — часть безопасности канала, а не только карты: `emitLocalChange` предлагает событие каждому inbox'у, удерживая `gossipMu.RLock`, поэтому закрывающий (он берёт `gossipMu.Lock`) выжидает каждого издателя, уже вошедшего в отправку, и отказывает всем последующим — к этому моменту записи в карте уже нет. Снять снапшот множества под замком и отправлять после его освобождения — НЕ эквивалент: снапшот называет каналы, которые cancel волен закрыть в щели, а отправка в закрытый канал — это паника в той горутине, которая случайно оказалась издателем.

Удержание доменного мьютекса на время отправок не нарушает правило «никакого I/O под замком»: каждая отправка неблокирующая (`select` с `default`), поэтому секция ограничена числом подписчиков и не может вернуться обратно в `Service`. Побочный эффект — warn-строка о переполненном inbox'е — печатается в `emitLocalChange` ПОСЛЕ того, как `offerLocalChangeToSubscribers` отпустила замок, по кросс-доменному правилу выше.

### Инварианты read-path

Горячие RPC-пути, которые уже читают atomic snapshots (`fetch_network_stats`, `fetch_peer_health`, `get_peers`) остаются lock-free; Фаза 2 их не трогает. Что меняет Фаза 2 — это экспозицию *refresher*-горутины к контеншну несвязанных доменов.

Текущий lock-footprint по каждому snapshot-рефрешеру:

- `networkStatsSnapshot` / `peerHealthSnapshot` — короткий `peerMu.RLock` (плюс вложенный `deliveryMu.RLock` там, где считается per-peer queued-count). Callback'ов в ipState нет, `statusMu` не удерживается.
- `cmSlotsSnapshot` — только `cm.mu.RLock` (отдельный мьютекс внутри `ConnectionManager`, доменным разделением не покрывается).
- `peersExchangeSnapshot` — сложнее. `rebuildPeersExchangeSnapshot` берёт короткий `peerMu.RLock` для `persistedMeta` / `health`, отпускает его, затем вызывает `peerProvider.Candidates()`. Этот Candidates запускает callback'и обратно в Service: `BannedIPsFn` захватывает `ipStateMu.RLock`, а `RemoteBannedFn` — `peerMu.RLock → ipStateMu.RLock` в каноническом порядке. Всплеск писателей IP-state (ban-обновления, observed-IP convergence) поэтому всё ещё может задержать именно этот rebuild.
- `routingSnapshot` — `routing.Table.t.mu.Lock` (эксклюзивно: `SnapshotIncremental` потребляет per-identity snap dirty-set и обновляет reuse-кэш; отдельный мьютекс внутри пакета `routing`, доменным разделением не покрывается). Построение проекции гейтится через `routing.Table.ConsumeDirty()` (CAS true→false), поэтому в idle-режиме publisher вообще не строит новый снапшот; rebuild происходит только если какой-то writer пометил таблицу dirty с момента последнего consume. Связующее правило: «любое изменение публикуемого поля снапшота (`Routes`, `FlapState`, `Health`, `CapStats`) ставит coarse dirty-флаг»; writer'ы делятся на две неисчерпывающие группы — *route-projection writers*, меняющие `Routes` и поэтому также метящие per-identity инкрементальный dirty-set (`UpdateRoute`, `WithdrawRoute` / `InvalidateUplinkClaim`, `AddDirectPeer`, `ConfirmHopAck` promotion; `RemoveDirectPeer`, `InvalidateTransitRoutes`, `TickTTL`-экспирация форсируют полную перекопию), и *snapshot-field-only writers*, меняющие `FlapState` / `Health` / `CapStats`, но не маршруты, так что инкрементальная сборка всё равно переиспользует каждый route-слайс (`MarkHopAck`, `MarkProbeAck` / `MarkProbeFailure`, `MarkHopFailure`, `TickHealth`, сброс black-hole cooldown, `RecordSuccessfulRouteAdd`, и engage SeqNo flap-cap на armed `AnnounceTo` / `AnnounceTargetFor`). Publisher за тот же проход строит кэшированный набор `reachable` за O(routes+health), индексируя глобальное подмножество Dead-health только один раз; bulk-readers reachability клонируют или обходят этот набор вместо вызова `BestRoute` для каждой identity. Cached-консумеры (`Service.RoutingSnapshot()` для RPC, `Service.reachableIDsFrame()` для desktop remote-RPC, callback file router'а `RouteSnap`, используемый в transit-форварде внутри `HandleInbound`) на read-path не берут мьютекс таблицы маршрутизации. Если подтверждённый исчезнувший последний маршрут обновляет `last_online_at` доверенного контакта, refresher после публикации снапшота ставит `trustStore.recordLastOnlineAt` в tracked runner `Service.goBackground`. Поэтому JSON marshal/write/rename не выполняется на горутине refresher'а; `WaitBackground` дожидается записи при shutdown и в тестах. `routeTableHandler` дополнительно обогащает каждый уникальный next-hop identity через `RoutingProvider.PeerTransport`, который в текущей реализации берёт `peerMu.RLock` — этот хэндлер поэтому остаётся подвержен writer-штормам peer-домена даже после устранения coupling'а с таблицей маршрутизации; миграция `PeerTransport` на кэшированный peer-transport view отслеживается отдельно. Три production-callsite'а сознательно обходят кэш и читают таблицу напрямую через `routing.Table.Lookup(peer)` — per-destination read, который берёт `t.mu.RLock` для O(K) скана записей _только_ этого destination identity, а не всей таблицы: `file_integration.isPeerReachable` (гейт пользовательских file-transfer'ов), `filerouter.Router.SendFileCommand` (locally-originated путь отправки, wired через `RouterConfig.RouteLookup` на ту же `Lookup`), и `filerouter.Router.ExplainRoute` (диагностический surface, обязан зеркалить live-send). Все трое требуют немедленной видимости маршрута, принятого за секунды до вызова — ~2–2.5 с stale view (2с-порог `routingSnapshotMinInterval` плюс ближайший refresh-тик) проявился бы как «isPeerReachable говорит да, SendFile падает» или как «ExplainRoute показывает путь, который live-send не может использовать». `isPeerReachable` держит `s.peerMu.RLock` только для peer-domain пробы и освобождает его перед routing-чтением, так что два мьютекса остаются последовательными, не вложенными; file-router callsite'ы вообще не берут Service-domain мьютекс на locally-originated пути. Transit-форвард внутри `HandleInbound` продолжает использовать кэшированный `RouteSnap`, потому что in-flight frames несут собственные metadata и ~2–2.5 с задержка (порог coalescing'а снапшота плюс refresh-тик) на свежепринятом маршруте там безвредна. С появлением copy-on-write инкрементального снапшота publisher вызывает `routing.Table.SnapshotIncremental` (он берёт `t.mu.Lock`, а не `RLock`, на короткое построение проекции: потребляет per-identity dirty-set, который поддерживают мутационные обёртки, и переиспользует неизменённые bucket'ы предыдущего снапшота, так что аллокация на rebuild пропорциональна изменённым identity, а не всей таблице). Эксклюзивный захват ограничен — не чаще раза в `routingSnapshotMinInterval` и короче старой полной глубокой копии — и остаётся внутри собственного мьютекса пакета `routing`, поэтому канонический порядок Service-мьютексов не затрагивается. Контракт однопоточного publisher'а здесь несущий: `SnapshotIncremental` кэширует предыдущую проекцию и потребляет dirty-set, поэтому второй конкурентный вызыватель недопустим — любой другой консумер, которому нужна всегда-полная копия, вызывает `routing.Table.Snapshot` (по-прежнему `RLock`, по-прежнему полная глубокая копия). Bulk-мутации (`RemoveDirectPeer`, `InvalidateTransitRoutes`, `TickTTL`) форсируют полную перекопию, и publisher дополнительно апгрейдит уже происходящий (таблица была dirty) rebuild до полной перекопии, когда с момента последней полной прошло `routingSnapshotFullInterval` wall-clock времени — self-heal на случай сайта мутации, забывшего пометить свою identity dirty. Это никогда не будит чистую таблицу: пропущенная пометка может устаревить опубликованный снапшот только если rebuild вообще произошёл (coarse `dirty` выставлен, per-identity mark забыт), поэтому heal лишь подъезжает на будущем dirty-rebuild, а инвариант idle-skip выше сохраняется. Каденция по настенным часам (через timestamp `atomic.Int64 Service.lastRoutingFullSnapAtNanos`, выставляемый единственным snapshot-refresher'ом плюс последовательным startup-prime) выбрана намеренно: счётчик проходов дрейфовал бы вместе с частотой тикера refresher'а, потому что idle clean-skip не двигает `lastRoutingSnapAtNanos`, троттл пропускает каждый тик 500 мс, и счётчик форсил бы full примерно вдвое чаще задуманного.

Что Фаза 2 убирает — это общий контеншн *между доменами*: запись в `fileMu` или `statusMu` больше не блокирует ни один из пяти refresher'ов (`networkStatsSnapshot`, `peerHealthSnapshot`, `peersExchangeSnapshot`, `cmSlotsSnapshot`, `routingSnapshot`). Что Фаза 2 **не** убирает — это внутридоменная связь выше: при разборе staleness-спайка у `get_peers` нужно смотреть и на трафик писателей IP-state, а не только на peer-домен. Эта внутридоменная зависимость — сознательный компромисс: `BannedIPsFn` / `RemoteBannedFn` — это correctness-гейты списка кандидатов; плата за корректность — короткие блоки на IP-state, которые окно staleness 500 мс у snapshot'а поглощает до того, как они доходят до RPC-хендлера.

Presence-классификация не добавляет второго health/routes-прохода внутри этого lock-window: `ReachableIdentitiesWithTransit` одновременно строит reachability и `hasTransit` с одним Dead-health индексом и одной map, а lock-free identity-only кэш публикуется компактным immutable slice.

Персистенция last-online принадлежит node, а не bus. Подтверждённая чистым удалённым EOF потеря direct peer получает timestamp при закрытии сессии и наблюдается после `RemoveDirectPeer`; мутация возвращает post-removal reachability под локом таблицы и с тем же предикатом, что `Snapshot.ReachableIdentitiesWithTransit`. Подтверждённое исчезновение
последнего transit-маршрута определяется сравнением снапшотов. Сериализованная `presenceProjection` хранит, были ли у каждой ранее достижимой identity direct- и/или transit-источники. Direct teardown удаляет свой источник под тем же локом, который сериализует snapshot capture; lifecycle потребляет весь переход только когда действительно публикует подтверждённый финальный EOF, а ambiguous direct close оставляет имевшийся transit-источник snapshot-пути. Поэтому ownership не зависит от того, попали direct- и transit-loss в одно поколение снапшота или в два, и cross-goroutine dedup marker не нужен. Оба пути ровно один раз
ставят `trustStore.recordLastOnlineAt` в `Service.goBackground`, затем публикуют
`identity.presence.changed` как best-effort уведомление. Событие несёт identity
ноды-наблюдателя в `Source`, по которому фильтруются desktop-консумеры общего
bus. Ни filesystem I/O, ни публикация не выполняются под routing-локом;
`ReachableIDs` пишет только route-subscriber со snapshot reason.

#### Cluster-mesh Phase 2 — владелец `RouteHealthState` это `routing.Table.mu`

Phase 2 cluster-mesh плана (не путать с Service-mutex Phase 2
выше — имена совпали случайно; wire-протокол — в
`docs/protocol/route_health.md`, ranking-контракт — в
`docs/routing.md` «Здоровье маршрутов и composite scoring»)
вводит новый per-`(Identity, Uplink)` слой quality-сигналов:
`RouteHealthState` (state machine Good→Questionable→Bad→Dead),
per-pair RTT EWMA и ranking-функцию `CompositeScore`. Решение
по locking-ownership enforced так:

- `healthStore` живёт **внутри `routing.Table`** как leaf-структура без собственного мьютекса. Его защищает `t.mu` — ровно так же, как уже защищает `store` и `flap`. Lookup-path читает uplinks, RTT и health под одним `t.mu.RLock()` без cross-mutex координации — это важно потому, что `sync.RWMutex` в Go отдаёт приоритет писателям (writer в очереди блокирует всех новых читателей), и паттерн «cross-mutex snapshot» создавал бы риск deadlock'а под нагрузкой.
- Writer-методы health (`MarkHopAck`, `MarkProbeAck`, `MarkProbeFailure`, `TickHealth` — приедут в PR 11.2 / 11.3 / 11.4) захватывают `t.mu.Lock()` в W-режиме. Им запрещено выполнять блокирующий I/O (запись в сокет, диск, peer-callback) удерживая lock — канонический протокол: «взять t.mu, помутировать, отпустить, потом (опционально) вызвать `sendFrameViaNetwork[Sync]` вне lock'а».
- RPC-хэндлеры `fetchRouteHealth` И `fetchRouteLookup` (в `internal/core/rpc/routing_commands.go`) синхронно зовут `RoutingProvider.HealthSnapshot()` per request. `fetchRouteLookup` попал на этот путь, когда `Snapshot.Health` сузили до подмножества `{Dead ∪ cooled}` (его CompositeScore-ранжированию нужны полные per-pair тиры); он гейтит вызов наличием живого маршрута у target, поэтому lookup-miss сюда не доходит. Тот вызов приходит в `routing.Table.HealthSnapshot`, которая берёт `t.mu.RLock()`, deep-copy'ит каждый `RouteHealthState` через `healthStore.snapshotLocked`, отпускает lock и возвращает value-slice. Каждое такое RPC-обращение кратко берёт `t.mu` в R-режиме — сейчас НИКАКОГО `atomic.Pointer[healthSnapshot]` кэша между RPC и storage НЕТ. Lock window — это полный проход + deep copy всего health-стора, O(total tracked `(Identity, Uplink)` пар), масштабируется со всей таблицей маршрутизации (сотни тысяч пар на dense-узле, НЕ ограничено числом прямых пиров). Под R-режимом он не блокирует других reader'ов, но `fetchRouteLookup` теперь ходит тем же путём на hit'е, так что высокая частота этих диагностик — реальное copy/lock-давление. Writer-пути с эксклюзивным lock'ом (`MarkHopAck`, `MarkProbeAck`, `TickHealth`, health-bookkeeping в `UpdateRoute`) конкурируют с этими вызовами как с любым другим reader'ом, но writer-preference Go'шной `sync.RWMutex` всё ещё применяется, так что writer в очереди блокирует новые RPC-чтения.
- Eviction в storage'е driver'ит health-cleanup — в точках удаления. `routeStore.onClaimDropped` (в `NewTable` подключён к `healthStore.evictUplinkLocked`) срабатывает под тем же `t.mu.Lock()` для каждого claim, физически покидающего storage: in-place cap-вытеснение в `AdmitNew` / `AdmitDirect` и TTL-компакция в `CompactExpired`. Отдельного reconcile-прохода нет — прежний запускался только когда `CompactExpired` что-то удалял, поэтому cap-замена, победитель которой продлевал TTL, бессрочно оставляла по одной health-записи на каждый вытесненный uplink (28 510 health-записей против 3 585 claims на relay с uptime 5 суток). `RemoveDirectPeer` и `InvalidateTransitRoutes` дополнительно evict'ят eager при tombstoning. `WithdrawRoute` / `InvalidateUplinkClaim` — НЕТ: withdrawn claim становится tombstone (`Hops=HopsInfinity`, `Withdrawn=true`), а его health-запись удаляется, когда `CompactExpired` уберёт tombstone. `Lookup` отфильтровывает withdrawn claims до обращения к health, так что health-запись за tombstone'ом на ranking не влияет и ограничена 1:1 tombstone'ом, который она сопровождает. Инвариант — `health keys ⊆ storage keys`; `Table.Usage` публикует `route_health_orphans` (saturation-gauge, обход O(N_health) под `t.mu.RLock`), чтобы работающая нода могла доказать, что он держится. Отдельного health-only TTL нет.
- Probe и query send-пути (PR 11.3 / 11.4) готовят target-списки под `t.mu.RLock()` (snapshot Questionable pairs / target identity), отпускают lock, потом итерируются по snapshot'у вызывая `sendFrameViaNetwork`. Удержание `t.mu` через wire-send связывало бы routing-state critical sections с socket-I/O latency — это явно запрещено.

#### Cluster-mesh Phase 3 — владелец reputation-полей это `routing.Table.mu`

Phase 3 cluster-mesh плана (полный рабочий документ — `docs/cluster-mesh/phase-3-multipath-reputation.md`, обновление ranking-контракта — `docs/routing.md` «Здоровье маршрутов и composite scoring») расширяет per-`(Identity, Uplink)` слой quality-сигналов hop-ack reputation'ом: `HopAckAttempts`, `HopAckSuccesses`, `ReliabilityScore` (EWMA бинарных outcome'ов), `ConsecutiveFailures` и `CooldownUntil` (black-hole arm). Решение держать эти поля под тем же `routing.Table.t.mu`, что и Phase 2 `RouteHealthState`, зафиксировано в §2.5 phase-документа и enforced так:

- Reputation-поля **встроены прямо в `RouteHealthState`**, а не лежат в параллельной `reputationStore` с собственным мьютексом. Lookup-path атомарно читает `(uplinks, health, RTT, reputation)` под одним `t.mu.RLock()`; cross-mutex координация повторно ввела бы writer-priority pitfall, уже навигированный Phase 2 (writer в очереди на параллельном мьютексе блокировал бы reader'ов Lookup'а, ломая bounded-latency цель).
- Writer-методы reputation (PR 12.2 принесёт расширение `Table.MarkHopAck` и новый `Table.MarkHopFailure`; PR 12.4 подцепит `applyCooldownExpiryLocked` к `Table.TickHealth`) захватывают `t.mu.Lock()` в W-режиме. Как и в Phase 2, им запрещено выполнять блокирующий I/O удерживая lock — multi-path failover (PR 12.3) снимает snapshot ranked uplink set под `t.mu.RLock()`, отпускает lock, потом зовёт `sendFrameToAddressVia` / `sendRelayMessage` вне critical section'а.
- RPC-хэндлер `fetchRouteReputation` (PR 12.7, в `internal/core/rpc/routing_commands.go`) повторяет паттерн `fetchRouteHealth`: `t.mu.RLock()` + deep copy через `Table.ReputationSnapshot`, никакого `atomic.Pointer` кэша. Стоимость остаётся O(N), где N — число tracked pairs (≤24 на identity в densely-connected mesh'ах); promotion к snapshot pointer'у отложен до момента, когда field telemetry покажет contention.
- Eviction следует контракту Phase 2 verbatim: reputation-поля живут внутри `RouteHealthState`, так что тот же `evictUplinkLocked`, что дропает health entry, дропает и его reputation-счётчики. Reputation не персистится через restart (Phase 3 §4.9 решение #6) — process wipe = cold-start warmup для каждого uplink'а.

Разделение катится домен-за-доменом, от самого изолированного. Каждый шаг — самодостаточный commit:

1. `fileMu` — наименьшая поверхность, проще всего верифицировать. **[готово]**
2. `ipStateMu` — изолирован от delivery-путей. **[готово]**
3. `knowledgeMu` — пишет только при handshake. **[готово]**
4. `gossipMu` — покрывает reader-путь `fetch_messages`, чисто ограниченный. **[готово]**
5. `deliveryMu` — relay/outbound очереди. **[готово]**
6. `peerMu` — крупнейший домен; `statusMu` свёрнут в тот же коммит. **[готово]**
7. `statusMu` — свёрнут вместе с `peerMu` (агрегированный статус — производная от peer + delivery state). **[готово]**

Фаза 2 завершена. Поле `s.mu` на `Service` больше не существует; doc-comment каждого `*Locked`-хелпера явно называет, какой именно доменный мьютекс (или мьютексы, в каноническом порядке) требуется вызывающему. Не предполагать никаких значений по умолчанию из прошлого — смотреть doc-comment хелпера.

### Контракт тестов

Каждый шаг миграции должен оставлять существующий node test suite зелёным. Целевые regression-тесты из Фазы 1 (reader-starvation reproducers в `*_starvation_test.go`) перегоняются после каждого шага чтобы подтвердить: свойство no-starvation сохранено или улучшено.
