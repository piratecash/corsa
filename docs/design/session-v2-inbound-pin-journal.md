# N-in quota journal decision / Решение о журнале квоты N-in

## English

**Owner decision, 2026-10-19: approved for implementation and light functional checks.** The owner approved the rolling window, bounded history and conservative time model below. This does not enable N-in classification, approve a resource profile, or close S6/G2/D1. The accepted 20,000 unique-pin bound, N-in class capacity 4,096, no eviction, and separate loopback source group remain as recorded in [the class decision](session-v2-pin-classes.md). Classification still requires a genuine continuous inbound v2 session of at least ten minutes; the journal allows at most 64 new classifications per source group in its rolling window.

### Approved journal and time contract

- Use a **rolling 24-hour window**, with events in `(quotaNow - 24h, quotaNow]`; an event exactly 24 hours old expires.
- Debit **new N-in classification**, after the ten-minute witness, together with its allocation. Immediate mandatory unclassified v2 pinning remains unchanged. Reproof, restart ACK and protective recovery do not debit again. Removal followed by a genuinely new qualifying allocation does debit again, including the same identity. Removal never refunds history.
- Use model A: up to **4,096 retained source-group rows in total**, including one reserved for loopback. This leaves 4,095 dynamic non-loopback rows. Each row stores up to 64 exact event timestamps. At full history capacity, an unseen group cannot earn a new N-in allocation until a row expires; an existing group below its own quota may continue. Ordinary v2 service and already installed pins continue. This is a **new availability limit**, not a consequence of the 4,096 live-class limit.
- Advance a persistent logical quota clock only by observed monotonic elapsed time. Do not credit unverifiable downtime. Wall-clock steps and repeated restarts grant no new budget. Time offline, lost unsaved elapsed progress or an elapsed source excluding suspend can therefore extend the actual waiting period beyond 24 hours. This guarantee assumes the elapsed source does not advance faster than reality; it is not a guarantee against arbitrary host compromise.
- A named, verified upgrade from an official pre-N-in build, with no prior N-in producer or inbound allocations, may initialize **KnownEmpty** without a 24-hour delay. A format number alone is not proof of that history. Imported or synthetic inbound metadata and unsupported restoration require **HistoryUnknown**. Preserve an independently retained, complete current journal in its original clock domain when available; otherwise refuse new N-in classifications for 24 hours of newly observed elapsed time before becoming KnownEmpty. Existing protection remains.

HistoryUnknown waiting is **cumulative observed uptime**, not a fresh 24-hour wait at every ordinary restart. Persist confirmed progress and continue it after restart; losing unsaved progress can only lengthen the wait. Diagnostics must show the restriction reason and remaining observed time. The restriction applies only to new N-in classification; existing pins and otherwise admissible sessions remain available. Classification and debit are persisted atomically; overflow or uncertain persistence must not remove earlier protection.

This decision authorizes implementation and light functional checks, **not resource acceptance**. Heavy configurations, thresholds, release admission and activation remain separate decisions.

### Exact scope of the storage estimate

Proposed packed model A has a 72-byte header and 520 bytes per retained group: a canonical five-byte source-group key, one count byte, two reserved bytes and 64 eight-byte ticks. The header includes model, policy/phase, content generation, logical tick, capacity, row count and checksum. Known/HistoryUnknown phase shares the policy byte; while unknown, the tick records newly observed recovery elapsed time from zero, no new debit is admitted, and reaching the window ends the phase. A separate unknown deadline would require extra bytes and a revised estimate.

Maximum packed payload is `P = 72 + 520G`; the proposed single Base64 JSON member adds `23 + 4*ceil(P/3)` bytes. For `G=4096`, these are **2,129,992 packed bytes** and **2,840,015 additional JSON bytes**. For `G=1024`, they are 532,552 and 710,095 bytes, with only 1,023 dynamic non-loopback groups. These are designed encoding bounds, not measured heap/RSS or total-store bounds. Runtime ownership, allocator overhead, full-main buffers and snapshot copies cost additional memory; replacement can retain both old and temporary files.

Alternative encodings were considered: an exact event pool uses `72 + 13E` packed bytes but adds a global retained-event ceiling; 25 conservative hourly buckets use `72 + 38G` but may retain a burst for nearly 25 hours. Neither alternative was selected; the approved contract uses model A above.

### Required implementation contract

The main pin format must atomically preserve allocation **and debit** in the same full snapshot, including ordinary writes and C3 removal/recovery writes. New readers must require the journal in the new format; old writers must reject that format rather than silently discard history. An independent entry backup never contains or reconstructs the whole journal. Missing/corrupt main remains subject to the existing fail-closed pin-store contract.

Admission rechecks actual inbound proof, continuously live ten-minute witness, original pin incarnation, actual canonical transport group, class capacity including absent C3 reservation, history, context and quota under the existing owner locks. Refusal changes neither allocation nor debit. Only a confirmed strict snapshot acknowledges the captured allocation revision and debit content. Ordinary save does not issue ACK. Unknown/failed commits retain both in memory as counted and unconfirmed; additional N-in promotions wait for a forced strict confirmation, while ordinary service continues. Time sampling alone must not increment debit/content generation or starve ACK; new debits and policy/history changes do.

C3 removal, rollback and single-entry recovery preserve current history and never refund or duplicate a debit. Do not guess a merge of backup timestamp lists: equal timestamps can represent different debits, and different logical clock domains cannot be compared. A supported full restore needs the complete independently retained current journal or enters HistoryUnknown. A checksum or generation inside the same restored file does **not** detect an unannounced rollback of the entire store. Protection against arbitrary out-of-band storage rollback requires an independent anchor and is outside this proposal.

Required checks include exact 64th/65th admission, window boundaries, actual source-group normalization and loopback reservation, concurrent last slots, ten-minute/EOF/reconnect behavior, removal/re-promotion, paired allocation/debit crash states, unknown commit and late cancellation, restart and clock faults, supported restore, legacy migration, malformed/oversized journal rejection, generation overflow, alias isolation and unchanged ordinary pin protection. No such implementation or resource result is claimed by this document.

### Inactive N0 core

N0 implements an internal journal/paired-admission core; **there is no production installation, inbound witness producer, timer, worker, RPC or activation**. Normal fresh, format1/2 and memory-only constructors retain format2 without a journal, elapsed sampling or additional progress writes. The only installation roots are test-source fixtures. Virgin fixtures verify audited main/marker absence and pristine owner state under the exclusive mutation/writer gates; legacy/synthetic/import fixtures install HistoryUnknown. There is no official-upgrade/restore capsule producer in N0, and a format number/checksum is not such authority.

A normal format3 load requires the complete canonical journal, preserves all history and creates a fresh elapsed anchor without crediting downtime. Missing/null/invalid journals refuse startup; required history cannot become nil/empty or format2. Every ordinary, strict metadata/K2, C3 and endpoint snapshot retains format3. Journal content starts runtime-unconfirmed after restart. Only a successful strict committed main snapshot confirms its captured domain/phase/content generation; ordinary persistence does not. Time sampling does not change content generation. Both periodic flush and the serialized writer sample before their no-op decisions. Successful coverage advances only the captured tick; a parked writer cannot erase a later suffix or phase transition. Diagnostics return fixed values/reasons and optional remaining observed time, with producer wiring explicitly false. They start no writes or timers.

Generic metadata CAS now refuses any Inbound change. The private fixture-only paired root requires a real accepted v2 proof, original mandatory pin incarnation, connection-owned lifetime/maturity and source group, then atomically stages the allocation and debit after strict-backend preflight. New staging waits while journal content is uncertain. Already Eligible, reproof, strict retry and protective recovery do not debit; fresh earning after C3 removal does. Historical Pending occupies its existing raw place but must debit to become Eligible. K does not discount raw N-in capacity; an absent C3 backup reserves its class place. Full-entry backup contains no journal, and no rollback/restore merges timestamps or rewinds the live journal. A future N1 must implement/review actual Service inbound publication, exact connection owner, all terminal paths and a joined bounded producer; N0 does not claim those live hooks.

The owner uses a lazy fixed arena of at most4096 rows of520 bytes. Lookup is bounded binary search; reclamation can inspect262144 event slots and insertion/compaction can copy about2MiB under the store mutex. Empty/Unknown owners allocate no arena. A serialized writer owns one bounded row copy; encoding/checksum/I/O occur outside the mutex. Only a fixed captured stamp survives write completion, not the full main DTO/maps. Arena, snapshot, packed/Base64/full-JSON buffers, existing maps and GC overhead have separate costs. Structural/allocation fixtures and unchanged legacy36MiB guard are engineering checks, **not D1 resource admission**, latency guarantees or whole-store read bounds. The initial whole-main read retains its existing behavior. Whole-file rollback detection, verified deployment migration and resource acceptance remain absent.

## Русский

**Решение владельца от 2026-10-19: утверждены реализация и лёгкие функциональные проверки.** Приняты описанные ниже скользящее окно, ограниченная история и консервативная модель времени. Документ не включает N-in, не утверждает ресурсный профиль и не закрывает S6/G2/D1. Сохраняются общий предел 20 000 уникальных pin, квота N-in 4096, запрет вытеснения и отдельная source group loopback. Нужна настоящая непрерывная входящая v2-сессия не короче десяти минут; журнал допускает не более 64 новых классификаций на группу в скользящем окне.

### Утверждённый контракт журнала и времени

- **Скользящие 24 часа:** учитываются события `(quotaNow - 24h, quotaNow]`; ровно на границе 24 часа событие истекает.
- Дебет появляется вместе с **новой классификацией N-in** после десятиминутного свидетельства. Немедленный обязательный unclassified pin не меняется. Reproof, ACK после рестарта и защитное recovery повторного дебета не создают. Удаление и новое полноценное получение N-in, даже той же identity, создаёт новый дебет; удаление историю не возвращает.
- Модель A: **4096 строк истории групп всего**, одна зарезервирована loopback; для остальных групп остаётся 4095. В строке до 64 точных timestamp. При полном журнале новая группа не получает новую классификацию N-in до освобождения строки; уже учтённая группа ниже своих 64 может продолжать. Прежние pin и обычные v2-сессии обслуживаются. Это **новое ограничение доступности**, а не следствие квоты 4096 живых N-in.
- Persistent logical clock продвигается только на наблюдённое monotonic elapsed time; непроверяемое время offline не засчитывается. Перевод wall clock и рестарты не дают нового бюджета. Поэтому offline, потерянное несохранённое продвижение времени и исключённый из elapsed suspend могут увеличить реальное ожидание свыше 24 часов. Гарантия предполагает, что elapsed source не идёт быстрее реальности; произвольный захват host она не покрывает.
- Подтверждённый именованный upgrade из официальной pre-N-in версии, где producer и inbound allocations отсутствовали, может начать с **KnownEmpty без ожидания**. Сам номер формата этого не доказывает. Импортированные/synthetic inbound metadata и неподдерживаемое восстановление требуют **HistoryUnknown**. При наличии независимо сохранённого полного актуального журнала сохраняется он в прежнем clock domain; иначе новая классификация N-in закрыта на 24 часа вновь наблюдённого elapsed time, затем история становится KnownEmpty. Прежняя защита сохраняется.

Ожидание HistoryUnknown — **накопительные 24 часа наблюдённой работы**, а не новое ожидание после каждого обычного рестарта. Подтверждённый прогресс сохраняется и продолжается после рестарта; потеря несохранённого прогресса может только увеличить ожидание. Диагностика показывает причину ограничения и оставшееся наблюдаемое время. Ограничиваются только новые классификации N-in; прежние pin и остальные допустимые сессии сохраняются. Классификация и дебет сохраняются атомарно; переполнение и неопределённость записи не снимают прежнюю защиту.

Это выбор реализации и лёгких функциональных проверок, **не ресурсная приёмка**. Тяжёлые конфигурации, пороги, выпуск и активация утверждаются отдельно.

### Размер и обязательные границы

Проект packed-формата: header 72 байта, строка группы 520 байт — key5, count1, reserved2 и 64 ticks по 8 байт. Phase Known/HistoryUnknown входит в policy byte; в Unknown tick хранит вновь наблюдённое время от нуля, дебетов нет, достижение окна завершает phase. Отдельный deadline потребует пересчёта размера.

`P = 72 + 520G`, JSON-добавка Base64 равна `23 + 4*ceil(P/3)`. При G4096 — **2 129 992 packed bytes / 2 840 015 JSON bytes**; при G1024 — 532 552 / 710 095 и лишь 1023 динамические группы. Это проектный encoded bound, не замер heap/RSS/всего хранилища: allocator, runtime state, полные buffers/snapshots и файлы замены имеют отдельную цену. Другие модели: event pool `72+13E` вводит общий предел событий; 25 часовых buckets `72+38G` могут задержать освобождение почти до 25 часов. Они здесь не принимаются.

Allocation и дебет должны попасть **в один полный main snapshot**, сохраняться ordinary writers и C3. Старый reader обязан отвергать новый формат, не стирать историю. Полный журнал нельзя восстанавливать из single-entry backup; missing/corrupt main сохраняет прежний fail-closed контракт pin store. Допуск проверяет настоящий inbound proof/ConnID, десятиминутное свидетельство, исходную pin incarnation, фактическую transport group, квоты с C3 reservation и отмену. Отказ не меняет allocation/debit. Только strict committed snapshot даёт ACK захваченных allocation revision и debit content. Unknown оставляет оба учтёнными и неподтверждёнными; до forced confirmation новые N-in promotions закрыты, обычная работа продолжается. Чтение/продвижение часов само по себе не меняет content generation и не должно бесконечно срывать ACK.

Удаление, rollback и single-entry recovery не возвращают и не повторяют дебет. Произвольный merge backup timestamps недопустим: одинаковый tick может быть двумя событиями, разные clock domains несопоставимы. Supported full restore сохраняет независимо удержанный полный текущий журнал либо входит в HistoryUnknown. Checksum/generation того же файла не обнаруживают произвольный полный откат store; для такой гарантии нужен независимый anchor, которого проект не добавляет.

До приёмки нужны функциональные 64th/65th и временные границы, нормализация групп/loopback reserve, конкурентные последние места, 10 минут/EOF/reconnect, removal/re-promotion, crash/Unknown/late-cancel, restart/clock faults, restore/migration, malformed/oversized input, overflow и alias isolation. Реализация, результаты проверок и ресурсная приёмка этим документом не заявляются.

### Неактивное ядро N0

N0 реализует внутренний журнал и парный admission; **production installation, inbound witness producer, новый timer/worker/RPC и активация отсутствуют**. Обычные fresh, format1/2 и memory-only constructors сохраняют format2 без журнала, elapsed sampling и дополнительных progress writes. Установка существует только в test-source fixtures. Virgin fixture проверяет audited отсутствие main/marker и pristine owner под exclusive mutation/writer gates; legacy/synthetic/import fixture получает HistoryUnknown. Producer подтверждённого official-upgrade/restore capsule в N0 отсутствует; номер формата/checksum такой authority не даёт.

Обычная загрузка format3 требует полного canonical journal, сохраняет всю историю и создаёт свежий elapsed anchor без зачёта downtime. Missing/null/invalid journal запрещает startup; обязательная история не превращается в nil/empty или format2. Все ordinary, strict metadata/K2, C3 и endpoint snapshots сохраняют format3. После restart journal content снова runtime-unconfirmed. Только успешный strict committed main подтверждает захваченные domain/phase/content generation; ordinary persistence ACK не даёт. Sampling времени не меняет content generation. Periodic flush и serialized writer оба делают sample до no-op решения. Coverage продвигается лишь до захваченного tick; parked writer не стирает поздний suffix или phase transition. Диагностика возвращает фиксированные значения/причины и optional оставшееся наблюдаемое время, producer wiring явно false; запись и timers она не запускает.

Общий metadata CAS теперь запрещает любое изменение Inbound. Private fixture-only paired root требует реальный accepted v2 proof, исходную mandatory pin incarnation, connection-owned lifetime/maturity и source group, затем после preflight strict backend атомарно stages allocation и debit. При неопределённом journal content новые staging ждут. Уже Eligible, reproof, strict retry и защитное recovery дебет не повторяют; новое получение после C3 removal повторяет. Historical Pending использует своё прежнее raw место, но переход в Eligible списывает квоту. K не уменьшает raw N-in count; отсутствующий C3 backup резервирует место класса. Full-entry backup не содержит журнал; rollback/restore не объединяет timestamps и не откатывает живую историю. Будущий N1 отдельно реализует и проверяет actual Service inbound publication, exact connection owner, все terminal paths и joined bounded producer; live hooks N0 не заявляет.

Owner использует lazy fixed arena: максимум4096 строк по520 байт. Lookup — bounded binary search; reclaim может просмотреть262144 event slots, insertion/compaction копирует около2МиБ под mutex store. Empty/Unknown owner arena не выделяет. Serialized writer владеет одной bounded копией строк; encoding/checksum/I/O выполняются вне mutex. После записи удерживается только фиксированный captured stamp, а не полный main DTO/maps. Arena, snapshot, packed/Base64/full-JSON buffers, прежние maps и GC имеют отдельную цену. Structural/allocation fixtures и неизменённый legacy36МиБ guard — инженерные проверки, **не ресурсная приёмка D1**, гарантия latency или bound полного чтения store. Initial whole-main read сохраняет прежнее поведение. Whole-file rollback detection, verified deployment migration и ресурсная приёмка остаются за границей.
