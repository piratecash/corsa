# Неактивная композиция исходного Runtime: Ready и own-DM R

Ready и существующий charged-R own-DM producer создаются через один `serviceConstruction`: один Service, runtime domain, publisher, trust/store и runctx. Исходный R2 port устанавливается после resolver, но до Ready check, последней установки статистики, Seal и возврата объекта. Ready сохраняет точный tuple port/owner/resolver/admission/profile и повторно проверяет его перед завершением. Mint один: старый изолированный конструктор использует тот же helper.

Новый внутренний конструктор принимает явный профиль, возвращает парные Service/port и cleanup исходного cancel и существующего background admission. SDK private candidate выбирает его внутри того же lifecycle body, что публичный `NewWithContext`; публичная обёртка передаёт nil. Typed Desktop проверяет исходные Service/identity и подключает DMCrypto до NodeProber, регистрации MessageStore и escape. Отправка идёт через обычный `Runtime.SendDirectMessage`, его lease/context, настоящее шифрование, SQLite и фактический Route. Новых D1 cfg flags, defaults, worker, фиктивных ACK, второго Runtime и позднего включения нет.

Typed own-DM send сохраняет два разных времени жизни. Operation context SDK по-прежнему управляет шифрованием, SQLite, dispatch и operation drain при закрытии; при возврате метода SDK освобождает и отменяет этот производный context, в том числе после успеха. Optional R residence отдельно сохраняет отмену и deadline исходного вызывающего и остаётся привязана к тому же исходному Service. Поэтому успешный возврат сам по себе не отзывает ожидающую residence и не заменяет исходный writer ACK. Явная отмена вызывающим, его исходный deadline, завершение исходного Service и существующее истечение residence/TTL по-прежнему запрещают ещё не заработанный R. Origin сохраняется один раз на входе Node Submit; cleanup операции, очередь и ACK не обновляют его и не продлевают сроки. Обычные Node/DMCrypto entry points с одним context передают его в обе роли и сохраняют прежнюю семантику отмены. Это разделение не включает активацию и не меняет публичные defaults.

Ошибка/паника конструктора отменяет исходную подготовленную жизнь Node и закрывает её существующий background admission до join и закрытия БД. Обычный Close сохраняет порядок operation/router drain → cancel исходной Node → join Run/background → SQLite. Close до Start отменяет ту же подготовленную жизнь и закрывает admission до Wait. Nil-profile Runtime получает тот же bound cleanup. Уже запущенный Run сохраняет закрытие admission в своём последнем defer; нового Service method/RPC entry нет.

Сквозной сценарий использует настоящие C→Y→X. Все три loopback Runtime явно задают SDK `NodeConfig.EnableDatagramV1` до `New`: это отображение существующего внутреннего transport flag, а zero/default SDK по-прежнему оставляют его выключенным. Сам флаг не выбирает D1 owner, не даёт R и не меняет публичные defaults. Тест проверяет через существующий `DatagramRuntimeState`, что datagram plane каждого исходного Service создан. DMCrypto делает X контактом K до Submit; Y остаётся non-K. Включённый plane позволяет исходный authenticated `push_identity` настоящего signed min2 record. Наличие ключей Y в `fetch_contacts` само по себе не доказывает импорт signed record: их также может дать Hello. Подтверждённый R всё ещё требует, чтобы неизменённый worker нашёл, проверил и повторно сверил точный текущий signed min2 record в исходном trust store. Тест не подменяет clock/record/route/session/ACK: наблюдает реальный маршрут, выдерживает исходный startup-интервал, вызывает SDK send, сравнивает ciphertext в обеих SQLite и echo, проверяет подпись sender, ждёт подтверждённый R с ProvenNextHop у Y и завершает тот же Runtime. Проверка запрета R до исходного writer ACK остаётся в существующих направленных Node fault tests; новый SDK positive не заявляет управляемый pre-ACK barrier.

Направленные тесты проверяют исходную construction и отмену, замену paired owner, Close до Start, ошибку конструктора и описанный выше настоящий SDK/SQLite/non-contact-hop сценарий. Результаты проверок и оставшиеся условия выпуска ведутся в плане работ. Тестовые значения профиля не являются deployment-порогами или memory acceptance. Активация D1, публичные defaults и release остаются отдельными решениями. Явный datagram opt-in использует существующее объявление transport capabilities и сам по себе не означает активацию D1.
